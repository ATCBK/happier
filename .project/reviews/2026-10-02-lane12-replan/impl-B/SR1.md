## FX103: requester custody cannot become another root's Machine authority

Observed canonical owner: `apps/cli/src/api/externalActionExecutionAuthorization.ts:489` (`projectExternalActionRequesterHttpAuthorization`). Its consumers include `ApiClient.readPublishedMachineRowForAuthority` (`apps/cli/src/api/api.ts:941`), installed finite SOURCE inspection and Sync topology preparation. The server's signed-root purpose verifier remains separate from ordinary Account Machine-read authorization.

| Attack / misuse | Result and deciding evidence |
| --- | --- |
| Use only a transported worker-bound root to acquire Account credentials | Refuted. `readRequesterAccountActionContext` reads a host-private Symbol from the Account projection (`requesterAccountActionProjection.ts:238`); JSON/strict wire parsing supplies no such custody. Without that context, the new branch is absent. The wire-root assertion at `requesterAccountActionProjection.test.ts:92` expects signed headers. |
| Substitute another root token, binding, Account or Home while retaining private custody | Refuted at projection. `externalActionExecutionAuthorization.ts:512` compares the custody token and entire binding; `:521` checks projected Account/server. Private admission verifies the credential's profile Account (`requesterAccountActionProjection.ts:278`), encryption mode/material and custody currentness. The substituted-root test at `requesterAccountActionProjection.test.ts:436` expects null. |
| Spend a different Action or child effect through the new bearer branch | Refuted by exact string comparison at `externalActionExecutionAuthorization.ts:574`: the root must be precisely `projects.script.run` or `projects.compute.exec`, and `request.effectActionId` must equal that root. Other effects take the signed path; a signed header is not admission, and the server still checks the effect. |
| Worker-bound root reads SOURCE/controller Machine | Allowed only with its already-admitted current requester custody; this is the intended case. A worker root alone has no bearer. The request is exact uppercase GET of a single Machine-row path other than the bound destination (`:574`). |
| Read a Machine the requester cannot normally read | Refuted by the ordinary endpoint. The new header is the requester's bearer, not the worker/custodian bearer. `apps/server/sources/app/api/routes/machines/machinesRoutes.ts:945` authenticates it and `:972` calls `readAccessibleMachineProjectionInTx` for that actor. Absent access returns 404. A bearer request has no signed managed-guest proof selecting custodian Account authority. |
| Retired custody, writes, destination reads, metadata reads or native execution inherit the bearer | Refuted. The branch checks both `finiteReadCustody.isCurrent()` and HTTP currentness before releasing headers. POST/PATCH and the destination path miss the predicate and keep signed-root headers. Native effects do not use this GET branch. Tests at `requesterAccountActionProjection.test.ts:61` assert signed destination/write/metadata headers, wire exclusion and null after disposal; composed worker tests include foreign SOURCE Account and retirement refusals. |

The server contract agrees: `apps/server/sources/app/auth/externalActionExecutionAuthorization.ts:1081` verifies the original root, and its `readsExecutionMachine` predicate only permits the exact bound Machine, same effect, GET and no body. Project metadata purposes (`:843`) do not authorize an arbitrary other-Machine row. The change supplies an ordinary requester read at the client owner rather than broadening that server execution-purpose authority.

Derived conclusion: no demonstrated cross-Account disclosure, credential borrowing or write/native authority expansion. The private context's credential is used only after its own Account admission and currentness checks; the destination retains resource authorization. Service Move's existing broader preparation-read port remains a distinct Action contract at the same HTTP owner, not a second finite-read decision-maker. No reader-local finite fallback was found in the inspected SOURCE/Sync composition.

## FX99: workspace carrier exception does not dispatch arbitrary RPC

Observed canonical issuance owner: `apps/server/sources/app/machines/peer/mediation/mintDirectRouteGrantV1.ts:276`. The existing producer is `apps/cli/src/daemon/peer/iroh/workspaceMachineCarrierTunnelOpen.ts:103`. It emits the singleton `workspace.sync` label with `rpcScopeId = operationId`, one call, matching single-use label and Machine/endpoint binding. The stream's application consumer is the rooted Sync target authority, not generic RPC dispatch.

| Attack / misuse | Result and deciding evidence |
| --- | --- |
| Add an arbitrary RPC method, allow multiple calls, use another route or include Session authority | The new exemption requires `iroh_peer`, `workspace_sync`, Machine initiator, singleton exact `workspace.sync`, maxCalls 1, absent sessionId and singleton matching highRiskSingleUseMethods (`mintDirectRouteGrantV1.ts:280`). Otherwise canonical RPC classification runs; the unclassified workspace label fails closed. Unit tests explicitly reject ordinary-route, mixed-method and multi-call variants (`mintDirectRouteGrantV1.spec.ts:24`). |
| Forge Machine pair, Account or endpoint | Refuted across real issuance and consumption. The HTTP route authenticates the actor and requires both referenced Machines' current owned admission (`registerPeerMediationGrantRoutes.ts:232`, `:476`); both endpoint authorities must match (`:272`). Strict V2 payload validation precedes signing (`mintDirectRouteGrantV1.ts:379`). The daemon verifies the signature/proof, Account, local Machine/role, signed absolute pair and authenticated remote endpoint (`machineCarrier.ts:196`, `verifyDirectRouteGrant.ts:82`). |
| Substitute another operation or relationship | Refuted by two owners. `packages/protocol/src/connectivity/iroh/machineHandshakeV1.ts:99` requires handshake.operationId to equal signed rpcScopeId. `workspaceSyncTargetAuthority.ts:3110` requires exactly one retained owner matching operationId/sourceMachineId/targetMachineId, local placement and retained root identity; relationship currentness is checked before and after agent acquisition. No caller-supplied root path or RPC method selects the application. |
| Use the carrier grant at generic Machine RPC dispatch | Refuted. Generic dispatch verifies its expected route binding (`mediation/rpc/validateRequest.ts:170`), classifies the requested method (`:225`) and checks scope.allowedMethods (`:251`). A workspace-only scope cannot authorize an arbitrary method. Conversely, the native workspace branch (`daemon/machine/bootstrapMachineSyncRuntime.ts:447`) returns only the approved rooted Sync ingress, not an RPC dispatcher. |
| Remove expiry, change signed fields, omit proof or impersonate a source endpoint | Refuted by strict grant/handshake parsing, signature and ephemeral proof verification. Only registered TCP previews can omit grant expiry (`directRouteGrantV2.ts:209`); this carrier cannot. `verifyDirectRouteGrant.ts:96` rejects at exact expiry. `machineCarrier.test.ts:153` attacks the authenticated source endpoint; `:177` tests exact expiry. |
| Replay a valid grant | **Bounded replay/retry remains possible for the same current operation and pair before expiry.** The verifier does not consume grantId. The Sync owner rejects concurrent active ingress (`workspaceSyncTargetAuthority.ts:3138`) and each local listener accepts one matching first-bytes capability (`:3285`), but cleanup permits a later acquisition for the same retained owner. The existing ingress test (`workspaceSyncTargetAuthority.test.ts:3648`) explicitly exercises retry and rejects another source Machine. This is not a global one-use grant claim. Cross-operation/pair replay still fails the signed binding and retained-owner checks. |

The daemon does not independently repeat the issuer's exact method-label/maxCalls predicate. It enforces signed operation identity, transport identity and rooted application ownership; generic RPC enforces its own method scope. I found no reachable arbitrary-RPC or different-root consequence from that division. Treating the carrier's maxCalls/highRisk labels as proof of globally consumed grant authority would be unsupported. If a separate approved requirement demands grantId consumption across sequential reconnects, that requirement is not established by this review and needs an owner-level decision rather than inferred replay machinery.
