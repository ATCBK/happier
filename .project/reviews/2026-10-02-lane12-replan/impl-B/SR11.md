## SR11-1 — definitive admission refusal becomes an uncertain native outcome

**Observed:** `claimReviewedServiceMoveStart` returns `service_move_start_authority_unavailable` on an unavailable/missing SOURCE authority or failed claim transport (`apps/cli/src/api/externalActionExecutionAuthorization.ts:115`, `:122`, `:131`). The destination returns that typed error at `RpcHandlerManager.ts:842`, before beginning or invoking its Start handler (`:846`–`:852`). This is an explicit negative acknowledgement of this native attempt, even if the SOURCE consumed its boolean before losing the claim acknowledgement.

**Independently exercised:** two read-only, in-memory Vitest variations used the real installed destination/requester/native composition. Only the outbound `callExactMachineRpc` transport boundary for `actionOperation.serviceMoveStart.claim.v1` was substituted: one case threw a synthetic SOURCE transport outage; the other returned `{ kind: 'refused', reasonCode: 'service_move_not_starting' }`. Each used `prepareSignedMove({ sourceCoordinator: true, activeMove: true, ... })`, called its real destination `start()`, asserted exactly one claim attempt, asserted the corresponding typed RPC error, and asserted zero destination native instances. Both passed. Thus the unavailable case is demonstrably refused before native Start; it is not a lost destination Start acknowledgement.

**Derived downstream result:** `projectServiceRelocationRoute.ts:221` converts an unsuccessful child Action to `{ status: 'failed', reasonCode }`. Its strict-result failure at `:227` also produces `failed`; a transport exception propagates to the coordinator catch. `projectServiceRelocation.ts:162` preserves a reason only for `status: 'denied'`, while `:163` maps `failed` to `outcome_uncertain` and `:172`–`:174` do the same for exceptions. Accordingly, none of those paths preserves the new explicit refusal as a definitive pre-establishment denial. This state conclusion is derived from the actual producer/consumer branches, not claimed as an executed full two-host Move.

The existing runner then deliberately retains `outcome_uncertain` as a running observation (`actionOperationRunner.ts:231`–`:234`), marks Move cancellation unsupported and removes its coordinator (`:294`–`:299`), and refuses same-request re-entry (`:336`). Its independently executed existing regression at `actionOperationRunner.test.ts:472` confirms running/no settlement/unsupported cancellation/no replay for an uncertain Move. Those are appropriate safeguards for a possibly established native service; the new admission error reaches them when this destination explicitly did not establish one.

**Concrete failure scenario:** an approved SOURCE → destination Move confirms the old native Stop and completes preparation. During its single destination Start, the destination's callback to the SOURCE loses connectivity or receives an unavailable-method response. The destination receives/sends an explicit claim refusal and does not call native Start. On receipt of that refusal, the original Move should retain the confirmed old Stop and settle with the typed admission failure. Instead the adapter/coordinator discard that distinction and retain an unknown destination outcome. This loses the actionable cause and falsely holds unknown/busy operation state. Plan 32 §9 (`32-service-placement-and-relocation.md:327`–`:330`) distinguishes failed Start after confirmed Stop from lost native-establishment acknowledgement; the current documentation makes the same distinction (`docs/cli-architecture.md:90`).

**Validation required for correction:** exercise a real forwarded Move's original Start with the claim transport unavailable and a delivered negative destination acknowledgement. Assert no destination instance, a failed operation with the typed cause, and retained confirmed-Stop facts. Keep the existing lost-Start-acknowledgement/cancellation/duplicate-attempt regressions uncertain. Extend the existing composed harness; do not fabricate a launcher snapshot merely to satisfy the Start response schema.

Confidence: high for the pre-handler refusal and downstream code derivation; a full source-coordinator → destination → source operation-state reproduction remains unexecuted.

### Raw-claim caller qualification

**Observed:** the request schema carries request id, SOURCE installation id and reviewed input, with no authenticated destination-origin witness (`projectServiceRelocationV1.ts:28`). Its handler validates the target SOURCE admission, not the requesting process's Machine identity (`actionOperationRpcHandlers.ts:125`). Route policy makes it server-required with Machine Use (`routePolicyV1.ts:174`, `:877`); governance labels it internal (`governanceV1.ts:248`, `:407`). The generic server route resolves the authenticated actor's current Machine admission (`apps/server/sources/app/api/socket/rpc/registerSocketRpcHandlers.ts:1830`–`:1857`).

**Derived:** the statement “only the destination can call/consume the raw claim” is stronger than this implementation. The same authorized requester Account can consume its own permission from another client/process. This cannot transfer Start authority to another destination: a destination Start must still pass the existing reviewed-child checks and independently obtain a claim; a previously consumed raw answer is not accepted as a capability. Other Accounts cannot select the victim's operation by supplying its Account id, because that id is not in the input and the scope comes from verified admission.

I did not promote same-Account self-denial into a cross-Account security finding: the same current requester can already cancel its own operation through the adjacent operation owner. If destination-process-exclusive consumption is an independently required security boundary, the current request cannot prove it; that would need an explicit caller contract at the existing admission owner. This review does not invent that additional requirement or a new identity protocol.
