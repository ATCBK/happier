## Replay and Artifact retirement: the actual boundary

**Observed:** `registerSocketRpcHandlers.ts:1081` rejects a duplicate requestId only while active; `:2143–2148` removes that entry when the call settles. The signed-purpose verifier (`externalActionExecutionAuthorization.ts:1372–1478`) neither consumes a packet identifier nor reads an approval Artifact. The SOURCE preparation owner refreshes requester authority and WorkspaceRefs/relationships, not approval-Artifact status (`createProductionDaemonWorkspaceSyncRuntime.ts:875–1015`).

**Derived:** a second sequential submission of the identical valid packet can be relayed while its underlying credential, signed root, Machine/source admission and route remain current. Removing or changing a separate approval Artifact alone is not a revocation signal to this relay. Changing the original envelope, selected source or signed relationship operation is different: the signature/binding fails unless the installed signer produces a new authorized packet. A captured packet cannot be transferred to a different signed input by naming another Artifact.

The normal approval entry point is a separate owner: `packages/protocol/src/actions/actionExecutor.ts:3315` rejects a missing Artifact, `:3330` returns the retained result for an already settled approved request, and `:3338` rejects a non-approved/rejected request before replay. This is not proof that a captured, already-issued SOURCE packet becomes invalid when that Artifact is later deleted. The newly selected FX108 tests do not execute identical-packet replay or Artifact deletion/rejection after capture; no live replay experiment or native repeated-effect guarantee is claimed.

I found no established requirement in this brief or inspected current owner that every valid preparation packet is globally single-use, or that deleting approval history revokes an already-admitted operation. Accordingly, this is an explicit contract limitation, not a speculative replay finding or a recommendation to add a consumption ledger. If Artifact retirement is intended as cancellation of an already-running operation, the parent must establish that contract and test it at its lifecycle owner; this report does not certify it. Current credential/relationship withdrawal remains enforced by the existing owners.
