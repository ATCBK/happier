## SR6-1 — status-only root becomes private catalog read authority

**Location and provenance:** introduced/activated by the worker-status addition at `apps/server/sources/app/auth/externalActionExecutionAuthorization.ts:866`; the overbroad decisions are at `:871` and `:872` in `isProjectAccountMetadataHttpPurpose`.

**Observed:** any schema-valid Project-row read or list is accepted under the unchanged `projects.worker.status` root. The list schema accepts `{}` and makes both `serverId` and `kinds` optional (`packages/protocol/src/projects/projectAccountRowsV1.ts:100`). Its key union also includes Project organization rows (`:18`), whose payload can contain labels and prompt-stack references (`:25`). No predicate compares a row key, requested Home, Project or Machine with the original status operand.

The downstream route supplies only `request.userId` and the requested key/filter to storage (`apps/server/sources/app/api/routes/projects/registerProjectAccountRowRoutes.ts:22`, `:29`). `listProjectAccountRowsInTx` lists the Account's complete reserved namespace and applies only caller-supplied kind/Home filters (`apps/server/sources/app/projects/projectAccountRowService.ts:66`). It does not narrow by the reviewed Project or execution Machine. The authentication decorator stamps the root principal's Account and marks the request externally authorized (`apps/server/sources/app/api/utils/enableAuthentication.ts:192`, `:205`); that marked execution bypasses the ordinary restricted-token route denial (`apiTokenRouteAdmission.ts:282`). Thus the comment about downstream row admission does not establish a Project/Machine scope.

**Concrete misuse, independently reproduced:** create a PAT granting only `projects.worker.status`, with only the bound Machine in its target grant, and mint that status root for one accepted checkout. A direct Account-row list with that PAT returns **403**. The bound installation signer can then sign POST `/v1/account/project-rows/list` with `{}` or `/read` with an unrelated key, keeping the original root/effect/target unchanged. The real Home returns **200** and private plaintext rows for an unrelated Project/unreviewed Machine, a row labeled with another Home, and unrelated Project organization metadata. This requires the valid root plus its authorized installation signer; possession of the root alone does not suffice. The probe supplied no requester Account custody or general Account bearer to those signed reads.

The in-memory extension of the existing real-Home test seeded those rows through the canonical mutation owner and separately seeded another Account's unique row. The deciding results were:

```text
SR6 status-only PAT { directRows: 403, minted: 200 }
SR6 row exposure {
  actionId: 'projects.worker.status',
  offProject: 'present', offHome: 'present',
  organization: 'present', otherAccount: 'absent'
}
```

Handles `77700` and `41266`, nl3, each exited 0 with one selected test passed and exactly one test-only transform. Production logic was unchanged. The second run additionally established the restricted-PAT distinction. A row labeled for another Home remains data stored on this authenticated Home; this did not contact another Home server. Actual plaintext root paths and organization labels were returned. E2EE payload decryption without requester material was not demonstrated.

**Impact and limits:** limited private catalog disclosure beyond the status operand, activated by a safe/read Action rather than an execution/inspection purpose. Account isolation, installed signatures and revocation still hold. No trust/config read, mutation, file-content access or native execution was demonstrated. MEDIUM reflects those limits. The experimental foreign-custodian/view-grant PAT variant returned `target_unavailable`/409 before root issuance (handle `5939`); it supplies no foreign-worker exploit evidence, and this finding does not depend on it.

**Minimal owner-level correction:** remove worker status from the generic signed-root Project-row allowance. Its real worker consumer already requires admitted private requester custody (`apps/cli/src/workspaces/execution/projectWorkerAction.ts:64`). Use that existing custody for its topology row reads at `projectExternalActionRequesterHttpAuthorization`, following the existing private Move preparation-read pattern at `apps/cli/src/api/externalActionExecutionAuthorization.ts:581`, with exact-root/effect and fresh custody checks. This avoids making a bare status root an Account catalog credential and needs no new registry, cache, persistence or coordination. Keep the row reader/publication owner canonical. If root-only signed catalog access is intentionally required instead, its confidentiality expansion and actual scope need an explicit contract; input-schema validity alone does not provide it.

**Required regression:** a status-only root without Account read custody must not acquire private catalog authority; legitimate admitted status must still resolve its SOURCE/worker topology and remain private. Include unrelated Project/Home/organization rows and retain wrong-signature/effect, mutation/trust/config and revoked-Machine refusals. The current positive table proves the broad read, not its confinement. Existing finite/inspection purposes have the same Account-census shape, but their prior contract does not independently justify adding that authority to status.
