## SR8-1 — admission does not preserve the policy that required Ask

**Location and provenance:** introduced by the early `return false` at `apps/cli/src/session/actions/createCliActionExecutorHarness.ts:96`–`:100`. The exemption recognizes an original credentialed host CLI invocation, but proves neither that the receiver will retain its CLI surface nor that the receiver will enforce its approval requirement. `params.credentials` includes ordinary Account credentials; `dispatchOriginalAccountAction` explicitly admits Account and terminal authentication (`apps/cli/src/api/externalActionExecutionAuthorization.ts:226`).

**Concrete misuse scenario:** an automated CLI caller has an ordinary Account credential, uses `surface: 'cli'` and `authority: 'account_automation'`, and invokes `projects.script.run` on its own admitted Machine. Persisted Action settings require approval on `cli` and waive approval on `ui`. The issuer's policy requires Ask, but the new exemption suppresses it. `createCliActionDeps.projectAction` sends the original input through Home (`createCliActionDeps.ts:4725`, `:4741`) without preserving the original CLI surface in the request. The receiving owner resolves an unstamped Account invocation as UI (`externalActionExecutionAuthorization.ts:141`; `executeExternalAction.ts:563`), consumes the UI waiver and admits the command without any approval.

**Observed independent reproduction:** memory-only test/fixture extension of the existing installed filesystem-approval composition, handle **82626**, nl3, exit 1. The fixture uses its generated Account token as the CLI credential, sets `approvalRequiredSurfaces: ['cli']` and `approvalWaivedSurfaces: { [actionId]: ['ui'] }`, then invokes the real credentialed CLI composer and installed receiver. The probe requires `approval_request_created` and no process launch. Current production instead reports:

```text
SR8_ACCOUNT_TOKEN_CLI {"ok":true,"hasApproval":false,"spawned":1,"state":"accepted"}
```

The test waits for the real finite execution path to reach the substituted PTY OS boundary before making that assertion. Home HTTP, transport delivery and native process IO are fixtures; no real credential or shell command was used. There is one appended test transform and one fixture transform, and no production transform in this reproduction. The fixture's existing `pluginActionExecutionOwner: 'current_process'` avoids unrelated contributed-plugin dispatch; finite placement, Action policy, schemas, requester custody, installed factory, operation runner and native command orchestration remain real.

**Causal falsifier:** handle **34166**, nl3, exit 0, runs the identical probe and fixture while removing only the new finite-CLI early-return block in a Vite pre-transform. It reports `hasApproval:true`, `spawned:0`, and the expected approval receipt. Exactly one production module is transformed. This establishes that the new deferral activates the surface mismatch; it does not recommend restoring unsigned local approval replay, which would reintroduce FX127's original admission defect.

**Impact and limits:** commands can cross the configured CLI approval boundary without a decision. This is a policy/consent bypass for an already credentialed caller, not a demonstrated cross-Account privilege escalation. Script Run is reproduced; Prepare and Exec share the same exemption and unstamped Account transport, so their exposure is derived from that shared path, not separately executed here. Normally paired terminal authentication retains the CLI surface and passes the existing Ask/replay composition.

**Minimal owner-level correction:** preserve the originating CLI approval requirement and surface while obtaining Home/Machine admission, and bind any resulting approval to that admitted root through the existing requester/approval owners. A receiver's UI waiver must not replace the CLI policy. Narrow or refuse deferral where the receiving policy cannot be shown to preserve the originating requirement; do not add a consumer-local waiver, restore unsigned replay, weaken Machine admission, or broaden UI policy. Add the unequal CLI/UI policy case to the existing composed owner test and require both a pending approval with zero native launches and successful exact-Machine replay after a decision. Preserve the existing terminal CLI/UI, Deny and missing-Home cases.

Claim: CONFIRMED. Impact: MATERIAL. Proposed response: ACCEPT an owner-level correction. Authority: within the requested approval-admission behavior; implementation remains with the author. Confidence: high on the composed source boundary.

A follow-up probe omitting the supplied provider, **60927**, also returned an accepted operation, but its expected Ask was not the default owner's contract. That failure is excluded from the security finding. The deciding Account-token reproduction above uses actual persisted CLI Ask/UI waiver settings and has no environment dependency.
