This page focuses on **session lifecycle and session control** from the CLI.

If you’re looking for install/auth/server profiles first, start at [CLI](/apps/cli).

For everyday command-line work, use these top-level commands. The longer
`happier session ...` forms remain available when they fit an existing script
or a detailed session workflow.

<Callout>
  **Developer Preview:** the top-level `spawn`, `list`/`ls`, `send`, `history`,
  `wait`, `stop`, and `delegate` commands described here are implemented in the
  current development source but are not released yet. They are first-class CLI
  commands registered alongside the established `happier session ...` family,
  which remains supported for detailed and existing scripted workflows.
  Run the examples below with `hdev` before release, unless you have explicitly
  pointed the `happier` shim at the development lane with
  `happier self release-channel use dev`.
</Callout>

These are complete commands. For the same operation, a first-class command and
its `happier session ...` form use the same request and produce the same JSON
envelope; choose the form that keeps your command or existing script clearest.

| Top-level command | Session command |
| --- | --- |
| `hdev spawn` | `happier session create` |
| `hdev list` or `hdev ls` | `happier session list` |
| `hdev send` | `happier session send` |
| `hdev history` | `happier session history` |
| `hdev wait` | `happier session wait` |
| `hdev stop` | `happier session stop` |
| `hdev delegate` | `happier session delegate start` |

## Session identifiers

Most Session-targeting commands accept a full Session id, an unambiguous id
prefix, or a Session tag. This page uses `<session-id-or-prefix-or-tag>` for
that shared selector. If a prefix matches multiple Sessions, the command fails
and prints candidates (use `--json` for structured output).

### Choose a machine explicitly

The first-class session commands accept `--machine-id <machine-id>`. Use it
when automation must target a known machine rather than rely on the CLI's
current-machine selection:

```bash
hdev spawn "Fix the failing tests" --agent <agent-id> --machine-id <machine-id>
hdev history <session-id-or-prefix-or-tag> --machine-id <machine-id> --follow --jsonl
```

With an API Token, the CLI can use its configured current machine or a sole
current machine. If more than one current machine is available and no target
can be resolved, it returns `machine_selection_required` with candidates;
provide `--machine-id` to make the target explicit.

## Attach vs resume

Use **attach** when the session is still running and you want to reconnect to the live local Agent process:

```bash
happier attach <session-id-or-prefix-or-tag>
```

Use **resume** to continue a session without checking its state first:

```bash
happier resume <session-id-or-prefix-or-tag>
```

Short version:

- **attach** = reconnect to a running session
- **resume** = attach if running and attachable; otherwise reopen an inactive vendor-resumable session

For the full workflows, see [Attach to a running session](/sessions/attach-to-session) and [Resume inactive sessions](/sessions/session-resume).

## Create a session

```bash
hdev spawn --title "My session" --message "Hello"
```

Target a different directory:

```bash
hdev spawn --path /path/to/repo --title "Repo session"
```

- `--env KEY=VALUE` sets one environment variable on the spawned process and can
  be repeated for several (`--env API_BASE=… --env LOG_LEVEL=debug`); the value
  is everything after the first `=`. It is carried only on the CLI's
  direct-to-daemon creation path, so it never enters server-visible creation
  state and is not available when a Session is started from the app or the API.

### Agent targeting (`--agent`)

`--agent` accepts a friendly Agent id from the installed Agent catalog:

```bash
hdev spawn --agent <agent-id>
```

When in doubt, inspect the current schema and available options via the action catalog:

```bash
happier session actions describe session.spawn_new --json
```

Use `spawn` to create a Session from the top-level CLI:

```bash
hdev spawn "Fix the failing tests" --agent <agent-id>
```

### Follow a new session from automation

In the current development source, use `--follow --jsonl` when a script needs
the created Session id and the live transcript in one stream:

```bash
hdev spawn "Fix the failing tests" --agent <agent-id> --follow --jsonl
```

The first line is the normal `session_create` JSON envelope, including
`data.session.id`. Each later line is an existing compact history row. A
session that produces no history rows still emits the creation envelope and
exits successfully.

If creation requires approval, the command emits the successful
`approval_request_created` creation envelope and does not start following. If
creation fails, it emits one failure envelope. If following fails after
creation, the already-emitted creation envelope remains first and a standard
failure envelope terminates the stream.

`--follow --json` is rejected; use `--jsonl` for a multi-line stream. These are
instances of the [CLI automation contract](/apps/cli#cli-automation-contract),
which also fixes the JSON envelope, stdout purity, `0`/`1`/`2` exit codes,
cancellation, and jq pipelines that preserve failure status.

## List sessions

```bash
hdev list
```

Scripting-friendly:

```bash
hdev list --json
```

Useful filters:

```bash
hdev list --active
hdev list --archived
hdev list --resumable
```

### Operational awareness

<Callout>
  **Developer Preview:** `--awareness` is implemented in the current development
  source and is not released yet.
</Callout>

Filtered listing in the development source returns separate ordinary and
attention continuation fields. When `attentionHasNext` is true, pass
`attentionNextCursor` as `--attention-cursor` and repeat the same filters:

```bash
happier session list --scope my_work --attention-cursor '<attentionNextCursor>' --json
```

Use `--cursor` for `nextCursor`. Send only one cursor per request; an exhausted
ordinary page (`hasNext: false`) does not mean attention paging has finished.

`--awareness` asks for the structured operational view of each session instead
of the default summary:

```bash
happier session list --awareness --json
```

The response is explicitly marked so a script can tell it apart from a summary:

```json
{
  "view": "awareness",
  "projectionVersion": 1,
  "sessions": [
    {
      "v": 1,
      "sessionId": "...",
      "lifecycle": "active",
      "runtime": "working",
      "freshness": "live",
      "operational": { "primary": "permission_required", "reasons": ["permission_required", "working"] },
      "encryption": "plain",
      "availability": "complete"
    }
  ],
  "nextCursor": null,
  "hasNext": false
}
```

Notes:

- The states are structured facts, not display strings. `unknown`, `stale`,
  `offline`, and `locked` are truthful answers and never collapse to “idle”.
- `operational.primary` is the one state a compact row shows; concurrent facts
  stay in `operational.reasons`.
- Fields whose content this account cannot read — a title or work headline in a
  session you have no key for — are omitted rather than guessed, and
  `availability` says so.
- Awareness never reads transcripts. The `session.list` action rejects it
  combined with `includeLastMessagePreview` rather than fetching messages.
- If the Home answering the request is older than this view, the command fails
  with `awareness_view_unsupported` instead of silently returning a summary.

## Status

```bash
happier session status <session-id-or-prefix-or-tag>
```

Live status (when supported):

```bash
happier session status <session-id-or-prefix-or-tag> --live
```

`--json` returns the same `awareness` object documented under
[Operational awareness](#operational-awareness) beside the session summary, so a
script reads one session and a list of sessions through the same states. With
`--live`, runtime evidence observed over the socket is folded in before the
states are decided rather than patched onto them afterwards.

## Messaging

Send a user message:

```bash
hdev send <session-id-or-prefix-or-tag> "ping"
```

Observe that exact sent input's outcome (unreleased 0.3 development):

```bash
hdev send <session-id-or-prefix-or-tag> "ping" --reply wait --timeout-seconds 60
```

Or wait for Session idle without sending:

```bash
hdev wait <session-id-or-prefix-or-tag> --timeout 60
```

Notes:

- `send` targets active sessions. For inactive sessions, use `hdev list --resumable` and `happier resume <session-id-or-prefix-or-tag>` first.
- In 0.3 development, `--reply wait` observes the exact admitted input, not Session idle or the lifetime of a Run. See [Reply modes](#reply-modes-03-development); older scripts may use the retained `--wait` ingress spelling.
- `--permission-mode` lets you override the permission intent for a single send.
- `--model` lets you target a specific model for that message when the selected Agent supports it.
- `--json` + explicit timeouts are recommended for scripts.

## Delegate work

Start delegated work from an existing Session with a chosen Agent:

```bash
hdev delegate <session-id-or-prefix-or-tag> "Review the failing tests" --agent <agent-id>
```

Plan and voice-agent runs use their canonical nested commands:

```bash
happier session plan start <session-id-or-prefix-or-tag> --backends <agent-id> --instructions "Plan the change"
happier session voice-agent start <session-id-or-prefix-or-tag> --backends <agent-id> --instructions "Investigate the issue"
```

Besides the Session, `--backends` (or `--agent`) and `--machine-id`, these
commands, and `session review start`, accept every field of their Action as an
ordinary flag with the same spelling as `happier actions invoke` (for example
`--model-id`, `--run-class`, `--io-mode`, `--permission-mode`, and `--retention`
for the retention policy), or the whole Action input with `--input-json`. An
unknown option or an invalid value is refused before any credential is read.

`delegate`, `session plan start`, and `session voice-agent start` select the
credential-aware Action transport before any legacy Session bootstrap. They
therefore also work with `--api-token` or `HAPPIER_TOKEN`, subject to the same
account-automation restrictions as every other API Token invocation.

See [Delegated work](/extending/subagents) for lifecycle and result details.

## Discussions

<Callout>
  **Under development:** the first-class Home Discussion command family is being
  implemented in 0.3 source and is not released. The Session Conversations
  feature must be enabled on the selected Home. Package and live validation of
  this refactor are not complete.
</Callout>

Discussions belong to the selected Home and can exist without a Session. Use
the root `discussions` command, then inspect metadata or read messages:

```bash
happier discussions list --json
happier discussions show <discussion-id> --json
happier discussions read <discussion-id> --json
```

Create a Discussion and post another message:

```bash
happier discussions create "Release notes" "Draft the highlights"
happier discussions post <discussion-id> "I added the migration note"
```

Use `--mentioned-account-ids <account-id>` more than once, or pass a
comma-separated list, to attach explicit Account mentions. For a safe retry
after an ambiguous response, reuse the original identities with
`--creation-local-id` and `--message-local-id` on `create`, or `--local-id` on
`post`. Creation and the first message must use distinct identities; keep both
when retrying an uncertain create.

Manage the Discussion through the same Action-backed command family:

```bash
happier discussions rename <discussion-id> "Updated title"
happier discussions archive <discussion-id>
happier discussions restore <discussion-id>
happier discussions read-state <discussion-id> <last-read-seq>
```

The [host Action reference](/plugins/api/host-actions) owns the full operation
and authority inventory, including participants, invitations, access grants,
Leave and ownership transfer. A Discussion has its own grants and encryption
key; an optional Session anchor grants no access to either resource. Leave
removes only your direct invitation, so inherited Team or Group access may
remain. An owner must transfer ownership or archive instead.

Use `--server-id <saved-home>` to select the exact Home. The command retains that
Home's identity, credentials and endpoint for the operation; the same raw
Discussion id on another Home is a different address. Reading messages does
not acknowledge a person's read cursor. If encrypted creation has an uncertain
outcome, retry with the original identities so the client can recover the
accepted Discussion and its original key. Pending recipient-key delivery does
not mean creation failed.

For the app’s typed participant picker, four answer policies, private draft
review and source-access preview before asking for a second opinion, see
[Discussions](/organize/discussions). These are unreleased development
workflows, not a completed live-conversation certification. A Bot participates
through its ordinary Session; invitation does not start a turn, grant source
access, or change its machine, login or permissions.

The friendly `discussions post` spelling sends text and optional Account
mentions. A literal `@name` in that text is not an executable Session mention.
Use the app’s selected participant reference, or the canonical structured
`discussion.post` / `discussion.reply` Action input in the
[host Action reference](/plugins/api/host-actions). A human reply to an
agent-authored message can address that agent, subject to speaking and delivery
admission; it does not give you control of its Session.

An agent with a current admitted Discussion question can use
`happier discussions pass <discussion-id>` to pass on that exact question.
This Session-bound operation cannot pass for an arbitrary participant. For
private drafts, the entitled person uses the existing approval request to post
or decline; ordinary Action-confirmation settings do not remove that review.

## History

Get recent transcript rows:

```bash
hdev history <session-id-or-prefix-or-tag> --tail 20
```

`--limit 20` remains accepted for existing scripts and has the same behavior.

Scripting / debugging variants:

```bash
hdev history <session-id-or-prefix-or-tag> --json
hdev history <session-id-or-prefix-or-tag> --format raw --include-meta --json
hdev history <session-id-or-prefix-or-tag> --format raw --include-meta --include-structured-payload --json
```

For a human-readable live tail, use `--follow` without `--jsonl`; compact rows
print as they arrive. Use `--follow --jsonl` when another program consumes the
stream: each emitted line is one compact history row. `--follow --json` is
rejected because it cannot represent a multi-line stream.

Use `compact` when you want a simpler text-focused view.
Human compact output limits each long row to 24 lines or 2,000 characters and
marks it as truncated; use `--json` when you need the full text.
Use `raw` when you need provider payloads, metadata, or structured tool/message records.

For semantic transcript items with tool calls and results, use the existing
`session.transcript.get` Action:

```bash
hdev session actions execute <session-id-or-prefix-or-tag> session.transcript.get \
  --input-json '{"includeTools":true,"includeRaw":true,"limit":100}' --json
```

`includeTools` includes tool items; `includeRaw` adds their stored payloads.
Use `hdev session actions describe session.transcript.get --json` to inspect
the available filters and pagination inputs.

## Session control

Stop a session:

```bash
hdev stop <session-id-or-prefix-or-tag>
```

In 0.3 development source, CLI Stop holds the session until you explicitly
resume it. Another ordinary message does not release that hold. See
[resuming inactive sessions](/sessions/session-resume) for the distinction
between explicit Stop and machine resource controls.

Archive / unarchive:

```bash
happier session archive <session-id-or-prefix-or-tag>
happier session unarchive <session-id-or-prefix-or-tag>
```

Update metadata:

```bash
happier session set-title <session-id-or-prefix-or-tag> "New title"
happier session set-model <session-id-or-prefix-or-tag> <model-id>
happier session set-permission-mode <session-id-or-prefix-or-tag> <mode>
```

### Choosing the model source (`--provider-connection`)

A model selection names a model **and** where it comes from. `happier session create`
already accepts `--provider-connection <id>`; `set-model` and `session send` accept the
same flag, plus `native` for the Agent's own model source:

```bash
happier session set-model <session-id-or-prefix-or-tag> <model-id> --provider-connection <connection-id>
happier session set-model <session-id-or-prefix-or-tag> <model-id> --provider-connection native
happier session send <session-id-or-prefix-or-tag> "ping" --model <model-id> --provider-connection <connection-id>
```

Omit the flag to leave the current source unchanged. `native` clears the connection so the
Agent's own model source answers. On `session send` a connection is only ever applied together
with the model selection it sources, so the flag always needs `--model`: an exact `<id>` needs a
concrete model id, and `native` accepts a concrete id or `--model default`.

### Reply modes (0.3 development)

In **unreleased 0.3 development source**, choose reply behavior on the same send
command:

```bash
hdev send <session-id-or-prefix-or-tag> "The API contract is ready." --reply none
hdev send <session-id-or-prefix-or-tag> "Inspect the failure and summarize it." --reply wait --timeout-seconds 300
```

`none` sends information. `wait` observes the answer to that exact input; a
timeout stops waiting without cancelling accepted work. The existing `--wait`
flag remains supported for older scripts, but cannot be combined with `--reply`.
`return` additionally needs an admitted destination for the later answer; it
does not infer one from a standalone CLI's visible or most recent session.
In 0.3 development, a present-person Ask can target another Account's shared
Session. The requester must retain access to the target and input permission
for their own return Session. That Session's readers must also be allowed to
read the target. A machine signed into the requester's Account delivers the
retained answer, even when the return Session runs on another machine.
Returned information never requests an acknowledgment. Pass, failure,
cancellation and no result remain distinct outcomes.

Use [Action discovery](/plugins/api/host-actions) for Session selectors and
current operation support. A group resolves before approval, and approval keeps
the reviewed concrete sessions even if relations change. Selection never grants
access. Follow, Discussion and remaining selector integration may report
unavailable in development; a declared schema is not a promise of support on an
older Home. These contracts do not certify the composed UI or live Voice flow.

### Retrying one message safely (`--local-id`)

`happier session send` prints and returns the message's durable `localId`. If a send fails
ambiguously, retry with that exact id instead of sending again:

```bash
happier session send <session-id-or-prefix-or-tag> "ping" --local-id <local-id>
```

The pending queue is keyed by `localId`, so a retry rejoins the same durable input rather than
queueing a second message. `happier session create` has the same property through
`--spawn-attempt-id <id> --resume-spawn-attempt`.

### Permission intent (`set-permission-mode` and `--permission-mode`)

Happier stores a provider-agnostic **permission intent** string for each session.

Common intents and aliases:

- `default`
- `read_only` (also accepts `read-only`, `readonly`, `ro`)
- `safe-yolo` (also accepts legacy `acceptEdits`)
- `yolo` (also accepts legacy `bypassPermissions`)
- `plan`

Use it in either place:

```bash
happier session set-permission-mode <session-id-or-prefix-or-tag> read_only
hdev send <session-id-or-prefix-or-tag> "ping" --permission-mode safe-yolo
```

Notes:

- `set-permission-mode` updates the session’s persisted intent.
- `session send --permission-mode ...` is a one-message override.
- The exact allowed operations still depend on the Agent runtime, selected model provider, and your account policy.
- Use `--json` to see the normalized intent stored/used.

These session control commands invoke Actions such as:

- `session.title.set`
- `session.model.set`
- `session.permission_mode.set`
- `session.stop`
- `session.archive`
- `session.unarchive`
- `session.wait.idle`
- `session.message.send`
- `execution.run.start`
- `execution.run.send`
- `execution.run.stop`

That is what makes them available not just from the CLI, but also from external MCP hosts and session agents when the relevant surface is enabled.

## Approvals and action gating

Session control commands are implemented as **actions**.

That means:

- each action can be enabled or disabled on the surfaces it supports
- each action can optionally require approval per surface

When a command is approval-gated, the CLI returns an “approval request created” payload instead of executing immediately.
Approve/deny in the app Inbox:

- [Inbox and approvals](/sessions/inbox-and-approvals)
- [Happier tools & actions](/extending/happier-tools)

### Decide approvals from the CLI (advanced)

For automation-heavy workflows, the same approval flow is also available from
`happier session actions execute`.

Example:

```bash
# 1) run an approval-gated command
happier session set-title <session-id-or-prefix-or-tag> "New title" --json

# 2) approve it through the Action command
happier session actions execute <session-id-or-prefix-or-tag> approval.request.decide \
  --input-json '{"artifactId":"<approval-artifact-id>","decision":"approve"}' \
  --json
```

This is the same approval object that the app Inbox shows. A normally signed-in
CLI carries present-user authority and can make the decision. A CLI invocation
authenticated with `--api-token` or `HAPPIER_TOKEN` carries account-automation
authority instead and receives `present_user_required`; API Tokens cannot
approve their own requests. Most users should review in the app.

### Answer an agent tool permission request

An active agent tool approval can be answered through `session.permission.respond`.
Include the specific request ID:

```bash
hdev session actions describe session.permission.respond --json
hdev session actions execute <session-id-or-prefix-or-tag> session.permission.respond \
  --input-json '{"requestId":"<request-id>","decision":"allow"}' --json
```

Use `deny` to reject the request. Inbox Action approvals use
`approval.request.decide` as shown above.

## Actions (advanced scripting)

Use the root Action commands for Account-aware discovery and invocation across
built-in and plugin-contributed Actions:

```bash
hdev actions search [query...] --json
hdev actions get <action-id> --json
hdev actions invoke <action-id> --machine-id <machine-id> --input-json '<json>' --json
```

Plugin-contributed Actions use qualified IDs such as
`acme.notes/actions/save-note`. Use `hdev machines list` when you need an
exact machine ID. The [CLI guide](/apps/cli#discover-machines-and-actions-developer-preview)
covers authentication, targeting, Action settings, JSON envelopes, and errors.

The session-scoped commands remain useful when your script already identifies
a session by ID, prefix, or tag. Discover Actions:

```bash
happier session actions list --json
happier session actions describe <action-id> --json
```

Execute an action:

```bash
happier session actions execute <session-id-or-prefix-or-tag> <action-id> --input-json '<json>' --json
```

Current JSON envelopes:

- `session actions list --json` returns `data.actionSpecs`
- `session actions describe <action-id> --json` returns `data.actionSpec`
- `session actions execute ... --json` returns `data.result`

## Execution runs

Execution runs are the structured “run” layer for multi-step flows (review / plan / delegate / voice agent):

```bash
happier session run start <session-id-or-prefix-or-tag> --intent <intent> --agent <agent-id> --json
happier session run list <session-id-or-prefix-or-tag> --json
happier session run get <session-id-or-prefix-or-tag> <run-id> --json
happier send <session-id-or-prefix-or-tag> "message" --run <run-id> --json
happier session run stop <session-id-or-prefix-or-tag> <run-id> --json
happier session run wait <session-id-or-prefix-or-tag> <run-id> --timeout 300 --json
```

The one-shot lifecycle commands above, plus bounded stream start/read/cancel,
are compiled from the canonical `execution.run.*` Action declarations. Use
`--agent` to select the Agent; there is no separate CLI-only backend flag or
second hand-written run parser. An ID, unambiguous prefix, or tag is resolved to
one exact Session before execution. Ambiguous and missing selectors retain their
typed JSON error and candidate details rather than falling back to another
Session or Home.

Every `--intent` the `execution.run.start` Action accepts can be started this way.
Intents that carry typed input, such as `scm_commit_message` and
`scm_diff_summary`, get their Run kind and run shape (retention, class and I/O
mode) from the intent. Supply the typed input as `intentInput` through the
canonical whole-input JSON:

```bash
happier session run start <session-id-or-prefix-or-tag> --intent scm_commit_message --agent <agent-id> \
  --input-json '{"intentInput":{"scope":{"kind":"paths","include":["src/a.ts"]}}}' --json
```

Advanced run control:

```bash
happier session run action <session-id-or-prefix-or-tag> <run-id> <action-id> --input-json '<json>' --json
happier session run stream-start <session-id-or-prefix-or-tag> <run-id> "message" --json
happier session run stream-read <session-id-or-prefix-or-tag> <run-id> <stream-id> --cursor 0 --json
happier session run stream-cancel <session-id-or-prefix-or-tag> <run-id> <stream-id> --json
```

Input to a session-owned run is ordinary session input with one explicit
destination, so it shares the session send command, its pending admission and its
`--local-id` retry identity:

- `happier send <session-id> "message" --run <run-id>` — canonical spelling.
- `happier session send <session-id> "message" --run <run-id>` — same command.
- `happier session run send <session-id> <run-id> "message"` — deprecated
  compatibility alias for the same operation, keeping its `session_run_send`
  JSON envelope. It no longer accepts `--resume`.

When the target run cannot accept input, the canonical session-input owner
returns its typed refusal, and `--json` reports it in `error.code`. The CLI never
strips `--run` and retries the message into the parent session.

- `session_input_target_update_required` — this Home, the run's exact machine, or
  the targeted-input route cannot carry a destination yet. Nothing was queued, and
  ordinary main-session sends keep working.
- `session_input_target_unavailable` — the destination itself cannot accept input:
  it belongs to another session, has finished, or is not an interactive run. The
  message stays visible in that run's queue as blocked, with the normal retry and
  discard actions.

A run whose state is still unknown — not yet loaded, or being resumed — is neither
of those. Its messages simply stay queued for that run until it is ready.

Adding `--wait` to a `--run` send observes only the turn that message started. A
sibling run finishing, the parent session going idle, or the run reaching a
terminal state does not satisfy it, and the timeout ends the observation without
cancelling or resending the message. If the correlation is lost, the result is
`outcomeUnknown` and keeps the message's local ID, so reuse that same
`--local-id` to reconcile instead of sending a fresh message.

`execution.run.send` is a different Action for a genuinely detached Run and
requires `sessionId: null`. Do not use it for a Run that belongs to a Session;
Session-owned input must stay on `session.message.send --run <run-id>` so it
retains the Session's Pending queue, permissions, encryption, and exact-target
failure behavior.
