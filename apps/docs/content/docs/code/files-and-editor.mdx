A session is attached to a folder on one of your machines, and Happier gives you
that folder directly — not a copy, and not a summary the agent wrote. You can
read what the agent is working on, fix a typo yourself, drop a screenshot into
the repository, or open the file it just mentioned, without leaving the session.

<Callout type="info">
  Browsing and previewing files is part of the normal session UI. The embedded
  editor is a toggle under **Settings → Features → Embedded file editor**, on by
  default. Some actions need the machine running the session to be reachable —
  though if the session is inactive and the machine is still online, Happier can
  still load file data through the machine-level workspace APIs.
</Callout>

## Syntax highlighting (0.3 development)

In the unreleased 0.3 development version, file View and diff views default to
advanced syntax highlighting on web and desktop. Native clients use the simple
tokenizer. An explicitly saved Off, Simple or Advanced preference keeps its
meaning, including preferences saved by 0.2; only an unset preference picks up
the new default.

The existing tokenization budgets still govern large files and long lines.
Content remains readable when highlighting is skipped.

## AI code suggestions (0.3 development)

The unreleased 0.3 development editor includes opt-in AI suggestions. In
**Settings → Source control**, under **Editor · AI suggestions**, choose an existing provider
connection and a compatible model before enabling **Suggest code**. Enabling
it sends context from the open file to that provider. It does not add other
files, clipboard content or repository history.

Choose **While typing** or **On request**; on request uses Alt+\\. The delay
presets change how long the editor waits after typing, rather than setting a
model timeout. Excluded-file patterns and disabled language ids apply before
the machine resolves credentials or sends a request. The defaults exclude
`.env*`, secrets directories and `secrets.*` files. Patterns support `*`, `**`
and `?`, with `/` as the separator.

The usage row shows requests on this device today for the signed-in Account,
and cost only when the provider reports it. Usage counts do not collect source
text or enable training or telemetry. A quiet editor status links back to
settings when suggestions are off, sign-in is needed, the provider rate-limits
requests or the selected model is unavailable. No source is substituted
automatically. This work remains under integration and is not part of the
current stable release.

## Replace in files and blame (0.3 development)

The unreleased Files & Editor work brings replacement review into **Text in
files** and line attribution into the File page. These surfaces are under
integration and are not part of the current stable release.

Replacement reviews a proposed change per file and per match before writing.
Files already holding unsaved editor drafts are excluded from replacement. If a selected file
changes on disk or acquires an editor draft after preview, replacement refuses
the whole selection before writing. Refresh the preview before trying again.
Undo restores replaced
regions only while the file still matches the successful replacement. Literal
replacement keeps dollar signs literal; regex replacement uses JavaScript
capture syntax. Both operate within individual lines and preserve existing
line endings. Binary files and text that is not valid UTF-8 are skipped.

Regex preview uses the same JavaScript matcher as replacement, including
look-around and capture syntax. Cancelling stops between files; the result
still includes completed changes and their Undo data. A lost connection can
leave the outcome unknown, so it is not a reason to repeat the replacement.

Blame combines commit authorship with evidence from the Session whose File page
is open. Committed lines name their commit author. Uncommitted lines name a
Session turn only when its recorded edit still matches the displayed line;
otherwise they remain **Uncommitted**. Team-session attribution uses the same
requester identity and visibility rules as the transcript. A project page
without Session context shows repository attribution only.

## Where it appears

## Desktop layout: sidebar + details pane

The workspace UI is designed around two complementary surfaces:

- **Right sidebar**: quick navigation, tree/status browsing, branch summary, changed-files list, history list
- **Details pane**: deep work on the currently opened item

Typical flow:

1. Open **Files** or **Git** in the right sidebar.
2. Click an item to open it in the details pane.
3. Keep that item as a temporary preview tab, or pin it so it stays open while you inspect other files.

### Details tabs

The details pane supports multiple tabs for:

- file previews
- editable files
- review tabs
- historical commit diffs
- stash details

Important behaviors:

- Tabs keep their local state while you switch between them.
- Scroll position is preserved when you return to a tab.
- If you start editing a file, Happier keeps that editor state instead of reloading it on every tab switch.
- Pinned tabs stay open until you explicitly close them.
- On smaller layouts, the details surface can switch into an overlay instead of permanently shrinking the main session area.

### Give the editor more room (0.3 development)

In unreleased 0.3 development, **Hide session** in the session header hides the
main column while keeping its draft, scroll position and open content. The
restore chip beside the editor shows the session's identity and current state;
use it to show the session again. Projects, Workflows and app pages offer the
same control with their own name when another column is open. The left
navigation column stays independent. Phone layouts keep their existing page
navigation.

Session and Project pages can also use **Session first** or **Editor first**.
Editor first puts the file browser and editor before the session, while keeping
the columns' current content. This device-local preference is part of the 0.3
development layout work and is not available in the current stable release.

On phone-sized layouts the same surfaces live in the
[mobile Cockpit](/apps/app), which gives Files and Git their own tabs.

## Files

<Callout type="info">
  In unreleased 0.3 development source, Project Code uses the same qualified
  workspace browser as Session Files. A folder name opens its page; its
  disclosure control expands the inline tree separately. Code reads the actual
  latest commit touching the current file or folder and each visible entry,
  rather than showing the branch tip for every row. Missing or shallow history
  is shown as unavailable, and a failed refresh keeps known content marked stale.
</Callout>

The **Files** tab is the in-session file manager for the current workspace.

### What you can do

- Browse the repository tree.
- Search for files in the current workspace.
- Create files and folders.
- Upload files into the workspace.
- Choose an explicit upload destination when you do not want the project root.
- Rename and delete files or folders.
- Download a single file.
- Download a folder as a `.zip`.
- Download a single file as a `.zip` when you want archive-style handoff symmetry with folder downloads.
- Open a file in preview or edit mode.
- Filter the file tree down to modified files only.
- Watch transfer progress and cancel an upload or download that is still running.

Opening a file uses the same details surface whether you start from the file tree, a changed-file row, a review diff, a transcript file link, a review-comment jump, or a linked-file chip in the composer.

### Video preview and Android downloads

In the current development build (unreleased), supported MP4, M4V, MOV, and
WebM files open in the file view with playback controls, seeking, and fullscreen.
Playback depends on the codecs available on your device. The video downloads
before playback starts, using the normal file transfer limits; a video can be
larger than the text preview limit without being treated as oversized text.
Web playback also uses the browser's memory budget for buffering files. A
file-backed download may still succeed when a preview is too large.
If loading or playback fails, use **Retry** or download the file to open it in
another app.

On Android, the file view's download menu offers **Save as…**, **Open with…**,
and **Share…**. **Save as…** opens the Android document picker so you can choose
Downloads or another available location. Canceling the picker leaves no saved
file. **Open with…** lets you choose an installed app, and **Share…** sends the
file to another app. Downloads from the file tree use the same save picker.
Opening or sharing a file uses a temporary cached copy; use **Save as…** when
you want to keep a file in a location you can find later.

The transfer cancel control is available while the file downloads. Once the
system opens a save picker, app chooser, or share sheet, use that dialog's
controls instead.

Opened or shared copies stay in Happier's private app cache so the receiving app
can finish reading them. [Android may reclaim cache files when storage is low](https://developer.android.com/training/data-storage/app-specific),
and you can clear Happier's cache in Android's app settings. These copies have no
guaranteed retention period, and Happier does not currently purge them
automatically after an **Open with…** or **Share…** action.

If a save fails after you choose a destination, Happier tries to remove the
incomplete document. If the document provider refuses deletion, the error
identifies the remaining document so you can remove it yourself.

<Callout type="info">
  In the current development build (unreleased), **Project** view hides Git-ignored
  files and repository metadata while keeping tracked files, changed files, and
  files you reveal in the tree reachable. Dotfiles remain visible unless Git
  ignores them. Choose **All files** to include the hidden entries. When ignore
  information is unavailable, including with older Happier versions on the machine
  or outside Git repositories, the tree shows all files with an availability hint.
</Callout>

### Tree rows and status badges

The file tree is repository-aware.

When source-control data is available, Happier can show:

- modified / added / removed badges
- line-count summaries (for example additions/removals)
- folder-level summaries aggregated from descendants

This gives you a lightweight “what changed here?” signal without leaving the Files tab.

Long paths are formatted so the filename stays readable. On web, deeply nested directories use start-side ellipsis behavior, so the left side of a long path is shortened before the filename gets squeezed.

<Callout type="info">
  In the current development build (unreleased), the web file tree supports
  keyboard navigation: Up/Down move between visible rows, Home/End jump to the
  first/last row, Right expands a folder or enters it, and Left collapses it or
  moves to its parent. Enter opens a file preview; P pins the focused file.
</Callout>

### Search and modified-only filtering

Use the Files search field when you already know roughly what you want.

<Callout type="info">
  In the current development build (unreleased), exact filenames and paths rank
  ahead of broader matches. Searching without an extension favors that file's
  name before variants such as test files. While you refine a search, the previous
  results stay visible and are identified as previous results until the new
  results arrive.
</Callout>

Use the modified-only filter when you want the tree to behave more like a focused “changed files” explorer.

Typical use cases:

- narrow a large repo to the files touched by the current task
- find a config file by name, then jump straight into the editor
- browse only modified files while still keeping folder context

For text inside files, use [Search → Text in files](/organize/search#search-inside-workspace-files).
The Files field searches names and paths. Text in files searches the workspace
on the selected machine and opens a hit at its line with Find on the query.
In the 0.3 development channel, a directory-path search also finds files
below that directory. An unavailable or failed search shows an error; it does
not mean the directory contains no matching files.

### Create files and folders

The Files toolbar includes actions to create:

- a new file
- a new folder

These actions are meant for lightweight workspace edits without leaving the session.

### Uploads

Happier supports several upload flows:

- **Upload files** from the Files toolbar
- **Upload folder** on web
- **Drag and drop** files or folders on web
- **Drop onto a directory** to upload directly into that directory
- **Preserve relative folder structure** when you upload a folder or nested tree

Platform notes:

- **Web**: supports drag/drop, multi-file upload, and folder upload
- **iOS / Android**: supports file picking; folder upload is web-only

If your goal is to send a file with your next message instead of placing it into the workspace, use the session **Attachments** flow instead.

See: [Attachments & image previews](/apps/attachments)

### Upload destination selection

The toolbar upload menu includes an upload destination selector.

- If you leave it empty, Happier uploads into the **project root**.
- If you set a workspace-relative path, Happier uploads into that destination and creates missing parent directories as needed.
- Drag/drop over a specific folder row overrides the root/default destination and uploads into that folder.

Typical use cases:

- send generated assets into `docs/assets`
- upload logs into `.project/logs/...`
- drop a folder directly into `src/components`

### Upload conflict handling

When uploaded files already exist at the destination, Happier asks how to resolve the conflict batch:

- **Skip**
- **Replace**
- **Keep both**

`Keep both` is the default. Happier automatically creates a suffixed name such as `file (1).txt`.

### Transfer progress and cancel

Uploads and downloads run as managed transfers instead of fire-and-forget actions.

- Happier shows transfer progress while the upload or download is still active.
- You can cancel a transfer before it finishes.
- Folder `.zip` downloads are built first, then streamed back in chunks.
- Direct file preview, file download, folder download, and review/diff loading all use the same transfer/decryption path for session workspace data.

Platform notes:

- **Web**: downloads use the browser download flow.
- **iOS**: downloads are written to a temporary local file and then passed to the system share flow.
- **Android**: in the current development build (unreleased), downloads from the file tree open **Save as…**. The file view also offers **Open with…** and **Share…** using a temporary cached copy.

### Rename, delete, and download

Each tree row exposes an actions menu.

For files, available actions include:

- Rename
- Delete
- Download
- Download as `.zip`
- Copy path

For directories, available actions include:

- Rename
- Delete
- Download as `.zip`
- Copy path

Directory deletion is confirmed explicitly and applies recursively.

In unreleased 0.3 development source, submitting a rename applies it without a
second approval prompt. An agent's rename request still asks for approval by
default. You can change that Action's approval preferences under
**Settings → Actions**; an explicit requirement there also applies to your own
rename requests. Delete keeps its confirmation.

## File preview and editing

Opening a file from the Files tab or from Review opens it in the details pane.

Depending on the file type, Happier can show:

- a text preview
- a live editor
- an image preview
- a binary-file placeholder when inline rendering is not appropriate

### Image and binary handling

Happier now treats image previews as a first-class workflow:

- common raster images can be previewed inline
- SVG files can also be previewed instead of being treated as opaque binaries
- true binary files stay safe and do not try to render through the text diff pipeline

<Callout type="info">
  The shared Media stage, PDF/audio bodies and Markdown image rendering described
  below are under integration for unreleased 0.3. They are not yet mounted in the
  current file views; this describes the intended development behavior.
</Callout>

The shared Media stage keeps the gallery from the surface you opened, supports zoom and pan,
and returns to the thumbnail when dismissed. Use the arrow keys to move between
items, `0` to fit, `1` for actual size and Esc to close. Background selection is
manual: Checkerboard, Light or Dark, remembered on this device for the file kind.

PDFs use the same PDF implementation in the file view and Artifacts, with page
navigation, zoom and the shared Find controls. Password-protected PDFs need an
external app where you can enter the password. Native previews can be degraded
when a document needs fonts or image decoders that are not embedded; Download
and the platform's open/share options remain available.

Audio opens with playback and seeking controls. Video downloads before playback
and reports transfer progress; codec support still depends on the device.
Opaque binaries show their kind and size with Download and Open as text options.
Artifact previews share the file-preview budget, including the browser's 50 MB
whole-file buffering budget.

Markdown file previews and workspace README cards render standalone workspace
images relative to the Markdown file. Remote images stay unloaded until you
choose Load for that document; Happier remembers that choice on this device.
Inline images retain their alt text. Opening a rendered image uses the document's
image gallery in the Media stage. A large text file can be read in slices rather
than requiring a full-file preview.

If a file has no textual diff (for example an image or binary blob), Happier avoids crashing the diff renderer and falls back to the correct preview/placeholder path instead.

### Editing behavior

The editor is meant to feel like a real editor, not a disposable preview:

- switching tabs does not discard in-progress edits
- opening another file does not replace a pinned editor tab
- reopening the same tab restores the state you left it in

This matters when you:

- compare two files while editing one of them
- jump between Review and an editor tab
- switch sessions and come back later

### The 0.3 editing workflow

<Callout type="info">
  The editor workflow below is being integrated for **unreleased Happier 0.3**.
  It describes the development target, including conflict resolution, draft
  recovery and phone controls; it does not promise those controls in a released
  stable or preview client. Development builds may contain only part of this
  workflow while integration and live validation are in progress.
</Callout>

Open a text file and choose **Edit**. You can also start from **Changes** at the
change you want to edit. The editor keeps your place so you can move between
reading and editing without finding the same line again.

Make your edits, then choose **Save**. Saving leaves the editor open; **Done**
returns to reading. The header shows whether you are editing, have unsaved
changes, are saving, or have just saved. Saving your own edit uses the ordinary
file write and does not ask for a second confirmation by default. An explicit
approval preference can instead leave the save waiting for approval.

In the desktop app, use <kbd>⌘</kbd>+<kbd>S</kbd> on macOS or
<kbd>Ctrl</kbd>+<kbd>S</kbd> on Windows and Linux. In a web browser, use
<kbd>Alt</kbd>+<kbd>S</kbd> (<kbd>⌥</kbd>+<kbd>S</kbd> on macOS), so the browser
keeps its own Save shortcut. The header displays the shortcut for your client.
If several editor groups are open, the shortcut saves the focused group’s active
file. Autosave remains an opt-in preference.

#### Drafts and closing a tab

An unsaved edit pins its preview tab, so opening another file keeps the draft
open. Switching tabs or looking at View or Changes also keeps it. Drafts are
stored on the device where you are editing and can reopen after a reload; they
are not already saved to the Machine or copied to your other devices.

Closing a dirty tab offers **Save**, **Discard**, or **Keep editing**. If Save
fails or is still waiting, the draft stays open. A device-storage failure is
shown explicitly; keep the page open and save or copy the text before leaving
when the draft cannot be stored locally.

#### When the agent changes the same file

A save checks the version of the file you started from. If the file changes on
disk while your draft differs, the conflict line offers **Compare**, **Use mine**
and **Use theirs**. When Happier knows which agent wrote it, the last choice
names that agent.

Compare shows the disk version against your draft, with a choice for each
conflicting place. You can keep your text in one place and use the disk text in
another, then return to editing and save the merged draft. After restoring a
draft from a reload, Compare may ask about every place because the original
file text is no longer held on that device.

**Use mine** saves your draft against the disk version you were shown; another
change can still refuse that write. **Use theirs** replaces the buffer with the
disk version and keeps your displaced draft for Undo. Both choices offer a
dismissible **Undo** notice. It remains until you dismiss it or take the next
edit, save, comparison or review action; the notice has no countdown. Undo that
writes back to disk checks the version again too.

#### Editing while the Machine is offline

You can start or continue editing when Happier already holds the complete file
text, even if its Machine becomes unreachable. A restored draft can also reopen
without a fresh disk read. If neither the text nor a draft is on this device,
connect to the Machine first to load it.

While offline, your edits stay on this device and Save can try the Machine
again. The status line offers the existing reachability retry. When the Machine
returns, choose **Save**; reconnecting alone does not save your draft. If the
disk file changed meanwhile, the same conflict choices appear. Creating,
renaming or deleting a file still needs the Machine.

#### Large files, encodings and line endings

There is no separate editing-size cap in the 0.3 editor. The entire valid UTF-8
file must be loaded before it can become an editable buffer. A partial preview,
binary file or text that cannot be decoded losslessly stays unsaveable through
the text editor. Existing read and transfer limits still apply; use download
when the file cannot be loaded completely.

Large saves use file transfer with the same version check as smaller saves.
UTF-8 byte-order marks are preserved. Files using LF or CRLF keep that style;
mixed line endings are saved using the file’s dominant style, with a note before
you save.

#### Markdown, phone editing and change markers

Markdown uses **Raw** and **Rich** modes on the same draft. Switching flushes
the current editor first. Raw mode includes Find; if rich editing is unavailable
for the document, use Raw without losing the text.

In 0.3 development, enable experimental features under **Settings → Features**,
then enable **Rich markdown editor**. While editing a Markdown file, the
**Raw text / Rich (WYSIWYG)** menu is at the editor's upper right. It is not the
reading header's **Preview / Source** control. Without that optional feature,
the editor stays in Raw and does not show the mode menu.

On a phone, the editing accessory bar provides indentation, punctuation,
cursor movement, Undo/Redo, Find and a pinned Save control. **Done** dismisses
the software keyboard. On a phone-sized web viewport, the accessory bar appears
at the page’s lower edge.

The change gutter marks added, modified and deleted text from the selected
Changes scope. Open a marker to inspect removed lines and use the available
review actions. Next/previous change navigation moves between markers while
you edit. Discarding a marked change in a dirty buffer changes the draft, which
you can undo before saving; if you edited that same region, Happier refuses a
revert that no longer matches rather than guessing where it belongs.

### Review, Ask and Track (0.3 development)

<Callout type="info">
  These controls are under integration in unreleased 0.3 source. Their live
  desktop and phone journeys are still being validated.
</Callout>

The File page Changes model uses **This turn**, **This session** and
**Uncommitted** scopes. A file opened from a Session defaults to that Session;
a turn-card link keeps its turn, and a Project file defaults to Uncommitted.
Switching scope changes the comparison you read, not repository state.

**Keep** records that you reviewed a change. It does not stage or rewrite a
file, and an offline Machine does not block it. Marks follow unchanged content
through unrelated edits and line shifts. **Discard** reverts the selected
change only while the file still matches; a changed file is refused for another
review. Its Undo notice stays until dismissed or replaced by the next review
action. Review keys move by change with J/K and by file with Shift+J/K;
the editor keeps its own Undo while you type.

**Ask** prepares context in an editable composer draft; it does not send the
message. File and diff selections use saved-line anchors with a selected-text
snapshot. Terminal and transcript selections use an editable fenced quote.
See [Review comments](/code/review-comments) for how those anchors travel with
your message.

Without a Session, the Account's **Ask without a session** preference chooses an
editable side-run draft or a new-session draft. The side run uses the file's
Machine and folder, with no parent Session. **Ask in a side run** also offers
that separate draft when a Session is open. The selected quote is preserved;
unrelated browser attachments from the parent Session are not inherited.

**Track** is off by default on each device. Its controller follows the current
Session's file writes in a preview tab without replacing a dirty editor. Your
scroll, selection, typing or tab activation pauses following immediately;
Resume returns to the agent's current edit region. The region comes from the
agent's tool call, so it shows the edit location rather than individual keystrokes.

### Code navigation and outline

<Callout type="info">
  Language features below are under integration in **unreleased Happier 0.3
  development source**. Their desktop and phone surfaces and composed live
  journey are not yet verified. They are not promised in released stable or
  preview clients.
</Callout>

Language servers run on the Machine holding the workspace, not on the device
where you read it. View and Changes stay on demand: the first explicit hover,
Go to definition, Find references or **Check problems** starts the managed
server. Entering Edit counts as an explicit first use and starts an available
server so editing suggestions can become ready. The last open document closing
stops it. A large project can take time and substantial Machine memory to load;
a loading answer is not an empty result.

TypeScript and JavaScript use the bundled native TypeScript server. It is a
managed dependency, not a program from the workspace, and automatic package
acquisition is disabled. Plugins can declare other language servers on the
Machine. With a capable server, hover supplies signatures and documentation,
F12 opens definitions, and Shift+F12 lists references. Definition targets outside
the workspace remain non-navigable paths rather than widening file-read access.

The editing-intelligence extension also adds code suggestions, snippets and
auto-import edits, parameter help, type-definition lookup and implementation
lookup. Each depends on the selected server's capabilities; syntax highlighting
alone does not provide them. A missing capability leaves the rest of the editor
usable.

Formatting and organizing imports are explicit operations. In Edit, their edits
belong to the draft and its Undo history; they do not save the file. Applying a
reviewed edit set to a saved file checks its content hash and returns Undo data.
If the file changed since preview, refresh the preview before applying it again.

Problems offers **Open files** and **Whole project**. Use **Check the whole
project** in Problems or the File menu to request a project check; choosing its
scope alone does not start one. A project check uses the language server's
workspace diagnostics or its declared project checker, and can be cancelled.
There are no automatic project checks. While checking or loading, no confirmed
problem count is shown. **Ask to fix** prepares context in the existing composer in either scope;
problems in unsaved text require saving successfully before that context is made.
On phones, the integration uses tap-to-name in reading views and caret commands
in Edit; long-press selection and comments remain separate.

For a file without a capable server, Go to definition searches for declarations
with the selected name, preferring
the current file and then nearby files. References lists **Text matches** of
that name across searchable workspace files. These are navigation candidates:
two unrelated symbols can share a name, and a declaration can be missed when
its syntax is not recognized. A partial search does not establish that all
references were found. Connect to the file's Machine to search its saved files.

The **Symbols** search scope asks a capable language server for symbols across
the project. Each new query cancels the previous one, and selecting a result
opens its file at the symbol. Without that capability, or while its Machine is
unavailable, the active file's
approximate outline remains available, including Markdown headings. This
baseline does not resolve types or imports and can omit declarations.

When the language server supports call hierarchy, the References panel and
phone sheet offer a **Calls** tab with **Incoming** and **Outgoing** calls.
Choose a result to open the caller or called function in its file.

#### Language Actions for agents

Agents use the same language features through the
[Action reference](/plugins/api/host-actions). Session-bound tools use the
Session's Machine and workspace unless given an explicit target. Queries read
saved file text, include its content hash and refuse conflicting unsaved editor
changes. A project diagnostics query is explicit too; it is not a background
check after every edit.

For `code.format.apply` and `code.imports.organize`, request a preview first,
then apply its reviewed file edits. Preview is a safe read; apply asks automated
callers for approval by default. A present user's apply needs no extra prompt
unless their Action settings require one. Changing those settings changes the
approval policy, not the file-version check.

#### When language features are unavailable

Keep the workspace Machine online. A missing managed server uses the existing
dependency-install flow; a failed start or crash stays visible until **Restart**
or the last document closes and a new request opens it again. Restart is also
useful after external file changes the Machine's file-change feed cannot see.
Happier does not substitute text search for a server that crashed or failed to
start. Other file reading and editing remain available independently.

### Find in files, diffs and review

<Callout type="info">
  Find and the travelling Search query described here are part of the
  **Happier 0.3 development channel**, not a released stable version.
</Callout>

In a text preview or diff, use its **Find** control or
<kbd>⌘</kbd>+<kbd>F</kbd> (<kbd>Ctrl</kbd>+<kbd>F</kbd> elsewhere).
Find highlights matching text and the current match. Use the previous/next
controls, <kbd>⌘</kbd>+<kbd>G</kbd> and
<kbd>⌘</kbd>+<kbd>Shift</kbd>+<kbd>G</kbd> (Ctrl on other platforms),
or Enter/Shift+Enter while the Find input has focus. Esc closes Find and
returns focus. Case matching and regular expressions are optional.

Review Find searches the change set's diff text, including folded context
and files whose diffs have not loaded yet. Per-file counts help you move
through the review. A current match opens its file and folded region;
**Fold again** restores that temporary expansion without changing your folding
preferences. Binary files and failed diff loads leave coverage partial.
It searches the review's available diff corpus, not every line of every file
in the repository.

On web, a review using Pierre temporarily uses Happier's diff renderer while
Find is open so it can reveal offscreen matches. Closing Find restores the
selected renderer. **Monaco keeps its own Find widget**, including when a
Search hit supplies the query; there is no second Happier Find bar above it.
The native CodeMirror editor uses the live document's search with Happier's
Find controls. Images and binary previews have no text Find control.

An Agent or MCP caller can also control a mounted file, diff or review's Find
through `ui.find` when the app is connected to the addressed machine. It
returns status and counts rather than file text. Monaco accepts Find controls
but reports its counts as engine-owned and unavailable to the Action.
See [Agent Search and Find](/organize/search#let-an-agent-use-search-and-find)
for connection and approval outcomes.

### Find in terminal output

In the same 0.3 development channel, the terminal's **Find** menu item and
shortcut search retained, rendered output when the mounted terminal uses
**xterm**. This includes web xterm and the xterm WebView fallback on native
clients. On phone, Find replaces the terminal key rail while open; Done
returns to the keys and terminal focus.

Native **Ghostty** and **Termux** terminals do not support Find yet, so their
Find menu item is hidden. Support follows the actual mounted terminal, rather
than the operating system alone. Output that has left scrollback is no longer
searchable, and a reached scrollback or match-decoration bound is reported as
limited coverage. A handled Find shortcut does not also send input to the
shell; on Windows/Linux, Ctrl+F in a supported focused terminal opens Find.
You can rebind it under [Keyboard shortcuts](/apps/keyboard-shortcuts).

### File details action bar

File details use one shared action bar for preview, diff, edit, commit selection, and revert actions.

Depending on the file and repository state, it can include:

- a file/diff view dropdown
- a pending/included/combined diff dropdown
- an edit action
- **Select for commit** or **Remove from selection**
- selected-line actions when line-level selection is supported
- a revert action when the file can be reverted safely

On wide layouts, the path and actions share one horizontal row. On narrow layouts, Happier wraps the actions into a compact second row so the path, filename, and important actions stay readable.

<Callout type="info">
  In the current development build (unreleased), **Select entire file for commit**
  selects the whole file immediately. When using Git staging, the corresponding
  action is **Stage file**. Use the separate **Select lines** action for a partial
  selection, then apply the selected-line action. **Cancel** lets you leave line
  selection even before choosing a line. **Reveal in Files** locates the open file
  in the tree; **Open Changes** returns to source control.
</Callout>

## Link project files from the session composer

The session composer includes a **Link file** chip.

Use it when you want to attach workspace context to your next message without manually typing paths.

### What it does

- Opens a popover anchored to the composer
- Reuses the same repository/file browsing model as the file sidebar
- Lets you search and pick project files directly from the current workspace

This is useful for prompts like:

- “Explain why this file changed”
- “Refactor the files I linked”
- “Compare these two files”

You can also use `@`-style file search in the composer where supported. The goal is the same: quickly attach relevant workspace context.

## Open workspace file links from the transcript

When an assistant response includes a markdown link to a file in the current workspace, Happier can turn that link into in-app file navigation instead of sending you to a broken browser URL.

Supported link shapes include:

- workspace-relative links such as `src/index.ts`
- links with line and column suffixes such as `src/index.ts:12` or `src/index.ts:12:4`
- absolute local paths inside the workspace
- `file://` URLs inside the workspace
- loopback-expanded links from the web app, such as `http://localhost:18829/Users/alice/project/src/index.ts:12`
- Windows drive paths such as `C:\Users\Alice\project\src\index.ts`
- Windows `file:///C:/...` links and UNC-style file URLs inside the workspace

Happier only opens links that resolve inside the current workspace. Links outside the workspace, traversal paths, and arbitrary non-loopback `http`/`https` URLs stay external or are ignored for workspace navigation.

On desktop, opening a workspace file link opens the right sidebar/details pane. On phone-sized layouts, it opens the file in the **Tabs** surface with the session header still visible.

### Let an agent open or link a file

In unreleased 0.3 development source, an agent can ask the connected app to open
a file with `workspace.tabs.open`. Pass a `file` target instead of constructing
a navigation URL:

```json
{
  "file": {
    "target": { "kind": "session", "sessionId": "your-session-id" },
    "path": "src/index.ts",
    "anchor": { "kind": "fileLine", "startLine": 12 },
    "view": "view"
  },
  "mode": "preview"
}
```

The path is relative to the workspace. A project target names the project
workspace and Home instead of a session. The app must be connected to answer
this client-side Action, and normal workspace access still applies.
`workspace.files.link.get` takes the same file target directly, without the
outer `file` field, and returns its canonical link without opening a tab.
Both Actions have no approval prompt by default;
**Settings → Actions** can require one.

## Limits and safety

- Missing parent directories are created automatically where the operation supports it.
- File preview is size-bounded, and folder zip and download flows are size-limited and checked by the daemon.
- Folder upload is web-only.
