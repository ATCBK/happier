Work does not arrive in one place. Pull requests sit on a forge, issues sit on
another tab, and the errors that turn into issues sit in an observability tool
none of the others know about. **PRs & Issues** gathers them into a single
reviewable list, and lets you turn any entry into a session.

<Callout type="info">
  This guide describes the **Happier 0.3 development implementation**. It is
  not a statement of availability in an earlier stable release.
</Callout>

To load entries and use source actions, you need a reachable machine running
the Happier daemon, the relevant source plugin, and a configured source instance
with a usable credential.

## Where entries come from

Sources are contributed by plugins rather than built in, through a contribution
point the PRs & Issues plugin declares. The development implementation includes:

| Source | What it brings |
| --- | --- |
| GitHub | Pull requests and issues; opt-in Dependabot and code-scanning findings in 0.3 development source |
| GitLab | Merge requests and issues |
| Bitbucket | Pull requests |
| Azure DevOps | Pull requests |
| Sentry | Error issues, with their own detail body |
| PostHog | Error issues, with their own detail body |

Each source is configured as an *instance* — a credential choice, a service base, and
what to watch. Self-managed GitLab and Azure DevOps Server keep that configured
base explicit, including any path prefix, rather than silently treating another
deployment as the same source.

Because sources are a contribution point, a plugin you write can add one. See
[SCM plugins](/plugins/guides/scm).

## Use a machine's GitHub CLI login

In 0.3 development, GitHub source settings offer **Use this machine's GitHub CLI
login** when the selected machine is authenticated with `gh`. Select that choice
and configure the repositories or search you want to watch. An Agent configuring
the source through its administration Action can use the same native choice.

Authentication belongs to the machine running the source operation, not the
phone or browser viewing it. If that login becomes unavailable, sign in with
`gh auth login` on that machine and retry. An explicitly selected Happier
Connected Account takes precedence; a broken account selection does not silently
switch to the CLI login.

Only the native service choice syncs with the source configuration. Happier
obtains the token when needed on the executing machine and does not save or sync
that token as a Connected Account. Switching execution to another machine
requires a usable GitHub CLI login there too.

## What an entry is

Every entry declares one of four source-neutral subjects, and the subject is
what decides which actions apply:

- **Pull request**
- **Issue**
- **Error issue** — a finding such as an error group or security alert
- **Other** — anything a source declares that is none of the above

<Callout>
  Preparing a review workspace is admitted for **pull requests only**. An issue
  or an error group can start a session, but it has no branch to check out, so
  there is nothing to prepare a worktree from.
</Callout>

## GitHub security findings in development

The 0.3 development source adds Dependabot and code-scanning findings to the
existing GitHub connection. Their page composition and live-provider journey
are under integration; this is not a stable-release availability claim.

Each family is opt-in and uses the connection's existing repository selection.
Existing connections leave both disabled. Choosing All may require walking your
accessible repository inventory; selected repositories avoid that work. Findings
retain their native open, fixed or dismissed state, including history. Medium
and low severity findings remain visible. They are excluded from Tasks
completion because only GitHub can establish that a security finding is fixed.

Alert access and repository code access are separate permissions. GitHub's
[Dependabot endpoints](https://docs.github.com/en/rest/dependabot/alerts) use
the Dependabot alerts repository permission, while its
[code-scanning endpoints](https://docs.github.com/en/rest/code-scanning/code-scanning)
use Code scanning alerts. Read operations need read access; dismissing or
reopening needs write access and permission for the actual user. Classic and
OAuth credentials follow each endpoint's documented scopes. A denied family
does not make readable findings from another family disappear.

A scanning location identifies a file at its recorded commit. Reading its code
also needs the appropriate
[Contents access](https://docs.github.com/en/rest/repos/contents). If code is
unavailable, the path, line range and commit remain useful evidence. A missing
Dependabot patched version means no patch was supplied. The associated fix-PR
read opens the existing update PR; it does not request a new update. When no PR
is reported, use the alert's GitHub page to inspect the available update options.

Dismissal hides a finding rather than fixing it. Reopening is a separate native
transition, and an unknown result needs a confirming read before another write.
Agents use the same Actions with approval by default. Fix uses the existing
configured Agent, Session choice and compose/send policy; advisory and code
text enter as source evidence, not instructions that can change those choices.

## What you can do with one

- **Pin it.** Pins are yours and sync with your account, so the entry you pinned on your laptop is pinned on your phone.
- **Link it to a session.** The link is a durable relation, not a copied URL. Linked sessions are paged, so older relationships remain reachable, and a session opened from an entry stays associated with it.
- **Attach it to a message.** The composer has a **PRs & Issues** attachment, so you can hand an agent the entry itself rather than pasting a link and hoping it fetches the right thing.
- **Save a view.** Use **Views** in the PRs & Issues list to save or select a query, filters, ordering and Smart preferences. Temporary changes mark the view as modified; they do not overwrite it until you choose **Update**. The same control lets you rename or delete a view.

Your configured sources, pins, Session links, saved views, and action
configuration sync with your account. Provider entries are not copied into a
Happier database; they are read from their source when the list is refreshed.

If the daemon becomes unreachable, an already-open list can retain its last
window, marked stale, but source actions require reconnection. Your account's
saved state remains available while the Happier server is reachable. Opening
the page cold while offline does not restore a cached provider list, and
another device does not inherit the first device's loaded window.

## Give an entry to an Agent

Attach one or more entries in the Composer, or start a Session from an entry's
configured action. Happier resolves the current source context when the message
is sent and keeps a structured attachment presentation in the transcript, so
the Agent receives the selected work and the conversation keeps showing what
you attached.

## Pull-request explanations in development

The configured Actions catalog keeps your custom rows and order and adds missing
built-in actions. A stored empty list therefore does not turn built-ins off.
Turn a built-in off explicitly to keep it unavailable; removing a custom action
deletes that row. In the Actions editor's **Restore defaults** section, choose
**Restore** to remove the override and show the current built-ins. If the catalog
cannot be read, retry that read before starting an action.

The GitHub and GitLab sources' unreleased comparison retrieval keeps paged file evidence,
captured base/head and explicit missing-patch or stale states. The PR detail
preview alone is not a complete comparison. **Walk through** routes through
Triage's Session admission to the shared Session comparison surface, preserving
the pull request's source locator. Admission resolves the machine and workspace;
linking a Session does not select a checkout automatically. This routing is
implemented in development; the composed live journey remains under validation.

**Request review** asks people for review; it is distinct from starting an Agent
review. A walkthrough is an explanation, not a clean-review verdict or consent
to commit. PR comparisons cannot apply commit proposals in the current checkout.
See [Diffs and review](/code/diffs#walk-through-changes) and
[pull-request evidence](/code/pull-requests#comparison-evidence-in-development).
