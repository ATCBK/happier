Save instructions once, then insert them into the composer or use them as system prompt additions. Prompts, slash templates and ordered context additions share your library.

For portable `SKILL.md` bundles, use the separate [Skills library](/extending/skills). [Registry sources](/extending/registries) supply skills and other installable content.

<Callout type="info">
  The composer prompt picker, favourites, **Sent before**, **Save as prompt**
  and individual message-action switches below describe the **Happier 0.3
  development channel**. They are not yet part of a released stable version.
</Callout>

## The library

Open **Settings → Prompts** to manage your reusable content.

The Prompts collection holds reusable Markdown documents. Each prompt can have a title, folder and tags.

### Prompts

Prompts are best for:

- reusable instructions you want to insert into the composer
- reusable system prompt additions
- profile-specific or agent-specific guidance
- personal prompt snippets that should sync across devices

Each prompt can have:

- a title
- markdown content
- an optional folder
- optional tags

In the 0.3 development channel, a prompt can also be a favourite. Favouriting
keeps the same document, folder, tags and markdown; it adds that prompt to
the picker's **Favourites** group.

### Insert a prompt from the composer

Open **Prompts** using the library icon at the composer's top-right, to the
left of dictation when dictation is available. The icon also works with voice
off, in Session, new-session and Home composers. You can also type `/` and
choose the last **Prompts…** row.

With a hardware keyboard and composer focus, <kbd>Ctrl</kbd>+<kbd>R</kbd>
opens the picker on macOS web and supported desktop/native clients. It is
literal Control, not Command. Windows/Linux browsers keep Ctrl+R for reload;
use the icon or `/` → **Prompts…** there. You can change bindings under
[Keyboard shortcuts](/apps/keyboard-shortcuts).

The picker groups **Favourites**, **Library** and **Sent before**. Library
shows each prompt once, with its slash shortcuts alongside it. Choose a row
to insert it at the current selection, or replace the `/` token that opened
the picker. Enter inserts; <kbd>⌘</kbd>+<kbd>Enter</kbd>
(<kbd>Ctrl</kbd>+<kbd>Enter</kbd> elsewhere) inserts and sends when the
composer can send. When a prompt has an empty `$ARGUMENTS` placeholder,
insertion selects its first argument position so you can fill it in.
Use the favourite control on a library prompt to keep it close at hand.

**Sent before** searches decrypted user messages from known sessions in the
current account on the device. Search older history on demand, with progress
and **Stop**. Loaded results are not the complete account history: global
coverage stays partial because archived/shared inventory completeness cannot
be established. To keep a **Sent before** entry, use its favourite control to
name and save it in place as a library prompt. Your Up-arrow history navigation
is unchanged. Session-only
shortcuts are available in an addressed session, but not in new-session or
Home composers.

Hide the library icon under **Settings → Composer** if you prefer the other
entry points.

### Save a sent message as a prompt

Choose **Save as prompt** under a sent user message with readable text.
On phone, long-press the message and choose the same action. Name the prompt;
the favourite option starts on. Expand the optional slash-shortcut field to
give it a token such as `/review`. **Save** creates a library prompt with the
message's text, and the optional shortcut inserts that prompt. **Cancel**
stores nothing. Attachment-only or unsupported structured messages have no
Save as prompt action. If the prompt saves but its shortcut cannot be added,
Happier tells you; the saved prompt remains in the library.

### Choose which message actions appear

In **Settings → Transcript → Message actions**, switch individual committed
message actions on or off: **Copy**, **Fork**, **Rollback**, **Select**, **Pin**,
**Save as prompt**, **Make this repeatable**, and **Plugin actions**. Each switch
controls eligible actions; turning one on does not make it available for an
ineligible message. A switched-off action is absent from both the row and its
menus. When Workflows are available, **Make this repeatable** adds a draft
request to turn an eligible assistant message into a reusable workflow; you
choose when to send it. Pending-message recovery controls remain available. If you
switch Pin off, existing pin indicators still let you unpin those messages.

### Actions for prompts

The [generated Actions catalog](/plugins/api/host-actions) owns exact inputs,
outputs and supported surfaces. In this development channel,
`prompt_doc.create` creates a prompt, `prompt_doc.favorite.set` changes its
favourite state, and `prompts.library.list` reads library metadata through the
shared library operations. `prompt_doc.get` reads content; invocation list
and resolve Actions use the same shortcut availability rules as the composer.
Creation through an Agent follows the Action's approval policy.

In this development contract, `prompt_doc.get` also returns the document's current
revision. A reviewed `prompt_doc.update` can include that revision as
`expectedRevision`: if another edit changed the document after review, the update
conflicts rather than applying the reviewed change to a new version. Read the
current document and review the change again. The write also checks for competing
changes during execution. Omitting the reviewed revision preserves that write-time
check, but cannot protect an earlier preview.

Prompt edits use ordinary Actions approval. Automation defaults to **Ask first**;
an explicit **Allowed** setting applies to the exact Action and surface across
every Session using it. It is not a separate Bot permission. A required approval
is a human decision, and approval alone does not mean the content has saved.
See [Inbox and approvals](/sessions/inbox-and-approvals).

`ui.prompts.picker.open` opens an eligible mounted composer's picker; it does
not read prompt text or create a prompt. It is a client display Action and is
available to Agents through the connected app; it remains excluded from MCP.
`ui.find` and `session.pending.next` are available to Agents and MCP for
mounted-client Find and pending-request navigation. These Actions are delivered
to an app connected to the addressed machine and run through its usual Action
executor. The picker does not select, insert or send a prompt on the Agent's
behalf.

Without a connected app, the picker and Find return **unavailable** with reason
`noClient`; Next returns **unavailable**. With an app connected but no eligible
composer, the picker returns `noEligibleComposer`; Find similarly distinguishes
`noMountedSurface` from zero matches. Approval-required Actions wait for the
required decision before delivery; rejection or cancellation prevents
execution. A connection lost after dispatch can leave the outcome uncertain.
See [Agent Search and Find](/organize/search#let-an-agent-use-search-and-find)
for the related search Actions.

## Folders and tags

Use **Folders** when you want lightweight organization without duplicating prompts.

In 0.3 development, Prompt Library filters the same personal folder tree as
[Artifacts](/organize/artifacts#organize-with-folders). **Move to folder** and
dragging change the prompt's placement in both views, without changing its text
or sharing.

Recommended patterns:

- one folder per team or workstream
- one folder per provider or backend setup
- one folder for templates vs another for system additions

Tags are lighter-weight than folders and work well for:

- `coding`
- `voice`
- `review`
- `research`
- `profile`

## Templates (slash commands inside Happier)

Templates are Happier-native slash shortcuts built from saved prompts.

Open **Settings → Prompts → Templates** to create them.

Each template maps:

- a **slash token** such as `/review` or `/ship-check`
- to a **target prompt** from your library
- with a behavior:
  - **Insert**
  - **Insert and send**

Use templates when you want a fast reusable composer shortcut without turning the prompt into a system rule.

### Template behavior

When you type a saved token in the composer:

- Happier resolves the linked prompt
- inserts the prompt content into the composer
- optionally sends immediately if the template is configured that way

Happier blocks collisions with built-in action commands, so a template token cannot silently override a core slash action.

### Native composer suggestions (development source)

This workflow is **development-only and unreleased**. Before creating a session, typing `/` or `$` can discover native commands or skills from the selected agent on the selected machine. Discovery uses the project folder, profile, and selected authentication context, so changing those selections can change the suggestions.

Discovery starts when you open the relevant suggestions. Local commands remain available while native results load. Selecting a native skill preserves any agent-supplied identifier and its source reference for submission; skills without a native identifier resolve using their name and source path. Selection does not import the skill into your Happier library.

Managed prerequisites must already be ready on the selected machine. Discovering suggestions does not install or update them; session launch keeps its configured installation policy.

Native support depends on the agent's transport: a slash command does not automatically become a typed skill. Older daemons that lack this discovery method show no native pre-session rows and keep local suggestions available. OpenCode V2 pre-session discovery is currently unavailable; native commands and skills in an existing OpenCode V2 session use a separate runtime path.

## System prompt additions

This is the user-facing name for what the implementation internally stores as ordered prompt stacks.

Open:

- **Settings → Prompts → Context**

You can attach prompts to:

- the **Coding agent**
- the **Voice agent**
- any saved **Profile**

### How it works

System prompt additions are:

- ordered
- individually enabled or disabled
- reusable across multiple surfaces

Happier resolves them into the session’s append/system prompt in a shared way across UI and CLI.

That means:

- starting a session from the app and from the CLI uses the same prompt-building logic
- profile-linked additions and surface-linked additions compose consistently

### Context preparation (0.3 development)

The development context resolver composes Account, the Session's own Profile,
Source/Project and Session additions in that order. Coding preparation places
them before the Session's Role and Notes. A Source-backed Project uses its
Source's context attachments as the Project layer; a Project without a Source
uses the Session owner's personal Project additions. The CLI
coding and Voice adapters and the app's stack reader share this resolver. Worker
Sessions use their own selected Profile and Project context, without copying the
Lead's Session additions or switches for inherited entries. Explicit worker
Profile selections are saved with the new Session.

These are unreleased development contracts. The visual Project Context and Session
Work editors are being integrated; this section does not describe a released
editor workflow or completed runtime validation.

In these development Context surfaces, the memory section's **+** can save the
first fact for an Account or writable Project without an existing memory document.
If attaching the new document conflicts, the fact remains saved and the surface
keeps that exact document visible with a conflict notice; it does not retry by
creating another fact.

Each preparation reads the current library documents from their addressed Home
and Account. An older reference without a Home qualifier still uses its owner's
Home. A saved reference does not grant access, and a cached display copy cannot
replace the current document. In 0.3 development, legacy skill attachments migrate once into equivalent Where-it's-on rules, Profile seeds or Session selections. Their retained records no longer paste `SKILL.md` into context. Removing a migrated rule or seed does not recreate it on the next load; voice skill attachments stop contributing, while their library items remain. See [Skills](/extending/skills#existing-library-and-profile-seeds).

Changes apply at the next supported coding preparation or bound Voice preparation.
An already-prepared turn or Voice attempt keeps its installed instructions; this
does not promise a mid-turn update or support for every Voice carrier. Sharing a
Session or belonging to its Source does not share its owner's documents. A
separate document grant permits the content that grant covers; without it, the
document remains owner-private.

When a Session preparation supplies memory-off, memory documents are identified
from their headers and skipped before their bodies load; ordinary instructions remain usable. Switching off an inherited entry affects that Session
only. An empty document is valid. A definitively missing optional entry is skipped;
a missing required entry prevents preparation until it is repaired or detached.
Wrong-kind, unreadable or malformed content also prevents preparation. Temporary
read failures remain pending instead of silently supplying empty or stale
instructions. Session Instructions uses one enabled, required Session entry;
detaching it leaves its document in the library. Its Work editor is still being
integrated.

In the current development behavior, each nonempty memory block names its
document, context layer and saved reference. The always-loaded part contains the
memory index: active, unexpired key facts and topic titles with one-line summaries.
Facts render on single lines with an `id:` key and available source/date information.
Topic detail and archive facts are not included in that prompt block.

An optional `maxChars` budget selects complete index entries; it does not cut facts
mid-line or budget the source label. Without a budget, the complete eligible index
loads. Existing flat facts/archive documents and index-only documents remain
readable through the same memory adapter. Index and topics remain inside one
document, with its existing sharing permissions—not separate topic documents.

Account memory preferences apply when creating a Session: ordinary Sessions
default off and Bots default on, unless creation supplies an explicit choice.
The Settings Action anchors are `prompts.memoryUseInNewSessions` and
`prompts.memoryUseInNewBots`. Changing a default does not change existing Sessions'
memory choices.

Development context writes use the metadata revision the caller reviewed. If that
revision is stale, the write refuses instead of silently applying the change to
a newer Session. The CLI retains its queued intent and reviewed revision for
explicit review after a conflict. This is not a claim that the deferred visual
Work editor already provides draft recovery.

### Memory pages and topics in 0.3 development

Open a Memory document from [Artifacts](/organize/artifacts), or choose
**Show all** from its context section, to read its key facts and topic list.
Choose a topic to open its facts on demand. Topics and the archive stay inside
the same document and use its existing access permissions.

Select a fact to read its detail beside the list on a wide screen or on its own
page on a phone. Decisions include their reason and source; ordinary facts can
also link to a source Session. Opening a source still requires access to it.
The archive contains forgotten, superseded and expired facts; those facts remain
searchable but do not enter the always-loaded prompt index. Viewing memory does
not change which entries a Session uses.

The development Memory search surface searches remembered facts across topics
and the archive alongside past Sessions. A fact result opens its document at
the matching topic and fact; a Session result opens the conversation at the
match. See [memory search](/organize/local-memory-search#search-memory-documents-in-development)
for Machine selection and coverage limits.

### Saving memory and decisions in 0.3 development

The development Actions save facts in the existing Memory document. When
`memory.remember`, `memory.decision.save` or an edit finds a possible duplicate,
it asks for a choice against the revision you reviewed:

- **Update** corrects the selected saved fact.
- **Replace** makes the incoming fact supersede the selected fact.
- **Keep both** keeps the saved fact active and adds the incoming one.

Update and Replace keep the previous text in the archive. A stale choice refuses
instead of applying to newer content. For an edit that matches another saved
fact, Update corrects that candidate in its existing topic and archives both
prior versions; Replace uses the incoming edit's destination.

`memory.decision.save` also records a reason and an exact source message from a
Session or Discussion. The record identifies who approved it when the host
witnessed a person saving or approving that exact request; otherwise it means
**not approved by a person**. An Agent or an approval waiver cannot invent an
approver. Changed wording clears an earlier approval unless a new person save
or approval is witnessed; renewing only the expiry keeps the existing approval.

Expiry is **Never** or a date. Expired facts stop entering prepared prompts but
remain stored and searchable. Reason and source detail are read on demand. A
source link grants no access, and saving refuses when the source is unavailable
or the Memory document's audience may not receive it. A Project attachment alone
does not make a Memory document shared; its document grants decide who can read it.

The Project Memory page and decision-saving presentation are still being
integrated. These contracts do not promise a finished screen workflow. For
Project scope and older-machine behavior, see
[Local memory search](/organize/local-memory-search#availability-in-03-development).

### Recommended usage

Use coding additions for:

- code-review rules
- repo-specific style constraints
- output format expectations

Use voice additions for:

- shorter conversational style
- speech-friendly formatting
- dictation or accessibility preferences

Use profile additions for:

- environment- or endpoint-specific rules
- reusable “work profile” or “research profile” instructions

## Common workflows

### Build a reusable coding instruction

1. Create a **Prompt**
2. Put it in a folder if useful
3. Add it to **Coding agent system prompt additions**
4. Optionally attach it to a specific **Profile**

### Create a reusable slash shortcut

1. Create a **Prompt**
2. Open **Templates**
3. Map a token like `/review` to that prompt
4. Use **Insert** or **Insert and send**
