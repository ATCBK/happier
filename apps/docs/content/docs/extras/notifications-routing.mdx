Happier notifications are session-aware and multi-server-aware.

When you interact with a notification, Happier tries to land you in the exact place that needs attention:

- the targeted **session**
- on the correct **server profile**
- with the safest possible behavior for **permission actions**

This avoids landing on the wrong server or silently approving a request on an unexpected server.

## Typical notifications

- turn completion / "it's ready"
- permission actions
- action requests
- share/collaboration events

## Closed-app session alerts

Alerts sent by a Home for a session you follow name that Home by its own server identity rather than by whichever server profile is currently active. Happier resolves it against your saved profiles:

- if exactly one saved profile matches, the tap opens that session on that Home, switching profiles first when needed
- if no saved profile matches — or the identity is ambiguous — the tap does nothing rather than opening the wrong Home's session

When the app is already open, one committed event produces one visible alert on the device: if Happier's own local notification already showed it, the Home alert does not repeat it, and vice versa. This is best effort duplicate suppression on that device, not a delivery receipt or a guarantee that every alert arrives.

<Callout type="warn">
  **Known limitation: closed-app collaborator alerts are best effort on iOS.**
  When somebody mentions you, assigns you a session, or posts to a session you
  follow and Happier is closed, the Home sends a push carrying a generic body and
  asks the device to fill in the real text locally. On iOS the system decides
  whether and when to run that enrichment, so a collaborator alert can arrive with
  the generic wording, arrive late, or not arrive at all. Nothing is lost: the
  activity is in the session and on your attention surfaces when you next open
  Happier. Do not rely on a closed-app alert as the only signal for something time
  critical. On Android, Happier cannot be woken once it is fully
  closed, so activity it could not alert you about is waiting for you the next
  time you open it.
</Callout>

## What happens when you tap a notification

If the notification contains a session route, Happier opens that session.

If the notification belongs to a different saved server than the one currently active:

- Happier switches to that saved server first
- then it opens the session

This is the default behavior for normal notification taps and for the `Answer` action used by action-request notifications.

## What happens when you press a notification action

The mobile background permission actions below are an unreleased development capability. iOS requires an equipped native build; end-to-end notification-action lifecycle and physical-device validation are still pending.

On the mobile app, current interactive notification actions are:

- **Permission requests**: `Allow`, `Deny`
- **User-action requests**: `Answer`

Their behavior is intentionally different:

- On Android and equipped iOS builds, live `Allow` and `Deny` responses use the exact saved Home, Account, session and request turn without changing the selected Home or navigating away from your current screen. Successful background registration lets them respond without opening Happier. On iOS, the buttons require device authentication.
- If native support is missing or background registration is unavailable, the permission buttons open Happier. A live response uses the same exact-target handler without switching Homes or navigating. A later delivery or execution failure can leave the app closed.
- An unhandled saved launch response opens the session for review without sending a decision. The same response does not open the session again while Happier remains running.
- `Answer` opens the app directly on the session so you can answer in context

User-action requests include cases such as:

- **AskUserQuestion**
- **Exit Plan Mode**

Happier does **not** currently try to send freeform or multiple-choice answers directly from the notification itself. The action button is a fast path back into the correct session.

## Desktop Guard warnings (development)

The development Tauri client has a native transport for **Keep running** and
**Stop now** on an idle-stop warning. Native builds and desktop validation are
pending; this is not a claim of released availability. Both buttons use the
same Guard Actions and approval preferences as the app. A replaced or cancelled
warning cannot act on a later warning, and a reachable current Guard observation
withdraws the resolved warning.

Linux needs a desktop notification service with action support. macOS needs a
real app bundle and notification permission; an unbundled development binary
cannot use its Terminal identity for these actions. Windows needs an installed
app with its notification identity registered. Keep Happier running, including
in the background, to receive actions and withdraw warnings. Fully quitting it
ends those process-owned callbacks; cold-start actions and Windows Action Center
delivery remain unverified. Open the session to inspect its current countdown
and use its in-app control.

## Server-aware safety rules

These navigation rules apply to ordinary taps and `Answer`. An unhandled saved permission response follows the same navigation rules for review, without sending a decision. Live mobile permission actions use the separate rules below.

### 1) Server is already active

If the notification targets the server that is already active, Happier opens the session.

### 2) Server is saved, but not active

If the notification targets a saved server profile that is not currently active and can be switched to safely:

- Happier switches to that saved server
- opens the session

### 3) Server is not saved, and the device has no saved servers yet

If this is effectively the first server on the device:

- Happier may auto-add and switch to that server so the notification deep link still works
- Happier opens the session
- for security, Happier still does **not** auto-send `Allow` / `Deny` on an unsaved server

This is mainly a bootstrap convenience for first-run or self-hosted setups.

### 4) Server is not saved, and the device already has saved servers

If the app already knows about other servers, Happier does **not** auto-add the incoming one.

Instead it:

- stores the pending destination
- opens **Server settings**
- prefills the incoming server URL
- shows a hint that this server is not saved yet

After you choose **Add & Use**, Happier continues to the original session automatically.

## Why this flow is strict

Notification actions are convenient, but permission responses are security-sensitive.

Ordinary taps and saved launch responses provide navigation for review. They cannot authorize an approval or denial. A live permission action must verify the exact saved Home and Account before sending a decision, using the rules below.

## Mobile permission action safety and recovery

A live mobile action requires a saved Home and saved sign-in details for an account that can access the session. It can respond on an inactive saved Home without selecting that Home. An unknown or ambiguous Home or a notification naming a different account requires in-app review. Happier does not queue an approval for a later sign-in. A live or background response to an older notification without the request's turn sends no decision and leaves a review notice for when Happier is active, without opening the session.

The CLI checks that the request is still the one shown in the notification. An alert from an earlier turn cannot answer a newer request. Only an accepted response is confirmed; rejection or an uncertain result is not reported as approval success.

If a response is rejected or cannot be confirmed, Happier saves a generic recovery notice for when the app is active. It does not open the app from the background or automatically resend the decision. Open the relevant Home and session to inspect the current request before responding again. A saved cold-start response is navigation intent for review, never fresh authority to approve or deny. Only the generic notice is persisted; it contains no permission decision or session content.

Background action delivery depends on the installed native build and OS lifecycle rules, including Android battery restrictions and force-stop state. iOS can expire background execution before a response is confirmed; Happier records a review notice rather than replaying the decision. Saved iOS credentials retain their existing access restriction while the device is locked. End-to-end notification-action lifecycle and physical-device validation are not yet complete. Ordinary notification taps and `Answer` keep their existing foreground paths.

## Prerequisites

- App has registered push token(s) to your selected server.
- CLI/daemon and app are using the same server profile.
- For multi-server setups, each server profile is configured correctly.

## Troubleshooting

If notification taps open the wrong context:

1. Verify active server profile in app.
2. Re-run `happier auth login` on the correct server profile in CLI.
3. Confirm push token registration for that server profile.
4. If the notification came from a server that is not saved yet, add it from the prefilled **Server settings** screen first.
