Happier notifications are session-aware and multi-server-aware.

When you interact with a notification, Happier tries to land you in the exact place that needs attention:

- the targeted **session**
- on the correct **server profile**
- with the safest possible behavior for **permission actions**

This avoids landing on the wrong server or silently approving a request on an unexpected server.

## Typical notifications

- turn completion / "it's ready"
- permission actions
- action requests
- share/collaboration events

## What happens when you tap a notification

If the notification contains a session route, Happier opens that session.

If the notification belongs to a different saved server than the one currently active:

- Happier switches to that saved server first
- then it opens the session

This is the default behavior for normal notification taps and for the `Answer` action used by action-request notifications.

## What happens when you press a notification action

The Android background-action behavior below is an unreleased development candidate, not a verified stable-release capability.

On the mobile app, current interactive notification actions are:

- **Permission requests**: `Allow`, `Deny`
- **User-action requests**: `Answer`

Their behavior is intentionally different:

- On Android builds with background notification actions available, `Allow` and `Deny` send the permission response without opening Happier or switching the selected server. A successful response does not navigate away from your current screen.
- If Android background registration is unavailable, fails, or times out, the buttons retain foreground behavior. The same guarded executor handles live responses in the app without navigating; a terminated-state press that arrives only as a saved launch response is not executed and instead navigates to the session for review.
- On iOS, `Allow` and `Deny` retain their foreground behavior: open the app, send the permission response when safe, and open the session.
- `Answer` opens the app directly on the session so you can answer in context

User-action requests include cases such as:

- **AskUserQuestion**
- **Exit Plan Mode**

Happier does **not** currently try to send freeform or multiple-choice answers directly from the notification itself. The action button is a fast path back into the correct session.

## Server-aware safety rules

The navigation rules below apply to ordinary taps, `Answer`, and iOS permission actions. Android `Allow` / `Deny` use the separate rules in the next section.

### 1) Server is already active

If the notification targets the server that is already active:

- Happier performs the action immediately (for example `Allow` / `Deny`)
- then opens the session

### 2) Server is saved, but not active

If the notification targets a saved server profile that is not currently active:

- Happier switches to that saved server
- performs the action if applicable
- opens the session

### 3) Server is not saved, and the device has no saved servers yet

If this is effectively the first server on the device:

- Happier may auto-add and switch to that server so the notification deep link still works
- Happier opens the session
- for security, Happier still does **not** auto-send `Allow` / `Deny` on an unsaved server

This is mainly a bootstrap convenience for first-run or self-hosted setups.

### 4) Server is not saved, and the device already has saved servers

If the app already knows about other servers, Happier does **not** auto-add the incoming one.

Instead it:

- stores the pending destination
- opens **Server settings**
- prefills the incoming server URL
- shows a hint that this server is not saved yet

After you choose **Add & Use**, Happier continues to the original session automatically.

## Why this flow is strict

Notification actions are convenient, but permission responses are security-sensitive.

For the foreground navigation flow above, Happier only auto-sends a permission response when the targeted server is:

- already active, or
- already saved locally and can be switched to explicitly

If the server is unknown, Happier falls back to navigation and review instead of silently performing the approval.

## Android permission action safety and recovery

Android permission actions require a saved server with matching URL, saved credentials, and a non-empty session and request ID. They use the saved profile's canonical server identity and authenticated account scope, including when that server is inactive. They never add an unknown server, change the selected server, or queue an automatic approval for later sign-in.

The existing account-scoped session RPC resolves session access and encryption without a mounted UI. An account hint, when present in the notification, must match the saved credentials. Older payloads do not include that hint: for those, authenticated session access and the CLI's live request validation remain the authority. Expired or missing requests must be reviewed in the session; the app does not infer success from transport delivery alone.

Notification permission actions use a one-shot authenticated connection even while normal app networking is paused in the background. The connection closes after the action or when its execution deadline expires, even if native encryption has stalled; it does not resume background sync or change the active server. A late connection cannot send an expired action. The session lookup retains the same authenticated-origin checks and encryption handling as other account-scoped requests.

The foreground listener and background task share one request coordinator. Its device-local journal is keyed by server, account, session, and request, not notification ID. Concurrent identical decisions share work; a conflicting decision cannot overwrite it. The journal records issuance before the RPC emits. Only an explicit application acknowledgement of success is confirmed. Rejection, timeout, or an older acknowledgement without a result is not reported as approval success.

Issued decisions are never automatically retried, including after restart or a lost acknowledgement. A saved cold-start notification response is an observation, not fresh permission to send again. A decision that is known to have never been sent (for example, the device was offline) can be retried — or changed — by pressing a notification button again; only an ambiguous issuance requires in-app review. This is conservative replay protection, not an exactly-once network guarantee.

If Android opens Happier from a terminated state but only exposes a saved response (with no live listener or background task handling the press), the saved response does not send the approval. Instead, Happier navigates to the relevant session — using the same server-safety rules as an ordinary notification tap — so you can review and answer the current request in the app. This also applies to the foreground fallback when background registration is unavailable.

If an action cannot be confirmed, a generic recovery notice is saved for when Happier is active. The notice does not open the app from the background and does not reveal session content. Open the relevant server/session yourself to check the current request before responding again. The journal stores only scope/request identifiers, decision, state, and timestamp, never tokens or tool arguments. It never evicts a record of an ambiguous (issued but unconfirmed) decision; if the journal holds only ambiguous records at its bounded capacity, or if storage fails, notification actions fail closed and require in-app review.

The journal retains at most 512 request records. At capacity, the oldest settled or never-sent records are reclaimed automatically to admit new requests, so everyday use is not limited over the device's lifetime. Records of ambiguous issuance are never reclaimed; clearing replay-protection storage by hand is not a safe workaround. Use the normal in-app permission controls when an action reports that it needs review.

### Native build and lifecycle limits

Background actions require a new Android build containing `expo-task-manager`; they cannot be delivered as an OTA-only change to an older binary. The native runtime version is bumped for that dependency. Registration is attempted once per runtime with a bounded wait. A late native completion is safe because any delivered response still uses the shared coordinator.

Expo SDK 54 documents Android action-task delivery in background and terminated states. It does not replace the foreground listener. OS force-stop, battery restrictions, and native delivery still need physical-device validation; JavaScript tests cannot prove that another app remains on screen or that the OS starts the task. Normal notification taps, `Answer`, web startup, and iOS foreground behavior are unchanged.

## Prerequisites

- App has registered push token(s) to your selected server.
- CLI/daemon and app are using the same server profile.
- For multi-server setups, each server profile is configured correctly.

## Troubleshooting

If notification taps open the wrong context:

1. Verify active server profile in app.
2. Re-run `happier auth login` on the correct server profile in CLI.
3. Confirm push token registration for that server profile.
4. If the notification came from a server that is not saved yet, add it from the prefilled **Server settings** screen first.
