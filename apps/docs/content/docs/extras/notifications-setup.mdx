Happier uses **Expo Push Notifications** as a delivery mechanism. In the current architecture:

- The **mobile app** registers an **Expo push token** and saves it to the server.
- The **server** stores push tokens per account and, for opted-in closed-app collaboration alerts,
  submits the existing OS-visible `activity_alert` payload through the Home's push transport.
  That payload is generic and contains no Session content or keys; it is distinct from the
  best-effort `session_changed` background wake used for silent reconciliation.
- The **CLI/daemon** still owns the ordinary rich runtime notification path and can fetch the
  authenticated account's saved tokens to submit notifications via Expo's push API (for example:
  *“It’s ready!”* or *Permission Request*).
- On a capable mobile build enrolled for remote alerts, the app rechecks access and recipient
  privacy locally and enriches the safe generic alert when possible; otherwise the already-safe
  generic fallback is shown. A build without the native alert consumer cannot receive this
  closed-app alert path; ordinary daemon/CLI notifications remain independent.

This page is about **push notifications**.

Happier also has separate **in-app attention surfaces** such as the Inbox dot, the Sessions-tab dot, and unread/shared-session organization in the session list. Those are part of the normal in-app UI, not the push-notification system. See [Inbox and approvals](/sessions/inbox-and-approvals) and [Session sharing](/accounts/session-sharing).

For the full cross-surface model, including the desktop overlay, Live Activities, widgets, badges, quiet hours, privacy modes, and sounds, see [Attention surfaces](/organize/attention-surfaces).

## What notifications can do

Happier can notify you when a session needs attention, including:

- **Ready** notifications when a turn finishes and the agent is waiting
- **Permission requests** when a tool/action needs approval
- **User-action requests** when the agent needs a structured human response

On the mobile app, permission and action-request notifications can also expose **action buttons**:

- **Permission requests**: `Allow` / `Deny`
- **User-action requests**: `Answer`

Current behavior is intentionally conservative:

- tapping the notification opens the targeted session
- pressing a notification action button can execute the direct action when the runtime can verify the target server/session and the surface policy allows direct actions
- an action can open the targeted session for review instead of sending a decision
- when an action opens Happier and its server is not saved yet, Happier uses the safest add/switch flow instead of silently approving on the wrong server

**Development builds only:** Android and equipped iOS builds can send `Allow` and `Deny` without opening Happier, changing the selected Home, or leaving your current screen when background action registration succeeds. On iOS, permission buttons require device authentication; saved credentials keep their existing protection while the device is locked. If the native support is missing or registration is unavailable, the buttons open the app. A live response still uses the same exact-target action handler. Background delivery or execution can fail after registration without opening Happier. If a response is unconfirmed, open the session to inspect the current request. End-to-end notification-action lifecycle and physical-device validation are still pending; an OTA update alone cannot add the required iOS native support.

For the exact routing behavior, see [Notification routing](/extras/notifications-routing).

## Richer notification details

**Development builds:** request previews can include the requested command or file path and any supplied explanation. Question previews include the question text, answer options and their descriptions, and whether multiple selections or a custom answer are allowed. Happier formats supported request fields rather than sending raw tool-input JSON. Supported requests can also include a plan for approval, a history-import explanation, or a web URL or search query.

Remote request previews are on by default. Disable **Request previews** in notification settings to omit this content from push notifications. Each webhook destination has its own request-preview switch, and the shared attention privacy policy can also restrict previews. Device-local request previews have a separate preference and follow the local attention policy.

These details may appear on the lock screen or be received by your webhook endpoint. Disable request previews to omit command and question content from the notification and webhook request details. See [Attention surfaces](/organize/attention-surfaces) for the shared privacy controls.

Long push previews are shortened with an ellipsis to fit the outbound payload budget while preserving session and request routing. Open the session for the complete content. Expo also enforces its own [notification payload limits](https://docs.expo.dev/push-notifications/sending-notifications/).

Older senders cannot honor the new preference and continue using their existing detail hints.

Platform details:

- **iOS** can show the tool/request name as a notification subtitle
- **Android** uses dedicated channels for permission requests and action requests so users can tune them separately at the OS level

## Notification preferences

The app also exposes notification preferences so users can tune how noisy Happier should be.

Current settings include:

- **Push notifications** on/off for the account
- per-type toggles for **Ready**, **Permission requests**, and **User-action requests**
- **In-app notifications** behavior while the app is open: `Full`, `Silent`, or `Off`
- bundled **Soft** and **Urgent** notification sounds, native system sounds, or silent mode
- Live Activity remote update preferences when the selected server advertises support

Quiet hours are evaluated by the shared delivery policy for each notification channel and event.
They suppress or make interruptive channels silent when that event's policy says so; they do not
disable every attention surface or override an explicitly independent channel such as a webhook.
The device's OS notification permission, Focus/Do Not Disturb and local device override remain
separate last-mile controls.

When you are already looking at a given session, Happier suppresses notifications for that same session to avoid duplicate noise while you are actively reading it.

### Closed-app session alerts

Sessions you collaborate on can also alert you while the Happier app is closed, without a daemon of your own running. Because your notification settings are end-to-end encrypted, this leg only works when you explicitly turn it on and enroll a device build that includes the native alert consumer:

- **Allow remote session alerts** (per account) publishes a limited, derived copy of your alert policy — event categories, quiet hours and time zone, preview limits, and sound choices — to that Home. Session content, titles, and encryption keys are never shared.
- **Receive on this device** (per device) enrolls this device's push registration. It is stored on the exact registration row this device already uses, and it publishes only the quiet-hours, in-app behavior, preview ceiling, and volume semantics from your device overrides. Local-only switches, badges, widgets, and Live Activity settings stay on this device.
- The device switch appears only on app builds that ship the native alert consumer, and enrollment is only offered by Homes that support it. Older Homes keep ordinary notifications and show remote alerts as unavailable. Physical iOS/Android build and terminated-process behavior remains platform/release dependent.
- The Home applies the remotely published mute and quiet-hours policy **before** sending, and the
  mobile device applies its local privacy and OS-notification policy before display. It can only
  alert you while the stored copy matches your current settings version. Changing settings from a
  client that cannot publish the copy leaves the status as **Policy needs syncing** until a capable
  client republishes it.
- Turning either switch off clears the enrollment at your next reconciliation. Alerts already sent cannot be recalled.

If the enrolled native consumer cannot enrich a permitted alert, it shows the safe generic Happier
copy. Device-specific enrichment and terminated-process behavior remain subject to the installed
iOS/Android build and its platform delivery rules; a build without that native consumer is not
eligible for this closed-app alert path.

## What you need to configure

### 1) Server (any deployment)

Your server must expose the push token routes:

- `POST /v1/push-tokens`
- `GET /v1/push-tokens`
- `DELETE /v1/push-tokens/:token`

If you’re self-hosting the server, see: `Deployment` → `Docker` / `Environment variables`.

### 2) Mobile app (iOS + Android)

For self-hosting, the recommended flow is:

1. Self-host the **server**, then
2. Use the Happier app and set its **Server URL** to your instance.

In this setup, you do **not** need to configure APNs/FCM yourself. The app already includes the required push notification credentials; your server just stores the user’s Expo push tokens.

### 3) CLI (sender)

The CLI sends notifications by:

1. Calling your server to fetch saved Expo push tokens for the authenticated user.
2. Sending push payloads via Expo’s push API to those tokens.

If a user runs their **own server + CLI**, they must:

- Point both app and CLI at the same server URL.
- Ensure the server stores push tokens (routes above).

## Self-hosting checklists

### Recommended (server-only)

1. Deploy the server.
2. In the Happier app, set **Server URL** to your server.
3. Run the CLI against that same server URL.

Once the app has registered a push token to your server, the CLI can send notifications (including permission notifications) via Expo.

## Multi-server behavior

Notifications are also **multi-server-aware**.

When a notification targets a different server than the one currently active in the app, Happier tries to route you correctly:

- if that server is already saved, Happier switches to it first
- if it is the first server on the device, Happier can bootstrap that server so the deep link still works
- if the app already has saved servers and the incoming server is not one of them, Happier opens **Server settings** with the URL prefilled so you can review and add it explicitly

After you add and use that server, Happier continues to the original session/request automatically.

See [Homes](/accounts/multi-server) and [Notification routing](/extras/notifications-routing) for the full user-facing flow.

## API key restrictions (Android / Firebase)

For Firebase Android configs, the API key embedded in `google-services.json` is **client-side**. Security comes from **restrictions**, not secrecy:

### Application restriction (recommended)

In Google Cloud Console, restrict the API key to:

- **Android apps**
- Your app’s **package name(s)**
- Your signing certificate **SHA-1** fingerprint(s)

#### Finding the SHA-1 fingerprints you should add

You typically need **more than one** SHA-1 during development and release:

- **Debug / dev builds** (your dev keystore)
- **Release builds** (your release/upload keystore)
- **Play Store installs** (the **Play App Signing** key, once enabled)

Common places to find them:

- **EAS**: view Android credentials and copy the keystore SHA-1 (upload/release key).
- **Play Console** (after enabling Play App Signing): *App integrity* → *App signing certificate* → SHA-1.
- **Firebase Console**: *Project settings* → *Your apps* → *Android app* → add SHA-1 fingerprints (so Firebase recognizes the signing cert).

Note: the “fingerprint” shown in EAS build lists is **not** the same thing as the Android signing certificate SHA-1.

### API restriction (recommended minimal allowlist for Cloud Messaging)

If you use Firebase **Cloud Messaging** only, Google’s own allowlist guidance for Firebase keys is:

- **Firebase Management API** (`firebase.googleapis.com`)
- **Cloud Logging API** (`logging.googleapis.com`)
- **Firebase Installations API** (`firebaseinstallations.googleapis.com`)
- **FCM Registration API** (`fcmregistrations.googleapis.com`)

If you enable additional Firebase products (Firestore/Storage/Auth/etc), expand the allowlist accordingly.

## Development builds (optional)

By default, Happier avoids registering push tokens in `__DEV__` to prevent accidental token churn during local dev.

To enable push token registration in dev builds, set:

- `EXPO_PUBLIC_ENABLE_DEV_PUSH_TOKEN_REGISTRATION=1`
