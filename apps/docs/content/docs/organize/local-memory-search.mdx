title: Local memory search
description: Search a machine-local index of past conversations, with optional memory hints and embeddings.

Local memory search lets Happier build a **machine-local search index** from
sessions owned by a daemon-connected machine and, when you opt in, Agent
conversations started outside Happier.

Use it when you want Happier to answer questions such as:

- “Do you remember when we discussed this?”
- “Find the session where we talked about OpenCode quotas.”
- “Show me the earlier conversation about the daemon memory plan.”

## Availability in 0.3 development

This page describes **0.3 development/preview** behavior, not a released stable
version. The Search settings and native-conversation indexing described here
require a matching development build on the machine and client.

The 0.3 development defaults enable keyword search with deep indexing and
embeddings off. This default keyword path needs no model API credentials and
makes no summarizer or embedding calls. An explicitly disabled
machine stays disabled, and existing indexing choices are retained. These are
development defaults, not a claim about released builds.

In development, deep search can also search attached memory and instruction
documents through the existing `memory.search` Action. Explicit `corpora` selects
documents, Sessions, or both; omitting it for global/Session scope preserves Session results. Document
search includes the complete stored memory index, every topic, and archived or
expired facts—not just the short index loaded into a prompt. Each query checks
current attachment membership, read access, and document revision before returning
snippets. Unavailable context reports unavailable document coverage, not a complete
search with zero matches.

Development Action callers can restrict memory search to a Project by its
Home-qualified identity, including a Project with saved memory and no Sessions.
This searches that Project's current attachments and matching Session evidence
on the selected machine. It requires a daemon that explicitly supports Project
search; an older daemon reports unsupported instead of searching everywhere.
Project queries include documents and Sessions by default; other scopes keep
their transcript-only default when no corpus is selected.
Unreadable Project membership or native conversations without a proven Project
association produce partial or unavailable coverage, rather than a false
complete result. Project search does not include unrelated Account or Profile
attachments.

An unsupported peer returns `memory_project_scope_unsupported`, not an empty
Project result or an automatic search of everything. Update Happier on the
selected machine before retrying. Choosing a broader search is a separate
explicit choice. The scope described here is a development Action contract,
not released availability.

In the development memory-document summary, **Always remembered** counts facts
selected by a fresh preparation for the open Session, after its switches, inherited
entry exclusions, expiry and prompt budget apply. It does not describe a previous
accepted turn. **Searchable** counts indexed facts at the displayed document's exact
revision: key facts, topic facts, archive and expired facts. Instructions and past
Session transcripts are not part of that fact count. A document page without a
Session preparation shows the loaded count as unavailable; pending indexing,
unreadable context and older daemons do not become zero counts.

Authenticated CLI/MCP calls negotiate document support with the selected daemon;
older daemons retain Session matches without claiming document coverage. A
credentialless Session-bound MCP tool has no document authority and remains
transcript-only. Light indexing does not provide document search. Combined-search
presentation is available in the development Memory surfaces; the live
cross-client journey remains unverified here. This is not a claim about released
builds.

## Search memory documents in development

The development Memory search surface combines remembered facts and past
Sessions on the chosen Memory Machine. Project Memory searches that Project's
attachments and Session evidence. A matching fact opens its
[Memory page or topic](/extending/prompts#memory-pages-and-topics-in-03-development);
a matching Session opens at the conversation match.

Choose a Memory Machine for the current Home before searching. The document
search surface uses that explicit selection; it does not automatically query
every machine. A selected offline Machine remains identified so you can repair
the connection or choose another. A failed read offers Retry. Missing access,
pending indexing or an older daemon is reported as unavailable coverage rather
than a successful search with no remembered facts.

Document search requires deep indexing and the **Memory search** feature.
It searches the complete stored memory, including topic, archive and expired
facts, even though only eligible key facts and topic summaries enter a prepared
prompt. Search results and the document's current access are checked separately;
a result link grants no access.

## What it does

When local memory search is enabled on a machine, Happier can:

- build and maintain a **local derived index** from that machine’s transcripts
- search it from [Search](/organize/search) and the session list’s search field
- open the matching session at the relevant conversation point
- let coding and voice agents use memory tools for recall instead of guessing from model memory

Each machine owns its index. **All machines** in Search queries those indexes
without copying them into a shared server-side index.

## Where to find it

Choose the machine under **Settings → Search**. **Search on demand** controls
explicit native-history scans; **Memory search** opens that machine's indexing
options under **Settings → Local memory search**. In 0.3 development,
the `memory.search` feature is enabled by default; an explicit switch off in
**Settings → Features** still disables the local search surface.

Searching happens in the same places everything else is searchable —
[Search](/organize/search) and the session list’s search field. There is no
separate Local Memory Search screen: transcript matches appear as a Messages
group beside the other results, and session-list matches surface as normal
session rows.

## Two transcript search sources

Local memory search is one of two Happier-session sources Search can consult. A Personal
Home’s plaintext transcripts are searchable directly when that Home's
operator enables Home search; the app's `memory.search` feature switch does
not control it. Otherwise, a machine with local memory search answers from its
own index. Opted-in native conversations can still come from machine-local
indexes alongside Home session results. [Search](/organize/search) describes
source selection, All machines scope and coverage.

## Important model: machine-local, not account-global

Indexing and its settings belong to the **selected machine**. Search can query
one machine or all machines in the selected Home.

That means:

- each machine has its own index
- a laptop and a remote dev box do **not** automatically share one memory index
- if a machine is offline, Happier cannot query its local memory index; other
  online machines can still answer an All machines query
- remote embeddings settings are also machine-local, not shared globally

This design is deliberate:

- transcript decryption already happens on the client / daemon side
- the derived memory index stays on the machine that built it
- users can choose different storage and embeddings settings per machine

## Light vs deep indexing

Happier supports two indexing modes.

### Light

Light mode stores **summary shards** only.

Use it when you want:

- lower disk usage
- faster background maintenance
- a lighter-weight recall layer

Selecting hints opts into summarization. Hint generation has an independent
enablement switch and can also be used with deep indexing. Deep keyword indexing
is the 0.3 development default and does not enable hints.

### Deep

Deep mode stores **message chunks** locally.

Use it when you want:

- stronger recall over real conversation content
- better search quality for specific topics, decisions, or snippets
- optional embeddings-based reranking

Deep mode uses more disk and can take longer to backfill.

Keyword retrieval ranks full-text matches, keeps identifiers such as
`session_handoff` searchable whole or as separate words, matches prefixes,
and can repair a mistyped word from the indexed vocabulary. Snippets are
centered on a match. Actions support paging and date bounds for indexed hits;
these bounds do not turn an unindexed standard scan into a date-filtered search.
Edited Happier messages are reindexed, including edits that keep the same
message position.

## Index conversations outside Happier

Under **Settings → Search**, enable Memory search, then turn on **Index these
conversations** in **Conversations outside Happier**. Pick the Agents whose history may be indexed,
choose **How far back**, and enable **Include tool output** only if you want
that content stored too. Native indexing defaults to off, with no Agents
selected, all history as its window, and tool output excluded. The history
window works within the machine's existing backfill and coverage choices.

### Supported native history

This matrix applies to **0.3 development**, not a released stable build. Every supported row supplies standard content search and opt-in native indexing through the same transcript reader.

| Agent | Standard search and opt-in indexing in 0.3 development |
| --- | --- |
| Claude Code | Local JSONL transcripts; appends and rewrites use the existing reader. |
| Codex | Local rollout families; app-server-only threads without a readable transcript remain a coverage gap. |
| Pi | Native JSONL history, through the shared decoded-text search helper. |
| OhMyPi | Native JSONL history, with source-wide change observation. |
| Antigravity | Native JSONL history, with source-wide change observation. |
| OpenCode | Decoded messages from its native client; requires an available endpoint. |
| Gemini | CLI v0.64.0 JSONL recordings and legacy JSON; patches, checkpoints and inclusive rewinds select visible history. |
| Qwen Code | CLI v0.25.3 JSONL, including archived chats; active-parent replay and streaming fragments preserve visible text across compression. |
| Copilot | Event-v1 history; transient deltas and model-only compaction data are excluded. |
| Droid | Schema-2 history characterized from CLI 0.170.0; follows the visible active parent chain. |
| CodeBuddy | CLI 2.170.0 JSONL, including native replay and rewind. |
| Grok | Paired summary and history files; producing CLI version unknown. |
| Cursor CLI | JSONL transcripts with v1 chat metadata; producing CLI version unknown. |
| Kiro | V1 paired CLI chat store; separate ACP V3 history remains unsupported. |
| Kimi Code | CLI 0.18.0 / wire protocol 1.4; retains compacted history and applies undo/clear boundaries. |
| Kilo | CLI 1.0.25 JSON session/message/part files; other storage dialects remain unsupported. |
| FX | CLI v0.0.14 schema-4 events and referenced tool results; legacy formats and opt-in sessions-v2 remain unsupported. |
| Auggie | CLI 0.36.0 JSON snapshots; backups and temporary files are excluded, and summaries cannot recover discarded history. |
| Devin | CLI 3000.6.7 schema-16 database; active ancestry excludes abandoned branches and private thinking. |
| Custom ACP | Unsupported without a named definition and characterized native-history reader; list/resume alone is insufficient. |
| CodeRabbit and DeepSec review Agents | No arbitrary native conversation corpus is characterized; their Happier review output belongs to Happier-session search. |

Both modes require readable history on an online machine and a matching development daemon. The table describes characterized formats, not every version of an installed Agent. Unknown formats and unreadable ranges report partial or unsupported coverage, never a complete search with no matches. Installed-CLI capture and platform validation remain release checks for the new readers. File readers require no export or vendor process; OpenCode uses its native client.

Devin reads only private temporary byte copies of its database and WAL, opens those copies read-only, then deletes them. SQLite never opens the vendor files. A copy taken during a write may be slightly stale; failed reads retain indexed history, while confirmed deletion removes it.

Being installed or appearing in the Agent selection list does not prove readable history. Enable indexing only for the sources you want stored locally.

The index follows native transcript changes through the existing source
observation. Confirmed source removal drops its indexed content; an incomplete
or failed read does not count as proof of deletion. Index status reports
progress for the machine. Actions also expose source readiness, so Search can
use a ready native index and fall back to an explicitly started scan for
sources that are not ready. Browse Existing Sessions uses eligible indexes as
you type; its Search control explicitly includes unready sources when Search
on demand is enabled.

## Backfill behavior

When you turn local memory search on, you can choose how much history Happier should index:

- **New only** — index only content created after enabling memory search
- **Last 30 days** — backfill recent history
- **All history** — backfill everything available on that machine

If you want the fastest, lowest-risk rollout, start with **New only**.

If you want older conversations to be searchable immediately, use **Last 30 days** or **All history**.

### Archived sessions

Archived sessions are **excluded from a machine’s index by default**. Turn on
**Search archived sessions** in that machine’s memory settings to make them
eligible; turning it off again removes already-indexed archived content from
that machine’s search.

Two honest details. Enabling the switch does not backfill everything on its
own — what gets indexed still follows the backfill choice above. And the
switch only takes effect where the machine’s Happier build supports it: when
a machine has not reported support, Happier shows that an update is needed
there instead of applying a setting it cannot honor.

## Memory hint generation

Light mode relies on **memory hints** (summary shards). The independent
`hints.enabled` switch defaults to false and is enforced by the worker.
Selecting hints enables it without requiring a change from deep indexing.

You can configure:

- the summarizer backend
- the summarizer model
- whether summarization runs with `no tools` or `read only` permissions

This is useful if you want memory hints to run through a specific backend or model already available on that machine.

## Embeddings in deep mode

Embeddings are optional and only apply to **deep** indexing mode.

Without embeddings:

- Happier still performs deep search
- ranking falls back to text-based matching only

With embeddings:

- Happier can improve deep-search ranking
- the embeddings layer is blended with text ranking

## Embeddings presets

Happier currently exposes these modes:

- **Off** — deep search uses text-only ranking
- **Balanced** — `Xenova/all-MiniLM-L6-v2`
- **Long context** — `Xenova/jina-embeddings-v2-small-en`
- **Quality** — `Alibaba-NLP/gte-modernbert-base`
- **Custom** — choose your own local model or OpenAI-compatible endpoint

Embeddings are off by default. When choosing a local model, `Balanced` offers:
- smaller download
- lower cold-start cost
- good overall retrieval quality

`Long context` works well and is often a better fit for larger transcript chunks, but it still has a heavier first-use cost than the default.

`Quality` is the heaviest preset and is best treated as an evaluation / advanced option.

## Local embeddings

For local presets and custom local models:

- Happier manages the local runtime itself
- the model downloads on first use
- after that, the model runs locally from the daemon cache

Users do **not** need to install Python, Ollama, sentence-transformers, or another separate embeddings service.

## Custom remote embeddings

Advanced users can choose **Custom → OpenAI-compatible endpoint**.

That lets you provide:

- a base URL
- an API key
- a remote embeddings model
- optional dimensions

This is useful if you already operate your own embeddings service or want to use an OpenAI-compatible endpoint instead of a local model.

Important details:

- the remote settings are **machine-local**
- the API key is stored in the daemon’s local sealed settings, not as plaintext
- if the remote endpoint is unavailable or misconfigured, Happier falls back safely to text-only ranking instead of breaking memory search

## Privacy and cleanup

The derived conversation index is **plaintext on the machine that builds it**.
This includes decrypted Happier transcript text and any native conversations
you opt into indexing. Account E2EE protects server-stored envelopes, not this
local SQLite index. Enable native indexing only on machines where you accept
that local storage. Optional remote embeddings send indexed text/query input
to your configured endpoint; they are a separate choice from local indexing.

When enabled, Happier stores local indexes such as:

- the light index database
- the deep index database
- optional local model caches

You can enable **Delete on disable** to remove local indexes and caches when memory search is turned off on that machine.

**Clear index** under **Settings → Search** asks for confirmation and removes
the machine's derived conversation databases and indexing progress, including
native rows. It preserves saved Search settings and inference-model caches.
If indexing remains enabled, the index can rebuild immediately. Turn off
indexing first if you want it to stay empty. Clearing does not delete the
original conversations and is not secure physical erasure.

## What agents do with it

When memory search is available and usable, Happier prompts its agents to use memory tools for recall requests.

In practice, that means:

- if you ask “do you remember when we discussed X?”, the agent should search memory first
- if it finds a likely hit, it can fetch the matching window before answering
- if memory search finds nothing, the agent should say that clearly instead of inventing an answer

This applies to both normal coding sessions and voice flows when memory search is available on the target machine.

In this development channel, Agents and MCP callers can read or change Search
choices with `search.settings.get` / `search.settings.set`, inspect per-source
readiness with `memory.status`, and use `search.conversations` through a
connected app to choose indexed, standard or best-available search across
machines. `memory.search` queries one machine; `memory.get_window` retrieves
the context around a Happier or native hit. Native context requires
authenticated access; a credentialless session-bound MCP tool remains
session-only. `memory.clear_index` is a danger Action requiring approval by
default; its configured policy can change that default. See the
[generated Actions catalog](/plugins/api/host-actions) for inputs and surfaces.

## Typical use cases

### Find an earlier design discussion

Use **Local Memory Search** when you remember the topic but not the exact session.

Example:

- “Find where we discussed connected-service quotas.”

### Re-open an old session at the right moment

Search for a topic, then open the hit to jump back to the matching part of the transcript instead of scrolling through the full session manually.

### Improve recall on a primary work machine

Enable deep indexing and a local embeddings preset on the machine where most of your sessions run.

### Keep a remote dev box searchable

Enable memory search separately on a remote machine if that is where the daemon actually runs your sessions.

## Limitations and expectations

- Local memory search is **not** a server-wide shared search index.
- Search quality depends on what has already been indexed on the selected machine.
- Deep indexing and embeddings can take time after first enablement or after switching models.
- Remote embeddings are an advanced option and depend on your endpoint behaving like an OpenAI-compatible embeddings API.

## Recommended setup

For most users:

1. Choose your main machine
2. Start with **Deep** keyword search; enable hints or embeddings deliberately
3. Use **New only** first
4. Turn on **Delete on disable** if you want easy cleanup
