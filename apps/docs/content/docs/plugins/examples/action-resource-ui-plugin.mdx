title: Action + Resource + UI plugin
description: One small plugin that declares an Action, a Resource, and a surface that reads both.
---

This is the smallest plugin that spans all three ordinary contribution kinds:
one Action the user can run, one Resource the UI reads, and one surface that
mounts them together. Everything below is one `definePlugin(...)` declaration
plus one component file.

## The declaration

```ts
import {
  definePlugin,
  defineUiSurfaceDefinition,
} from '@happier-dev/plugin-sdk';

const statusPanel = defineUiSurfaceDefinition({
  id: 'status',
  placement: 'appPage',
  title: 'Build status',
  renderer: {
    kind: 'reactNative',
    // Name only the host methods the surface cannot run without.
    requiredHostMethods: ['context', 'executeAction', 'readResource'],
  },
});

let lastBuild = 'never';
let invalidateBuildStatus: (() => void) | null = null;

export const { manifest, activate } = definePlugin({
  id: 'com.example.build-status',
  version: '0.1.0',
  entrypoints: { daemon: './dist/index.js' },
  actions: {
    'run-build': {
      title: 'Run build',
      description: 'Runs the workspace build and records when it finished.',
      execution: { target: 'daemon' },
      surfaces: ['agent', 'cli', 'mcp', 'ui'],
      async run(_input, context) {
        context.signal?.throwIfAborted();
        lastBuild = new Date(0).toISOString();
        invalidateBuildStatus?.();
        return { lastBuild };
      },
    },
  },
  resources: {
    'build-status': {
      source: 'dynamic',
      kind: 'config',
      scope: 'global',
      contentType: 'application/json',
      maxBytes: 4096,
      runtime: {
        read() {
          return JSON.stringify({ lastBuild });
        },
        // The host invalidates readers; the plugin only says when to look again.
        observe(invalidate) {
          invalidateBuildStatus = invalidate;
          return { dispose() { invalidateBuildStatus = null; } };
        },
      },
    },
  },
  ui: { surfaces: [statusPanel] },
});
```

The high-level surface derives the executable artifact id `status-renderer`.
Expose its `renderSurface` module through the matching package export:

```json
{
  "exports": {
    "./happier-plugin-ui/status-renderer": "./src/ui/StatusPanel.tsx"
  }
}
```

Three things are doing the work:

- The **Action** is the only implementation. A CLI call, an agent tool, and the
  button below all reach this one handler.
- The **Resource** is how the surface reads plugin-owned state. It is a read
  path, not a second write path — the Action still owns the mutation.
- The **surface** derives its renderer and artifact ids from its surface id, so
  there is no separate `ui.views` / `ui.renderers` pair to keep in sync.

## The surface

```tsx
import * as React from 'react';
import { defineUiSurface, usePluginResource } from '@happier-dev/plugin-ui';
import { Action, Card, Text } from '@happier-dev/plugin-ui/components';

function StatusPanel() {
  const { resource } = usePluginResource('build-status');
  const lastBuild = resource.value
    ? (JSON.parse(
        new TextDecoder().decode(resource.value.bytes),
      ) as Readonly<{ lastBuild: string }>).lastBuild
    : 'unknown';

  return (
    <Card>
      <Text variant="title" value="Build status" />
      <Text variant="body" value={`Last build: ${lastBuild}`} />
      <Action.Execute action="run-build" title="Run build" />
    </Card>
  );
}

export const renderSurface = defineUiSurface(StatusPanel);
```

`Action.Execute` names the same local id the manifest declared; the host binds
it. Do not add a local click handler that calls your daemon another way.

## Add host-rendered Session Inbox controls

In **0.3 development source / Developer Preview**, a dynamic JSON Resource can
publish Session Inbox rows with optional declarative `controls`. Import
`PluginSessionInboxRowV1` and `PluginSessionInboxRowPageV1Schema` from
`@happier-dev/plugin-sdk/resources`. These are source contracts; check the
installed SDK before targeting a published host.

Declare the index Resource with `scope: 'surface'` and
`sessionInbox: { detailResourceId: 'session-detail' }`, plus a same-plugin JSON
detail Resource with `scope: 'session'`. Its `read` callback returns a serialized
page such as this:

```ts
import type { PluginSessionInboxRowV1 } from '@happier-dev/plugin-sdk/resources';

const row = {
  id: 'deployment-42',
  session: { serverId: 'home', sessionId: 'session-42' },
  title: 'Review deployment',
  detail: null,
  detailResource: { pluginId: 'com.example.build-status', resourceId: 'session-detail' },
  controls: [
    {
      id: 'Review #42',
      label: { key: 'deployment.review', fallback: 'Review' },
      effect: {
        kind: 'open',
        page: { pageId: 'deployment-review', subPath: 'deployments/42' },
      },
    },
    {
      id: 'Continue',
      label: { key: 'watch.continue', fallback: 'Continue' },
      effect: {
        kind: 'action',
        invocation: {
          action: { pluginId: 'com.example.watch', localId: 'continue' },
          input: { sessionId: 'session-42', expectedRevision: 4 },
        },
      },
    },
  ],
} satisfies PluginSessionInboxRowV1;

const page = { kind: 'ready', rows: [row], nextCursor: null };
// Return JSON.stringify(page) from the declared index Resource's read callback.
```

Control ids are nonempty strings unique within the row; labels can be literals
or `{ key, fallback }`. This is the same button/effect binding used by
[native notification buttons](/plugins/services/notifications#add-native-notification-buttons).
An open effect targets your declared page and exact subPath; omitting `page`
uses the row's normal destination. Two localized Allow and Deny controls may
both open the same review page: neither submits a decision merely because of
its label.

An Action effect may reference another plugin's currently admitted Action.
`input` is required strict JSON, including `null` when appropriate; there is no
`args` alias. The host offers no affordance for an absent or disabled Action.
A press goes through the contributed-Action front door with the viewer's UI
authority, normal policy and confirmation, and the captured Home, Account and
Session. The target Action still validates its own input and current state;
include its expected revision when its contract uses CAS. Stale or replayed
presses gain nothing beyond that Action's own rules. Returning Resource data
never runs an Action or grants person authority to plugin JavaScript.

The host owns the control-row presentation; this declaration does not add a
plugin renderer, Inbox producer registry or permission workflow.

## What to add next

- Needs the Resource to refresh when the Action lands? Swap
  `usePluginResource` for `useLivePluginResource` and add `watchResource` to
  `requiredHostMethods`. It watches for invalidation — it does not poll.
- Needs Account-backed rows instead of one document? Use
  [Account Collections](/plugins/guides/account-collections) with
  `usePluginCollectionQuery`.
- Needs to test it? [Testkit recipes](/plugins/testing/recipes) covers the
  Action, its host boundaries, its typed failures, and its cancellation.
