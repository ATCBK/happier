---
title: Account Collections migrations
description: Declare one Collection contract and migrate its rows through the candidate-local callback projection.
---

Use Account Collections when a plugin needs Account-scoped structured data. The
installed SDK's `capability-matrix.json` is the availability authority; this
guide explains the available `accountCollections` task without creating another
catalog. “Available” here means the current source author contract, not public
package or release availability.

## One declaration, one ordered migration chain

Keep the schema and each adjacent migration edge in one
`defineAccountCollection(...)` declaration. `definePlugin(...)` projects the
static manifest identity (`id`, source version, target version, and migration
id) into the cold manifest, while the migration callback stays candidate-local.
Do not hand-author a second manifest migration list or a separate callback map.

```ts
import { definePlugin } from '@happier-dev/plugin-sdk';
import { defineAccountCollection } from '@happier-dev/plugin-sdk/collections';

const reviewStatuses = defineAccountCollection({
  id: 'review-statuses',
  schemaVersion: 2,
  readableSchemaVersions: [1, 2],
  schema: {
    type: 'object',
    properties: {
      id: { type: 'string', minLength: 1 },
      title: { type: 'string', minLength: 1 },
      status: { type: 'string', enum: ['open', 'done'] },
    },
    required: ['id', 'title', 'status'],
    additionalProperties: false,
  },
  rowIdField: 'id',
  identityFields: [],
  serverReadable: ['title', 'status'],
  indexes: [{
    id: 'by-status',
    fields: [{ field: 'status', direction: 'asc' }],
  }],
  uiQueries: [],
  relations: [],
  migrations: [{
    id: 'review-statuses-v1-to-v2',
    fromSchemaVersion: 1,
    toSchemaVersion: 2,
    migrate(value) {
      const legacy = value as Readonly<{ id: string; title: string; done: boolean }>;
      return {
        id: legacy.id,
        title: legacy.title,
        status: legacy.done ? 'done' : 'open',
      };
    },
  }],
});

export const { manifest, activate } = definePlugin({
  id: 'com.example.review-statuses',
  version: '0.1.0',
  entrypoints: { daemon: './dist/index.js' },
  accountCollections: {
    'review-statuses': reviewStatuses,
  },
});
```

The host accepts one ordered source-to-target chain only: each callback must
match its declared migration id and adjacent source/target versions in order.
List every version that remains readable in `readableSchemaVersions`, including
the current version, so the host can verify that exact chain.
The callback receives the already-admitted source row and returns the target
row. It does not select an Account, Collection, storage writer, or retry loop.
The host may invoke it more than once while preparing or retrying a candidate,
until that exact staged output is accepted. Keep the callback pure and
idempotent, and do not perform external writes or other side effects from it.

Candidate preparation completes before the new plugin occurrence becomes
current. The server stages the exact migrated rows and promotes the complete
candidate atomically with the selected release; a failed callback, incomplete
stage, revision mismatch, or late promotion failure leaves both the incumbent
plugin and incumbent Collection data serving. Plugin activation never infers
that a Collection is absent and cannot bypass this promotion owner.

Reads of an absent row include the server-owned `absenceEpoch`. A create based
on absence is fenced to that value, and forgetting or deleting data advances
it. This prevents an update, uninstall, and later reinstall from resurrecting a
row that was deleted while another candidate was being prepared. Authors do
not allocate, persist, or reset the epoch; use the Collection APIs and preserve
the typed conflict/retry result.

## Where the current writer comes from

Each Account has one current writer contract per Collection. For a plugin you
installed as a published package, the release selected for the Account sets it.
Bundled, development, and drop-in plugins have no published release, so the
daemon running them claims the writer from the plugin's own declaration when
the plugin activates and before its first Collection operation. The server
rebuilds the contract from that declaration and recomputes its digest.

The claim carries the plugin's whole admitted manifest, so the same claim makes
the plugin's webhooks and automation Events current for the Account. The server
reads them from the claimed manifest while a machine runs that exact plugin
version. A plugin that declares only webhooks or Events claims too.

A few rules keep that claim predictable:

- A release selected for the Account always wins. The daemon's claim never
  replaces it.
- When machines run different plugin versions, the Account keeps the newest
  claimed manifest and the highest `schemaVersion` for each Collection. Until
  it updates, a machine running an older version receives no webhook
  deliveries, admits no Events, and cannot write. It reads a Collection only
  when its declaration already lists the newer version in
  `readableSchemaVersions`. A compatible retained contract at the same schema
  version can read but cannot write after another digest becomes current.
- In 0.3 development source, a compatible schema widening needs no new
  `schemaVersion`: the server proves that source values remain valid, including
  nested optional fields and wider value domains, while projection, index, query,
  relation, identity and quota semantics stay unchanged. Stored readers ignore
  unknown fields recursively while validating known fields. The server adopts the
  new contract atomically without changing payload bytes or row revisions.
  Incompatible changes, such as a newly required field or a narrowed type, remain
  refused under the same version; use a new schema version and migration. This
  includes removing a declared field from a closed object: tolerant reads can ignore its retained
  value, but the new writer schema rejects values the old writer accepted. This
  decision also applies to JSON Schemas imported from another package.
  The daemon retains the typed
  `plugin_collection_contract_conflict` for unchanged claim inputs, so repeated
  mutations do not resend the manifest. Reads still ask the server to admit the
  exact retained contract: compatible readers can read without reclaiming the
  writer; refused reads retain the typed conflict instead of looking empty.
  For incompatible changes, update the plugin's `schemaVersion` and migration,
  then reload the corrected plugin. Changed declarations, plugin occurrences,
  Accounts or Account Availability invalidations allow a fresh claim; network
  and 5xx server failures still retry on the next operation.
- In 0.3 development source, moving an empty Collection to a new `schemaVersion`
  is immediate. For populated Collections that need a migration, the daemon
  loads the declaring plugin's exported `collectionMigrations` and uses the same candidate
  preparation path as a portable release. It validates and stages retained
  rows against their observed revisions; the server rechecks them and promotes
  all target Collections with the writer claim in one transaction. Until that
  succeeds, the old writer remains admitted. Missing callbacks, changed source
  rows, cancellation or failed validation leave the writer and retained data
  unchanged; a later operation can retry. Data erasure is not an upgrade step.
  Schema-proven widenings use the same atomic identity adoption for release and
  daemon claims. An older narrower declaration cannot reclaim the writer.

## Portable migration entries

In 0.3 development source, a Collection's `migrationArtifact` selects a portable
entry whose zero-argument `collectionMigrations()` returns the callback map keyed
by Collection id. Share those migration arrays with the Collection definitions
so both paths use the same callbacks and migration identities.

Keep that entry and its dependencies pure. Importing the full daemon plugin
definition can pull in Node APIs and make the artifact fail to compile. The
Plugin UI build supplies the complete manifest it captured for discovery; authors
do not copy or rebuild a second manifest in the migration entry. The compiled
export returns `{ manifest, collectionMigrations }` for the candidate loader's
existing validation. Node built-ins remain unsupported in portable artifacts.

## Writing more rows than one batch carries

`batch` is atomic: every operation in one call applies together or none does.
A deployment bounds how many operations and how many encoded bytes one call may
carry, so writing a large set means splitting it into several atomic batches.

Do not guess those bounds. Read them from the collection handle:

```ts
const limits = await collection.limits();
const measurement = await collection.measureBatch(operations);
```

`limits()` reports what is actually in force — the deployment's published policy
narrowed by your collection's admitted quota — and says through `basis` whether
the deployment published it or the platform default is being assumed.
`maxRows` and `maxCollectionEncodedBytes` are this Collection's effective
ceilings. `maxAccountRows` and `maxAccountBytes` are the separate aggregate
ceilings shared by all Collections in the Account; neither pair substitutes for
the other.
`measureBatch()` reports what those operations cost on the wire, measured
through the same seal-and-serialize path `batch` uses, so the private envelope
is accounted for on an end-to-end-encrypted Account without you modelling it.

Costs are additive: a batch of any subset encodes to at most
`overheadEncodedBytes` plus that subset's entries in `operationEncodedBytes`.
Pack against those numbers, keep any operation that must repeat in every batch
(such as a fence `assert`) in the measurement, and stay within
`limits.maxBatchRows`. You may measure more operations than one batch can
carry — that is the point — and each reported cost stays exact.

The server remains the enforcement owner. Planning against these numbers avoids
a rejected batch; it does not replace the typed `collection_quota_incompatible`
failure you must still handle.

In 0.3 development source, both Account realms report a private envelope that
exceeds the existing encoded limit as `collection_quota_incompatible`, before
issuing a write. Its `PluginError.details` uses the same shape as a server size
refusal: `{ dimension: 'maxRowEncodedBytes', effectiveMaximum }`. This also
applies to `measureBatch()`. Split retained entries only after a known size
refusal; a malformed value or failed encryption remains an invalid-value error
and is not a reason to split. The private-envelope limit is unchanged.

## Failure, retry, and rollback

A migration failure rejects that candidate's preparation or transition; do not
catch it and silently write an alternate shape. Correct the source declaration
or callback and let the ordinary development or install flow prepare a new
candidate. The host owns retry and currentness around the admitted transition.

Rollback belongs to the installed-package lifecycle, not to Collection code and
not to development occurrences. If a prior compatible managed installation is
retained, use the normal plugin rollback flow. Plan a new explicit forward
migration when the data contract must change again, and keep its source and
target versions adjacent.

For a maintained direct-Data example without a migration, see the installed
`examples/projects-tasks/` package. Its Collection declaration remains the
canonical UI/client pattern; add a migration only when a real row contract
changes.
