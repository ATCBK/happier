---
title: Marketplace distribution
description: How marketplace sources recommend npm plugin packages, and what they never decide.
---

Marketplace distribution uses the same manifest-first and trust-first model as
local plugins. A marketplace source is a discovery index over npm artifacts —
not an artifact registry, certification authority, or signing infrastructure
of its own. It recommends exact npm packages; the registry artifact remains
the thing that is downloaded, reviewed, and trusted.

## What a source is and does

Every listing pins an exact npm package, version, registry origin, and SRI
integrity value, and installing it fetches exactly that artifact. Happier
ships no publisher PKI, certification, review-receipt, or global revocation
network behind a listing. Curation shapes what you discover and
recommends; it never decides trust by itself, never acts as hidden
authorization for one exact release, and never disables code you already
installed.

When an npm-compatible registry supplies its native registry signature,
Happier verifies that acquisition evidence over the exact package, version,
and SRI. The signing key belongs to the registry: it is not a certification of
the catalog's publisher label and key rotation does not change the trusted
plugin publisher. Catalog publisher names remain unverified discovery and
presentation metadata.

In **0.3 development source**, plugin discovery uses the Account's registry
sources. Public catalog and npm listings are fetched directly by the client;
choosing an installation machine is not a prerequisite for browsing. Exact
installation review, npm credential profiles and installation still belong to
the chosen machine. Three source paths feed that discovery:

- **Happier curated** — the configured Happier catalog, with reviewed
  recommendation and provenance but no automatic execution trust.
- **Community npm** — built in: keyword discovery over the public npm registry.
- **User catalogs** — catalog documents you add with `hdev registries add`.
  Each entry points at an npm artifact. Sources can be enabled or disabled for
  the Account; built-in sources cannot be removed.

## Curated catalog availability

Development builds now produce a strict static snapshot for
`https://marketplace.happier.dev/catalog.json`, but that hostname is not live
yet and the snapshot contains no plugin listings. Happier's first-party plugin
packages are bundled privately; they are not public npm coordinates that the
marketplace can install.

The first curated listing requires an approved review and a public, exact npm
release whose integrity and plugin metadata can be verified. Curation records
recommendation and provenance; it never makes a plugin trusted automatically.
Community npm discovery and user-added catalogs remain available independently
of curated content. A production website promotion will require the catalog
hostname to resolve and will compare the served bytes with the release
candidate before the deployment succeeds.

## Requirements

Marketplace entries should provide enough metadata for Happier to show:

- plugin identity
- source and provenance
- version compatibility
- requested host access and trusted-code disclosures
- contribution previews
- install/trust prompts

In the current Developer Preview source, catalog readers ignore unknown fields
inside `display`, `summary`, and `links`, then cache only the known fields.
Known values still have to validate. Plugin and source identity, npm
coordinates, integrity, compatibility, and review facts remain strict; an
unknown field in one of those envelopes rejects the source.

## Community npm discovery

Community discovery searches npm's `happier-plugin` keyword for candidate
package names and versions, combined with your search text. Happier then reads
each candidate's exact version metadata from the registry; it does not rely on
custom fields returned by search results to describe a listing.

`hdev plugins pack` emits the closed
`happier.marketplaceDiscovery` projection beside the generated compatibility
projection. npm supplies the package coordinate and `dist.integrity`; the
projection supplies the manifest-derived display, summary, and exact manifest
digest. A package is listed only when those published projections agree, and
the install path rechecks the selected SRI and manifest digest against the
staged archive before anything runs.

Start with a Community npm listing, then pass both identities from that
listing when you install it:

```bash
hdev registries browse --kind plugin
hdev plugins marketplace install marketplace:community-npm <pluginId> --package <npmPackage> --version <version> --machine <machineId>
```

The npm package name and the plugin ID are separate values and do not have to
match. `--package` is therefore required for Community npm installs. Curated
and added marketplace sources already bind the package coordinate to their
listing. Every marketplace install names the exact version you reviewed and
the machine that will install it. `marketplace:community-npm` is the built-in
source ID; it does not create or save another marketplace source. In 0.3
development source, a required review uses the ordinary `plugins.install`
approval Artifact in the Happier Inbox. Agents, MCP, and CLI callers can use
the same public `approval.request.decide` Action under the user's approval
policy; see [Review a pending change](/plugins/packaging/authoring-cli#review-a-pending-change).

## First install and update authority

Community npm listings and the marketplace sources you add are unreviewed,
and every first install — from any source, including the curated catalog —
reaches one concise trusted-code and declared-authority decision from
[Install and trust](/plugins/packaging/install-trust). Exact package, version,
registry origin, integrity, manifest digest, and compatibility remain technical
admission checks under Details rather than separate approvals. An
authority-neutral update does not prompt; an update that widens authority shows
only that delta. A curated listing the publisher withdraws cannot be newly
installed, but withdrawal is a discovery fact: installed plugins keep working
and keep updating under their own policy.

## Private and custom registries

Listings can point at any npm-compatible registry. Machine-local access is configured with
`hdev plugins registry add` and its `login`, `test`, `logout`, `remove`, and
`list` companions, then select the profile for a direct install. Account source
credentials are a separate contract; the machine profile is not the Account's
registry list. The profile supplies the registry origin, credentials,
and network reach for the artifact, and the review shows the exact origin a
package came from.

## Executable trust

Executable marketplace installs require explicit trust before daemon code
runs. Presence in any source — curated, user, or community — never
substitutes for that decision.

## Compatibility

Use the manifest schema version and optional `engines.happier` to communicate
compatibility. Omitting the engine range does not add a host floor or exclude a
valid packed plugin from Community npm discovery in the current Developer
Preview source. The pack owner emits the resulting generated compatibility
projection; it is not author-maintained marketplace metadata. See [Versioning
and compatibility](/plugins/packaging/versioning-compat).
