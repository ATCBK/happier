title: Notifications
description: Declare notification categories and channels, then send host-mediated notifications from invoked handlers.
---

Plugins declare notification categories and channels in the manifest and send
notifications through `context.services.notifications` from invoked handlers.
The installed SDK's `capability-matrix.json` stays the availability authority
for every contribution family.

## Availability

The Developer Preview source API has maintained external-author source-consumer
evidence and is available in the current source contract. The capability matrix
records loaded-platform and release evidence separately from source
availability. The nonbundled action-contract pair is external source-consumer
evidence, not a loaded-stack or release proof.

## Declare a category and a channel

`notifications` is a descriptor family: each category names its kind, the
events it covers, and the channels it prefers. `notificationChannels` pairs a
channel descriptor with a `NotificationSender` that performs the delivery the
host asks for.

```ts
import type { NotificationSender } from '@happier-dev/plugin-sdk/notifications';

const sendDocumentReviewReady: NotificationSender = async (request) => ({
  deliveryId: request.deliveryId,
  channelId: request.channelId,
  status: 'accepted',
  evidence: 'provider',
});
```

### Channel sender source migration (development)

In the current development source API, `NotificationSender` receives an optional
`categoryId`. Plugin-originated sends still carry the qualified plugin category;
host Activity notifications, including **Notify me** and Workflow Run updates,
have no plugin category and omit it. The `channelId`, title and delivery identity
remain present in both cases.

Channel authors upgrading from the required-category signature must update and
rebuild their sender. Check `request.categoryId !== undefined` before using it
for category-specific formatting or routing; handle a category-less notification
using its supplied title, body and data. Do not invent a plugin category for host
Activity. This is a development source-contract change, not a claim that an older
sender expecting a required category can safely accept the new requests.
`context.services.notifications.send` still requires a declared `categoryId`.

Declare both families in the same `definePlugin` input:

```ts
notifications: {
  'document-review-ready': {
    kind: 'activity',
    title: 'Document review ready',
    eventIds: [],
    defaultChannels: ['webhook'],
  },
},
notificationChannels: {
  webhook: {
    declaration: {
      kind: 'webhook',
      title: 'Document review webhook',
      configurable: true,
      defaultEnabled: true,
      settings: [{
        id: 'endpoint',
        title: 'Webhook URL',
        schema: { type: 'string', minLength: 1 },
      }],
    },
    sender: sendDocumentReviewReady,
  },
},
```

The repository's
[`action-contract-producer`](https://github.com/happier-dev/happier/tree/v0.3/packages/plugin-sdk/examples/action-contract-producer)
example is a conformance reference for this flow. It declares the category and
channel, registers the sender through normal activation, and sends through the
service from an Action. It proves the public external-author source seam, but
not loaded-platform or release availability.

## Send from an invoked handler

```ts
await context.services.notifications.send({
  clientRequestId: 'document-review-ready',
  categoryId: 'document-review-ready',
  title: 'Document review ready',
}, { signal: context.signal });
```

`context.services.notifications.send` accepts only categories the plugin
declares, and only channels that category declares. `clientRequestId` is the
idempotency key: repeating it with the same content replays the recorded
result instead of dispatching twice. The service also exposes `listCategories`,
`listChannels`, `preferences`, and `watchPreferences`.

Use `context.ui.notify(...)` instead when the intent belongs to the current
present-user invocation rather than the notification system; it does not fall
back to the notification service.

## Add native notification buttons

In Developer Preview source, a category can declare buttons with plugin-chosen
ids and labels. Labels use the same literal or `{ key, fallback }` form as other
manifest copy. Ids may be any nonempty string and must be unique within the
category; they are not restricted to a host vocabulary such as Allow or Deny.

Declare the `reviews` page and `accept-review` Action in the same plugin, then
add these buttons to its category:

```ts
buttons: [
  {
    id: 'Review details',
    label: { key: 'review.open', fallback: 'Review details' },
    effect: { kind: 'open', page: { pageId: 'reviews', subPath: 'pending' } },
  },
  {
    id: 'Accept this review',
    label: { key: 'review.accept', fallback: 'Accept review' },
    effect: {
      kind: 'action',
      invocation: {
        action: { pluginId: 'acme.reviews', localId: 'accept-review' },
        input: {},
      },
    },
  },
],
```

Here `acme.reviews` is the declaring plugin's id. An open effect selects an
exact plugin page and optional subpage; omitting `page` opens the notification's
own destination. An Action effect uses the shared closed `{ action, input }`
binding. `input` is required strict JSON and may be null, a scalar, an array or
an object. It must match the Action's input schema at execution.

To address a different item on each send, override the input for a declared
Action button without changing its effect:

```ts
await context.services.notifications.send({
  clientRequestId: 'review-42-revision-2',
  categoryId: 'document-review-ready',
  itemId: 'review-42',
  type: 'decision',
  title: 'Review 42 is ready',
  page: { pageId: 'reviews', subPath: '42' },
  buttonInputs: {
    'Accept this review': { reviewId: '42', expectedRevision: 2 },
  },
});
```

`buttonInputs` keys must identify declared Action buttons. An override replaces
that button's entire default input; it cannot change its Action, label or
navigation. The overrides travel in the native push payload, so never put
credentials or secrets in them. Reusing a
`clientRequestId` with changed overrides conflicts with the earlier send.

The host registers native categories under plugin-qualified ids and resolves
their labels for the active language. Plugin buttons open the app and re-admit
the notification's saved Home and Account for the pressing person. Execution goes through the normal
Action front door, input schema and policy. If an Action needs approval or
confirmation, or cannot execute, the host opens the notification's exact page for
review. It does not replace the Action with a prompt or treat the press as a
Session permission response. Cached launch responses only navigate.

Keep the target Action's own currentness checks, such as `expectedRevision`,
for changes that must reject stale or repeated requests. A notification button
does not add authority or promise exactly-once effects. Native OS presentation
and signed iOS/Android delivery remain release checks; source availability does
not certify a device build.

## Keep an Inbox item up to date

In current development source, a send can also create or update a private
Account Inbox notice. Supply a stable `itemId` for the item and a fresh
`clientRequestId` for each changed send:

```ts
await context.services.notifications.send({
  clientRequestId: 'review-42-revision-2',
  categoryId: 'document-review-ready',
  itemId: 'review-42',
  type: 'update',
  title: 'Review 42 is ready',
  page: { pageId: 'reviews', subPath: '/42' },
});
```

The page belongs to the sending plugin and must be declared by it. The host
supplies plugin and Account identity; requests cannot select another plugin's
item. Updating an item preserves the person's read and dismissed state. A send
with the same `itemId` and `resolved: true` resolves that item without sending
another channel notification. Resolving an item that does not exist is harmless.

Types `update` (the default) and `mention` arrive quietly. Types `decision`,
`approval`, and `blocked` are eligible for interruptions under the Account's
attention preferences and quiet hours. A notice does not grant authority to
approve a request. Use the owning Action for that decision. Without `itemId`,
the service keeps its existing channel-only behavior; `type` still selects
attention policy, while `page` and `resolved` require an item. An older host rejects unsupported item fields
instead of reporting that it saved an Inbox notice.

Item types control attention delivery. Preview formatting and disclosure remain
the existing source and channel sender's responsibility for their title, body,
and data payload; the service does not classify arbitrary plugin data for redaction.

## Host ownership

The host owns notification preferences, channel selection, Account-scoped
settings and secret custody, idempotency, currentness, cancellation, and
delivery outcomes. A plugin channel supplies the delivery boundary the host
calls; it does not own preference state, dispatch, or its own settings store.

## Rules

- Respect user preferences and host availability results.
- Do not call platform notification APIs directly from an Agent leaf.
- Keep titles, bodies, and data free of secrets and raw Provider tokens.
