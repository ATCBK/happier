This guide is for **server operators**. It explains the core auth model and the policy env vars that control signup/login enforcement.

For provider-specific setup guides, see:
- [GitHub auth](/self-hosting/auth-github)
- [OIDC auth](/self-hosting/auth-oidc)
- [mTLS auth](/self-hosting/auth-mtls)
- [Custom auth providers](/self-hosting/auth-custom-providers)

The env vars on this page configure the whole deployment. The 0.3 development branch also
has database-managed providers a Home administrator adds in the app, WorkOS SSO, and Team
sign-in connections with directory sync — see
[Enterprise identity](/self-hosting/auth-enterprise-identity) for how those relate to the
policy model below.

## Choosing an auth setup (private vs public servers)

What you should configure depends mostly on **who can reach your server**.

### Private server (Tailscale/VPN/LAN only)

If your server is only reachable from a private network (for example via Tailscale), you often don’t need provider-based auth:

- Recommended: keep **anonymous signup enabled** (default) and rely on network access control.
- Make sure your server is **not** reachable from the public internet (firewall / security group / reverse proxy).

Example config:

```bash
AUTH_ANONYMOUS_SIGNUP_ENABLED=true
AUTH_SIGNUP_PROVIDERS=
AUTH_REQUIRED_LOGIN_PROVIDERS=
```

Optional (private servers): you can also enable GitHub/OIDC **in addition** to anonymous signup, to offer multiple signup options:

```bash
AUTH_ANONYMOUS_SIGNUP_ENABLED=true
AUTH_SIGNUP_PROVIDERS=github
AUTH_REQUIRED_LOGIN_PROVIDERS=
```

### Public server (reachable from the internet)

If your server is publicly reachable, leaving anonymous signup enabled makes it easy for anyone to create an account. In that setup, it’s usually better to require an identity provider:

- Recommended: **disable anonymous signup**
- Recommended: require a provider for ongoing access (`AUTH_REQUIRED_LOGIN_PROVIDERS`)
- Optional: restrict eligibility with allowlists (for example “must be in GitHub org X”)

Example (GitHub):

```bash
AUTH_ANONYMOUS_SIGNUP_ENABLED=false
AUTH_SIGNUP_PROVIDERS=github
AUTH_REQUIRED_LOGIN_PROVIDERS=github
```

Then follow the provider setup guide:
- GitHub: [GitHub auth](/self-hosting/auth-github)
- OIDC: [OIDC auth](/self-hosting/auth-oidc)

## Standard authentication (device-key accounts)

Happier's active default is a **device-key** account model (each E2EE account is tied
to real client encryption material).

- Default behavior: users can create accounts via device-key signup (`POST /v1/auth`).
- You can optionally require external providers (GitHub and/or OIDC) for signup and/or ongoing access.
- External providers are **not** “password login”: if a user is trying to access an *existing* Happier account from a new device/browser, they still need to **restore** the account (for example via **Add your phone** / **Restore account**), then connect providers from settings.

### Keyed vs keyless (how providers show up in the UI)

The same OAuth provider (for example GitHub or an OIDC provider) can appear in the UI in two different roles:

- **Keyed provisioning** (“Continue with GitHub”): creates a **device-key** account.
  - Users must back up a secret key and **restore** on new devices/browsers.
  - This is the standard Happier model and works on E2EE-only servers.
- **Keyless login** (“Sign in with GitHub”): signs in to a **keyless/plain** account
  without requiring or persisting Account E2EE private material in the token-only
  credential.
  - Sign-in can be **seamless across devices**, but it is intended for enterprise deployments and usually paired with plaintext storage.

Here, **keyless** means a genuine token-only credential: bearer token only, with no
recovery secret, Account machine key, Account content key, or fabricated replacement.
Older documentation that inferred keyless behavior only from
`Account.publicKey == null` is superseded. Credential shape, current Account mode, and
the persisted representation of an existing row are separate facts.

Server operators control which role(s) are enabled via `/v1/features` (policy + feature env vars). Clients should not guess.

## Native email and password (0.3 development)

:::caution Release status
Native email/password ships unreleased, as part of 0.3 development. The source
owners and focused automated checks exist; real SMTP delivery and the complete
web, desktop, iOS, Android, and mixed-version journeys are release checks.
:::

Native email/password authentication is a Home method. Login and new-Account
provisioning are on by default; set `HAPPIER_FEATURE_AUTH_EMAIL_PASSWORD__ENABLED=0`
or `HAPPIER_FEATURE_AUTH_EMAIL_PASSWORD__PROVISION_ENABLED=0` to opt a deployment
out. The Home's effective authentication policy and transactional-mail readiness
remain authoritative, so a deployment that has not opted out still publishes only
the actions those two facts allow.

Verification, password reset, sign-in email changes, and authentication-change
notices require SMTP delivery. At minimum configure:

```bash
HAPPIER_AUTH_EMAIL_SMTP_HOST=smtp.example.com
HAPPIER_AUTH_EMAIL_FROM_ADDRESS=happier@example.com
```

Optional transport settings are `HAPPIER_AUTH_EMAIL_SMTP_PORT`,
`HAPPIER_AUTH_EMAIL_SMTP_SECURE`, `HAPPIER_AUTH_EMAIL_SMTP_USERNAME`,
`HAPPIER_AUTH_EMAIL_SMTP_PASSWORD`, and `HAPPIER_AUTH_EMAIL_FROM_NAME`.

Bearer emails also require a published Home connection descriptor and an application
origin. Configure the Home's public HTTPS ingress (or its supported Iroh endpoint), then
either set `HAPPIER_WEBAPP_URL` or serve the bundled UI from the configured public server
URL. Happier puts that portable Home target beside the one-time bearer. SMTP configuration
alone is not enough.

Mail-dependent actions (account creation by email, **Forgot password?**, sign-in email
changes and emailed invitations) are reported as unavailable until **both** are in place:
SMTP delivery and a link the Home can build. Clients then simply do not offer them, and other
authentication methods continue to work. Verification and reset requests stay
existence-neutral either way.

The UI keeps the journeys distinct: login authenticates an existing Account;
provisioning verifies an email before creating an Account; enrollment/change/removal
belong to Account Security; and password reset is recovery for a plain Account.
An E2EE password cannot replace the Account recovery key or approval from a device
that still holds the required Account material.

First password enrollment on an existing Account may send its own verification
email when that Account has no current evidence for the submitted mailbox. This is
separate from public Account provisioning: its link is bound to the exact signed-in
Account and can only be consumed by the atomic Account Security enrollment. Likewise,
a transferable Team invitation requests mailbox verification in the exact invitation
context; an invalid or no-longer-current invitation sends no mail even though the
public request response remains intentionally neutral.

For a Plain Account with a linked OAuth or mTLS identity, the exact prepared target credential,
canonical mutation digest, and provider-bound external proof stay only in current-process memory.
`TokenStorage`, browser local storage, and native secure storage reject the
`accountPasswordEnrollment` record. The OAuth callback claims the exact Account, Home, provider,
pending value, and request digest once, preserving it in memory only across callback-to-Settings
navigation; its return target uses the exact Home server ID. Reload, replay, expiry, cancellation,
abandonment, or substitution requires fresh salted preparation and proof. mTLS completes directly
in the same process. E2EE proof audiences bind the resolved Home's stable server identity and
canonical server URL, not a device-local alias or transport endpoint.

Trusted interactive CLI hosts expose the same journeys through the shared
Account Security Actions with `present_user` authority and direct confirmation.
Password and recovery-key operations never leave the host and stay unavailable
to agents, MCP, generic API, and the public plugin SDK.
The safe `happier auth security get` projection can also use an authenticated
API token; password and sign-in-email mutations still reject API-token callers.

```bash
# Plain Account sign-in and creation on the selected Home (--server/--server-url select the exact Home)
happier auth email login --email ada@example.com # prompts without echo
happier auth email provision --email ada@example.com  # requests mailbox verification first
happier auth email provision --email ada@example.com --mode plain # use stdin below for mailbox bearer automation

# Account Security (requires the selected Home's stored interactive login)
happier auth security get
happier auth password enroll-email-request --email ada@example.com
happier auth password enroll --email ada@example.com --yes # prompts for password and uses stdin for mailbox bearer automation
happier auth password change # prompts for both passwords and confirmation
happier auth password remove # prompts for the current password and confirmation
happier auth email connect --email ada@example.com --yes # prompts for password
happier auth email change-request --email new@example.com
happier auth email change-complete --verification-token <token>

# E2EE Account Security reuses the recovery secret already held by this CLI
happier auth password change --yes # prompts for the new password
happier auth password change --recover --yes # prompts for the new password
happier auth password remove --yes

# Mailbox and recovery helpers (existence-neutral; secrets never leave the host)
happier auth email verify-request --email ada@example.com
happier auth email reset-request --email ada@example.com
happier auth email reset-submit # prompts are unavailable for the bearer; use the stdin document below
happier auth recovery-key validate # prompts for the recovery key
```

For noninteractive automation, keep secrets out of process arguments by passing
one bounded strict stdin document. The accepted envelope is
`{"v":1,"secrets":{...}}`; supported fields include `password`,
`currentPassword`, `newPassword`, `recoveryKey`, `invitationToken`,
`verificationToken`, `resetToken`, and `reauthProofJson`.

```bash
happier auth password change --yes --secrets-json-stdin <<'JSON'
{"v":1,"secrets":{"currentPassword":"...","newPassword":"..."}}
JSON
```

Secret-bearing argv spellings remain compatibility inputs but are redacted from
CLI command context, logs, Doctor output, and remote diagnostics. Prefer the
no-echo prompt or stdin document because operating-system process listings may
observe argv before the CLI starts.

For an E2EE Account, the CLI derives the password wrapping material locally and
uses a Home-issued challenge bound to the exact Account, credential operation,
and Home identity. Enrollment, change, recovery change, and removal reuse the
Account recovery secret already held by the signed-in CLI; they do not rotate
the Account signing identity or content key. If this CLI has only device-local
data-key material, sign in with the password or recovery key first. Keep
recovery keys private.

`--yes` records the CLI's direct confirmation for that exact Account Security
Action. A Home or Account setting that explicitly requires an approval still
wins; the CLI does not use a generic approval bypass.

Email verification and password-reset links contain one-time bearer capabilities.
For first password enrollment on an Account without a verified sign-in email,
`enroll-email-request` sends the dedicated authenticated enrollment intent; pass
the resulting bearer only to `auth password enroll --verification-token`. This
request is bound to the selected Home and cannot be made with an API token.
Opening a link performs a read-only preview; an explicit user action consumes it.
Do not copy these URLs into logs, analytics, or support tickets. The standalone
web document declares `no-referrer` before its first subresource, and the bundled
server adds `Referrer-Policy: no-referrer` on capability-bearing routes. If you
host the web app separately, preserve the document policy and add the same HTTP
response policy for `/auth/email/verify/*`, `/auth/password/reset/*`, and
`/join/*` as defense in depth.

## Optional Account Service recommendation

These settings are part of the 0.3 development implementation. They are not a configuration contract for released 0.2 servers.

Homes do not recommend an Account Service by default. Configure one explicitly when clients should offer account-based Home discovery alongside the Home's own authentication methods:

```bash
# Default: offer no Account Service from this Home.
HAPPIER_AUTH_SIGN_IN_SERVICE_MODE=disabled
```

Use `self` only when this same server is configured as an Account Directory. It does not start another process:

```bash
HAPPIER_AUTH_SIGN_IN_SERVICE_MODE=self
HAPPIER_ACCOUNT_SERVICE_DISPLAY_NAME=Acme
```

Or refer clients to a separate HTTPS Account Service (loopback HTTP is accepted only for local development):

```bash
HAPPIER_AUTH_SIGN_IN_SERVICE_MODE=external
HAPPIER_AUTH_SIGN_IN_SERVICE_URL=https://accounts.example.com
# Optional identity pin discovered from that service:
HAPPIER_AUTH_SIGN_IN_SERVICE_SERVER_IDENTITY_ID=srv_accounts
```

The recommendation is discovery policy, not authorization: it does not link an Account or allow that service to issue Home credentials without the normal verified enrollment flow.

Three details decide whether this configuration takes effect:

- `disabled` and `self` reject `HAPPIER_AUTH_SIGN_IN_SERVICE_URL` and
  `HAPPIER_AUTH_SIGN_IN_SERVICE_SERVER_IDENTITY_ID`. Setting either alongside them
  is recorded as a configuration error and no recommendation is published — the
  server does not guess which half you meant.
- `HAPPIER_ACCOUNT_SERVICE_DISPLAY_NAME` is published only by a server that is
  itself Account-Directory capable, and it is what clients render in the sign-in
  copy ("Create an account with Acme, then find or add your Home"). It must be
  non-empty, free of control characters, and within the directory label's UTF-8
  byte limit.
- A Home owner can switch this recommendation **off** from
  [Home administration](/self-hosting/home-administration) when the deployment
  offers one. They cannot point the Home at a different service: the endpoint is
  yours to set here.

## Running your own Account Service

These settings are part of the 0.3 development implementation. Released 0.2 servers are not Account Services.

Happier Cloud is only the default Account Service. Any Happier server can be one, for example a company's own sign-in service for its people and Homes. Clients never assume anything about a service: the sign-in methods, account creation, password reset and Home discovery they show all come from what the selected service advertises. People pick a service in **Settings → Account → Change service → Another service…**, which checks the address before anything is saved.

A server is an Account Service when all of these hold:

- It can sign Home-directory assertions. That key is derived from `HANDY_MASTER_SECRET`, which every server already needs; a server that has it advertises `capabilities.accountDirectory` in `GET /v1/features`.
- It publishes a stable identity and audience: set `HAPPIER_CANONICAL_SERVER_URL` (or `HAPPIER_PUBLIC_SERVER_URL`) to its public HTTPS address. Without a canonical URL, clients treat the server as "not an Account Service".
- Optionally, `HAPPIER_ACCOUNT_SERVICE_DISPLAY_NAME` names it in client copy ("Sign in to Acme Accounts"). Without it, clients name the service by the Home it is, or use a generic phrase.

Sign-in methods are the server's own authentication methods, published through `POST /v1/auth/entry` with `purpose: "account_service"`:

- **Account key** sign-in (Key Challenge v2) is on by default.
- **GitHub and OIDC** follow the [OAuth return URL](#oauth-return-url-required-for-githuboidc-self-hosting) and provider settings below.
- **Email and password** follows [Native email and password](#native-email-and-password-03-development):
  - `HAPPIER_FEATURE_AUTH_EMAIL_PASSWORD__ENABLED` turns sign-in on or off.
  - `HAPPIER_FEATURE_AUTH_EMAIL_PASSWORD__PROVISION_ENABLED` turns account creation on or off.
  - Account creation and "Forgot password?" need SMTP (`HAPPIER_AUTH_EMAIL_SMTP_HOST` and `HAPPIER_AUTH_EMAIL_FROM_ADDRESS` at minimum) **and** a link the service can build (a published Home connection descriptor plus an application origin), as described there. Until both are set, clients offer email and password sign-in only: no "Create an account" by email, and no mailed reset.

Signing in with a password to an Account Service gives the device the service's restricted Account Directory credential, never an ordinary Home credential. A Plain account gets it from the password route. An end-to-end encrypted account unlocks its key from the password and proves it to the service's Account Directory key challenge; the key stays on the device. Creating an account proves the mailbox first: the person enters an email, opens the confirmation link, then chooses a password. That link carries `purpose=account_service`, so the device that opens it finishes signing in to the service rather than to a Home.

## Auth methods (discovery)

The current 0.2 client path discovers authentication methods through `GET /v1/features`.
In the 0.3 development implementation, clients instead request the exact current
Home actions from `POST /v1/auth/entry`. They use the legacy feature response only
when that endpoint returns HTTP 404, 405, or 501. Network failures, other error
statuses, malformed JSON, and incompatible response shapes do not cause a legacy
downgrade.

The legacy feature response advertises auth entrypoints via:

- `capabilities.auth.methods[]` (preferred; method + action + mode)
- plus legacy surfaces like `capabilities.auth.signup.methods[]` for older clients

Each method can advertise multiple actions:

- `login` (sign in to an existing account)
- `provision` (create an account)
- `connect` (link an identity provider to an already-authenticated account)

And each action declares its account key mode:

- `keyed`: device-key account (default Happier model)
- `keyless`: no Account E2EE private material is required or persisted in the
  token-only credential (enterprise mode; typically paired with plaintext storage)

## Keyless authentication (enterprise)

Some deployments want accounts to work **without client-held Account E2EE private
material** (for example: company-managed identity, server-side indexing/search, and
simpler multi-device behavior). A previously E2EE Account may retain public
verification anchors/fingerprints on the server; those values cannot decrypt content
and are not part of a token-only credential. A truly keyless Account has no such
public Account bindings. A client may still create a private device-local key for
local cache or daemon restart secrets. That key is not an Account key, is not
uploaded, and is not required to authenticate on another device.

The target keyless contract supports authentication via:

- [mTLS auth](/self-hosting/auth-mtls)
- keyless OAuth login (GitHub/OIDC) when enabled by feature env vars

Bearer/external authentication is enough to authorize a plain account. It does not
derive or substitute for Account E2EE material.

:::caution Activation status
The complete token-only OAuth/OIDC/GitHub/mTLS, UI, and daemon onboarding flow is
still activation-closed while the remaining account-data migrations and composed
checks land. The settings below describe the fail-closed activation contract; their
presence does not mean the genuine-keyless product flow is currently ready for
production enablement.
:::

Keyless account auto-provisioning is intentionally guarded:

- enable keyless accounts: `HAPPIER_FEATURE_E2EE__KEYLESS_ACCOUNTS_ENABLED=1`
- allow plaintext storage (required for keyless accounts): `HAPPIER_FEATURE_ENCRYPTION__STORAGE_POLICY=optional|plaintext_only`
- for OAuth keyless login:
  - enable: `HAPPIER_FEATURE_AUTH_OAUTH__KEYLESS_ENABLED=1`
  - allowlist providers: `HAPPIER_FEATURE_AUTH_OAUTH__KEYLESS_PROVIDERS=github,okta,...`
  - allow first-login account creation: `HAPPIER_FEATURE_AUTH_OAUTH__KEYLESS_AUTO_PROVISION=1`
- for mTLS keyless login: see [mTLS auth](/self-hosting/auth-mtls)

Recommended hardening for plaintext/keyless deployments:

- seal plaintext account settings at rest: `HAPPIER_FEATURE_ENCRYPTION__PLAIN_ACCOUNT_SETTINGS_AT_REST=server_sealed` (default)
- seal plaintext account connected-service credentials at rest: `HAPPIER_FEATURE_ENCRYPTION__PLAIN_ACCOUNT_CREDENTIALS_AT_REST=server_sealed` (default)
- seal plaintext account Artifacts at rest: `HAPPIER_FEATURE_ENCRYPTION__PLAIN_ACCOUNT_ARTIFACTS_AT_REST=server_sealed` (default)

Note: `HAPPIER_FEATURE_ENCRYPTION__DEFAULT_ACCOUNT_MODE` controls only the default mode for **keyed** accounts and new sessions when the storage policy is `optional`. It does not gate keyless auto-provisioning.

### OAuth keyless provisioning choice (optional encryption servers)

When the server storage policy is `optional`, new users coming back from OAuth (GitHub/OIDC) may be prompted to choose:

- **End-to-end encrypted (E2EE)**: creates a device-key account; users must back up a secret key to restore on new devices.
- **Not encrypted (plaintext)**: creates a keyless/plain account; sign-in is seamless across devices, but the server can read stored content.

When the provider is enabled for **both** modes (keyed provisioning + keyless auto-provisioning), the client should show the choice.
When only one mode is available, the client should auto-select it (no extra screen).

On `plaintext_only` servers, clients should automatically choose plaintext. On `required_e2ee` servers, clients should not offer plaintext/keyless choices.

This provisioning choice is the post-activation behavior. Until the activation status
above changes, operators should keep keyless provisioning disabled.

### Operator recipes

**E2EE-only (public server) + GitHub required**

```bash
HAPPIER_FEATURE_ENCRYPTION__STORAGE_POLICY=required_e2ee

AUTH_ANONYMOUS_SIGNUP_ENABLED=false
AUTH_SIGNUP_PROVIDERS=github
AUTH_REQUIRED_LOGIN_PROVIDERS=github
```

**Keyless-only (enterprise) + plaintext-only + GitHub required — post-activation**

```bash
HAPPIER_FEATURE_ENCRYPTION__STORAGE_POLICY=plaintext_only
HAPPIER_FEATURE_E2EE__KEYLESS_ACCOUNTS_ENABLED=1

AUTH_ANONYMOUS_SIGNUP_ENABLED=false
AUTH_SIGNUP_PROVIDERS=
AUTH_REQUIRED_LOGIN_PROVIDERS=github

HAPPIER_FEATURE_AUTH_OAUTH__KEYLESS_ENABLED=1
HAPPIER_FEATURE_AUTH_OAUTH__KEYLESS_PROVIDERS=github
HAPPIER_FEATURE_AUTH_OAUTH__KEYLESS_AUTO_PROVISION=1
```

**Optional encryption (enterprise) + OAuth provisioning choice (GitHub) — post-activation**

```bash
HAPPIER_FEATURE_ENCRYPTION__STORAGE_POLICY=optional
HAPPIER_FEATURE_E2EE__KEYLESS_ACCOUNTS_ENABLED=1

AUTH_ANONYMOUS_SIGNUP_ENABLED=false
AUTH_SIGNUP_PROVIDERS=github
AUTH_REQUIRED_LOGIN_PROVIDERS=github

HAPPIER_FEATURE_AUTH_OAUTH__KEYLESS_ENABLED=1
HAPPIER_FEATURE_AUTH_OAUTH__KEYLESS_PROVIDERS=github
HAPPIER_FEATURE_AUTH_OAUTH__KEYLESS_AUTO_PROVISION=1
```

Optional: allow users to switch existing accounts (`e2ee ↔ plain`) when storage policy is `optional`:

```bash
HAPPIER_FEATURE_ENCRYPTION__ALLOW_ACCOUNT_OPTOUT=1
```

## Upgrade notes (operator guidance)

- **Clients first is usually safe** for keyed accounts (device-key model), because older servers still accept the core `/v1/auth` login flow.
- **Do not enable `plaintext_only`** until you have clients that support plaintext storage (older clients will fail because encrypted writes are rejected).
- If you enable **keyless OAuth auto-provisioning**, ensure your clients are new enough to understand the keyless flows advertised by `/v1/features` (otherwise users may see missing buttons or failed sign-in attempts).
- During the current expansion phase, keep keyless auto-provisioning disabled even if
  a development client can parse the advertised contracts.

## OAuth return URL (required for GitHub/OIDC self-hosting)

If you enable any external OAuth providers (GitHub and/or OIDC), the server must know where to redirect the browser **back to the client app** after OAuth completes.

- If you use the hosted web app, you don’t need to set anything (default is `https://cloud.happier.dev`).
- If you self-host the web app (or you’re using a local dev UI), you **must** configure one of:
  - `HAPPIER_WEBAPP_URL` (most common for web)
  - `HAPPIER_WEBAPP_OAUTH_RETURN_URL_BASE` (often used for mobile deep links or custom paths)

Otherwise, users will be redirected to the wrong place (or the redirect may be rejected as unsafe).

## Auth policy (env vars)

Use these env vars to control who can create accounts and whether provider identity is enforced for ongoing access.

### Signup / login policy

The following four recommendation and presentation settings require the 0.3 development implementation:

- `HAPPIER_AUTH_SIGN_IN_SERVICE_MODE` (`disabled`, `self`, or `external`; default `disabled`)
- `HAPPIER_AUTH_SIGN_IN_SERVICE_URL` (required only for `external`)
- `HAPPIER_AUTH_SIGN_IN_SERVICE_SERVER_IDENTITY_ID` (optional identity pin for `external`)
- `HAPPIER_ACCOUNT_SERVICE_DISPLAY_NAME` (optional bounded name emitted only by an Account Directory)

- `AUTH_ANONYMOUS_SIGNUP_ENABLED` (default `true`)
  - If `false`, anonymous account creation is disabled (`POST /v1/auth` will return `403 signup-disabled` for new users).
- `AUTH_SIGNUP_PROVIDERS` (CSV, default empty)
  - Enables signup through deployment-contributed providers (e.g. `github`, `okta`). Home-managed providers follow the console admission policy; see [Enterprise identity](/self-hosting/auth-enterprise-identity).
- `AUTH_REQUIRED_LOGIN_PROVIDERS` (CSV, default empty)
  - Enforces providers for ongoing access (e.g. `github`, `okta`).

### What enforcement applies to

When `AUTH_REQUIRED_LOGIN_PROVIDERS` is set, eligibility is enforced for:
- Authenticated HTTP routes (via the `authenticate` pre-handler)
- Socket.IO handshake (`/v1/updates`)

If a required provider is missing:
- Requests are rejected with `403 provider-required`.

### Offboarding / eligibility checks

If you use allowlists (GitHub org allowlists or OIDC allow rules), the server can re-check eligibility periodically and cache results on the identity record.

- `AUTH_OFFBOARDING_ENABLED`
  - Defaults to `true` when any *membership-based* allowlists are configured (GitHub org allowlist and/or OIDC allow rules); otherwise `false`.
- `AUTH_OFFBOARDING_INTERVAL_SECONDS` (default `86400`, clamp 60–86400)
- `AUTH_OFFBOARDING_STRICT` (default `false`)
  - When `true`, the server **fails closed** if it cannot re-check eligibility due to upstream downtime (enterprise lock-down mode).
