---
title: Iroh transport relay
description: Run the stock Iroh relay profile that carries encrypted Home and Machine traffic when a direct path is unavailable.
---

Run an Iroh transport relay when native Happier clients and daemons need a
publicly reachable rendezvous and forwarding service. This is separate from the
Happier relay that stores and synchronizes session data: the Iroh relay is a
stateless transport process and has no Happier application authority.

## Availability

This page describes the managed profile in the current **0.3 development
source**. It does not claim that an Iroh relay image is available in a stable or
preview release. Use an image produced by the repository publisher and deploy
it by immutable digest.

Native Iroh connectivity exists in the current development source, and so does
browser Home connectivity: in this development source a browser carries Home
HTTP and Socket.IO over Iroh when the Home publishes an exact endpoint and at
least one configured relay. Browser Machine transport is also wired through the
canonical finite file and attachment transfer owners in the development source,
including encrypted chunks, destination finalization, cancellation, and the
terminal no-fallback result. Its complete Chromium development journey has
passed, but this does not claim stable or preview availability, multi-browser
support, or certification for released targets; release validation remains
separate from this development-source path. The browser form is
relay-only and shows **Secure relay**, never **Direct**. A browser is never a
Home, and this adds no gateway, local-loopback emulation, JavaScript relay, or
browser Mutagen workspace-sync engine.

The managed profile runs stock `iroh-relay` 1.1.0 with forwarding and QUIC
address discovery (QAD) enabled. A forwarding-disabled QAD-only run remains a
planned development diagnostic; it has not been run as release evidence and is
not a supported production deployment or managed-product profile.

## What you need first

- An immutable `happierdev/iroh-relay` or
  `ghcr.io/happier-dev/iroh-relay` image reference in
  `registry/repository@sha256:digest` form.
- A TLS certificate chain and private key for the relay, stored as
  `certs/default.crt` and `certs/default.key` beside the deployment Compose
  file. The relay runs as numeric UID/GID `65532:65532`, so the mounted
  directory must be traversable and both files readable by that identity
  inside the container. Keep host permissions as restrictive as the platform
  permits while satisfying that access.
- Public TCP ports 80 and 443, and UDP port 7842.
- Measured link and instance capacity from which to choose the relay's receive
  token-bucket settings.

The repository's
[deployment README](https://github.com/happier-dev/happier/blob/dev/deploy/iroh-relay/README.md)
links the Compose file and pinned configuration and carries the complete build
notes.

## Run the managed profile

Set these values in the environment used by Docker Compose:

```bash
HAPPIER_IROH_RELAY_IMAGE=registry/repository@sha256:digest
HAPPIER_IROH_RELAY_RX_BYTES_PER_SECOND=<measured-positive-integer>
HAPPIER_IROH_RELAY_RX_MAX_BURST_BYTES=<measured-positive-integer>
```

Then start the deployment from a checkout:

```bash
docker compose -f deploy/iroh-relay/compose.yaml up -d
```

The versioned image owns the matching relay configuration template; Compose
mounts only the operator-managed TLS directory. The entrypoint writes the
effective configuration into the container's memory-only `/tmp` mount.

The two receive settings are upstream token-bucket controls. Derive them from
the capacity of the deployed link and instance; they are not Happier account
quotas. The receive rate must be a decimal integer from `10` through
`4294967295`; the pinned relay refills in 100ms intervals and rejects a lower
rate. The burst must be a decimal integer from `1` through `4294967295`,
matching the relay's `NonZeroU32` input. All three variables must be non-empty
or Compose stops before it starts the container; the relay entrypoint rejects
receive values outside those ranges.

Pinned `iroh-relay` 1.1.0 declares `accept_conn_limit` and
`accept_conn_burst`, but upstream documents them as unimplemented and
no-effect. Do not treat them as concurrent-endpoint or global-capacity controls.
This deployment does not add a Happier endpoint registry or custom limiter to
simulate them.

Compose only checks that the image variable is set. It does not look inside the
reference, so pinning the digest is your responsibility: a mutable tag would
start without complaint. The trustworthy image is the one the repository
publisher pushed with BuildKit SBOM and provenance attestations. The publisher
captures the pushed digest and inspects that exact multi-platform index for the
Linux AMD64 and ARM64 images and their attestation manifests. Take the reported
digest from that publication rather than from a tag that can move underneath
you.

The process exposes aggregate upstream metrics on container port 9090. The
provided Compose profile deliberately does not publish that port. Attach a
private metrics network or collector if you scrape it.

The runtime image includes the selected upstream MIT license and the
BSD-3-Clause notice required for the Tailscale-derived relay portions.

## Point your Home server at the relay

The relay process does not register itself anywhere. A Home server uses your relay only when its
environment selects it:

```bash
HAPPIER_IROH_RELAY_POLICY=automatic
HAPPIER_IROH_RELAY_URLS=https://relay.example.com
```

- `HAPPIER_IROH_RELAY_URLS` lists the relay URL you deployed — for this profile, the HTTPS origin
  serving TCP 443. Entries must be unique absolute HTTP(S) URLs without credentials, query
  material, or fragments.
- `HAPPIER_IROH_RELAY_POLICY` accepts `automatic` (the default) or `disabled` (direct-only,
  contacts no relay, cannot be combined with relay URLs). An `automatic` policy with no relay
  URLs stays direct-only: there is no ambient or default relay set.
- The Home advertises exactly these URLs in its connection descriptor, so clients and machines
  can reach it through your relay when no direct path works. The relay-only browser form requires
  at least one configured relay.
- An invalid explicit value fails the server's Iroh endpoint composition closed and keeps the
  ordinary HTTPS Home running. The machine daemon reads the same two variables where it runs.

These variables configure the Happier side, not the relay image above. The server's Iroh endpoint
additionally requires a stable `HAPPIER_CANONICAL_SERVER_URL` — see
[Environment variables](/self-hosting/env).

The local relay used by development transport tests is a test fixture. An ordinary Home or
development stack does not start it automatically. Default grant signing does not provision an
Iroh relay or enable a native carrier that is unavailable on the running computer.

Browser Home connections use the Home's published Iroh endpoint. Browser finite Machine transfers
use the target Machine's published endpoint and its configured relay URLs; setting relay URLs only
on the Home does not supply the Machine's missing endpoint or relay configuration. Both runtimes
must have a usable native carrier before they can publish those endpoints.

In current unreleased 0.3 source, bounded text-file previews use the existing filesystem Action
and Machine RPC, so they can work through the ordinary Home connection without an Iroh relay.
Downloads and other prepared finite transfers still require the Machine carrier. An older served
UI export can still send previews through finite transfer; rebuild and load the updated UI before
checking the new preview behavior.

### Persist the Home and Machine settings

Home and Machine runtimes persist these values through different owners:

- For a Personal Home, set the variables in the environment used for `happier home create` (local
  or `--ssh`). The Personal Home installer writes the normalized values into that Home's managed
  runtime configuration, and later reconciliation keeps them there.
- For this computer's Machine daemon, set the variables while running `happier service install`.
  The installer validates and normalizes the two supported values, writes only those canonical
  keys into the launchd, systemd, or Windows Scheduled Task definition, and restarts the service.
  Re-running `happier service install` without a relay override retains the values already in that
  service definition; `happier service repair` also retains them when replacing the selected
  service owned by the same Happier Home. Run the install command with new values to update them.

For direct-only operation, set `HAPPIER_IROH_RELAY_POLICY=disabled` and make sure
`HAPPIER_IROH_RELAY_URLS` is unset. Do not put relay credentials or unrelated shell variables into
either setting.

In the current 0.3 development clients, **Standard only** in the device's server settings is a
different choice: new Home connections and Machine transfers on that device do not acquire an
Iroh carrier. Existing finite transfers finish on their selected route. CLI authentication and
the Machine daemon can select the same mode with
`HAPPIER_HOME_CARRIER_POLICY=standard_only` in their process environment; the default is
`automatic`. An invalid explicit value stops that client operation. Standard only needs an
independently reachable HTTPS Home or eligible Standard Machine route; an Iroh-only target is
unavailable. Unlike the relay policy above, Standard only also prevents direct Iroh contact from
that client. It does not change the Home server's advertised endpoint for other clients. For a
managed Machine daemon, set the variable while running `happier service install`; the selected
mode is retained by later service updates and repair unless explicitly overridden.

## Trust and path selection

The managed profile accepts every EndpointId authenticated by Iroh and forwards
opaque encrypted transport. That admission grants transport only. The relay
does not receive the Happier database, application secrets, payload inspection,
or operation-level accounting. Home authentication and signed Machine grants
remain mandatory at the endpoints.

Native clients choose a working direct or relayed path automatically. Normal
users do not choose between those paths, and path changes do not change the
Home URL, credentials, or session identity. Direct-versus-relay details and
EndpointIds are technical diagnostics, not routine connection controls.

The applied native policy is either automatic or disabled. Automatic uses the
relay URLs explicitly configured for the endpoint and lets Iroh choose direct
or relayed reachability; disabled contacts no Iroh relay. In both cases,
the connection succeeds only when Iroh authenticates the remote peer as the
exact EndpointId selected from the Home or Machine descriptor. Relay URLs and
direct-address hints help find that endpoint but never prove its identity.

## Optional private admission

The managed profile has no admission callback. Happier Server does not provide
a default callback route.

A private deployment may use the stock HTTP callback only when an external
service owns a complete allowlist for every Home, Machine, and account-client
EndpointId the relay must carry. Configure all three values together:

```bash
HAPPIER_IROH_RELAY_ADMISSION_URL=https://admission.example.com/check
HAPPIER_IROH_RELAY_ADMISSION_TOKEN=<service-credential>
HAPPIER_IROH_RELAY_PRIVATE_ALLOWLIST_COMPLETE=true
```

The callback receives the authenticated identity in the `X-Iroh-NodeId`
header. This exact header applies to the pinned 1.1.0 relay and should be
re-checked before upgrading Iroh. The callback allows the endpoint only by
returning HTTP 200 with a body of exactly `true`; any other status or body
denies it. Do not build this callback from a partial
Home-only or Machine-only registry: the relay cannot infer application roles,
and an incomplete list denies legitimate endpoints. A public-client shared
token is not supported.

## When it goes wrong

- **Compose stops before it starts the container.** One of the three required
  variables is unset or empty. Compose does not look at the image reference
  itself, so also confirm you pinned a digest rather than a tag such as
  `latest` or `preview`.
- **The relay exits while reading receive limits.** The receive rate must be a
  decimal integer from `10` through `4294967295`, and the burst must be a
  decimal integer from `1` through `4294967295`; derive both from measured
  capacity.
- **TLS startup fails.** Confirm that `default.crt` contains the certificate
  chain and that `default.key` is its private key, mounted read-only under the
  deployment's `certs` directory.
- **A private callback denies every connection.** Confirm that all three
  admission values are present, that the URL is absolute HTTPS, and that the
  callback reads `X-Iroh-NodeId`.
- **The diagnostics show a relayed path.** This is not an authentication or
  application-policy failure by itself. Check endpoint authentication or
  signed Machine-grant errors separately.
- **The relay runs, but clients never use it.** The server's `HAPPIER_IROH_RELAY_URLS` is unset
  or does not match the deployed relay origin; with no relay URLs an `automatic` policy stays
  direct-only.
- **A browser transfer requires a direct machine connection despite enabled grant signing.**
  Check that the target Machine publishes an Iroh endpoint with at least one relay URL, declares
  finite import/export support, and that the client permits Iroh. Enabled transfer and signing
  gates do not establish those facts. A daemon reporting an unavailable native carrier cannot
  publish its endpoint; configuring a relay alone does not repair that carrier.
