## What is the pending queue?

The pending queue lets you **store messages for a session** without sending them to the agent immediately.

Pending messages are:

- **Session-wide**: anyone with edit access to a shared session can see and manage them.
- **Ordered**: you control the order they will be processed.
- **Editable**: you can edit, remove, or reorder them before they run.
- **Stored with the session**: pending content uses the same storage mode as the session transcript (encrypted by default, plaintext on deployments that use plaintext storage).

Pending messages **do not affect “unread”** indicators. Instead, you’ll see a separate **pending count badge**.

## Where you’ll see it

### Session list badge

In the session list, sessions with pending messages show a **pending count** badge (for example `3` or `99+`).

### In the session view

When a session has pending messages, a **“Pending (N)”** indicator appears in the session view. Tap it to open the **Pending messages** sheet.

For a resumable inactive Happier session, the composer remains available even when its target machine or daemon is offline. The session still shows **offline**; sending persists the message in Pending instead of implying that the Agent is already reachable.

A banner above the composer distinguishes four durable states:

- waiting for the offline machine and its daemon to return,
- waiting for a reachable daemon to start the session,
- kept queued without a start request, or
- a terminal start failure that needs an explicit retry.

Depending on the state, the banner offers **Retry**, **Resume**, or **Process when online**, plus **Keep queued** and **Auto-resume options**. A terminal failure is not retried on every reconnect; choose **Retry** or **Resume** when you want another attempt.

In unreleased 0.3 development source, queued Follow updates appear as source
notices. Several queued or delivering updates from one source share one notice
with a count; a **needs you** update takes precedence. Blocked or failed updates
stay separate. This changes the display, not the underlying queue or delivery.
Quiet Follow context waits for the next real input, so resuming an idle session
does not by itself consume every queued update.

## Managing pending messages (UI)

Open **Pending messages** from the session view indicator.

### Pending messages actions

For each pending message you can:

- **Move up / Move down**: changes the order the agent will process messages.
- **Edit**: update the message text before it runs.
- **Remove**: deletes the pending message (it won’t be processed).
- **Send now**: stops the current turn and sends the message immediately.

### Discarded messages

Sometimes messages end up in the **Discarded messages** section (for example, when switching a session from remote to local and the pending queue must not be processed).

From Discarded messages you can:

- **Re-queue**: move the message back into the pending queue.
- **Remove**: permanently delete it.
- **Send now**: send it immediately.

## Message sending settings

Go to **Settings → Session → Message sending**.

### Automatic resume after sending

This account preference controls future sends to resumable inactive sessions:

- **Now or when machine returns:** Happier queues the message and parks a request for the daemon on that session's exact machine. If the machine is offline, the request waits for daemon availability.
- **Only if machine is online (default):** Happier makes one resume attempt when you send and only if the exact machine is currently reachable. If the machine is unavailable or the attempt races with a disconnect, the message stays queued and does not authorize a later automatic start.
- **Never automatically:** Happier queues the message without requesting a session start. Use **Resume** from the composer banner when you are ready.

Changing the preference affects future sends only. It does not create or cancel a request for input already queued. For a manually queued offline message, **Process when online** authorizes automatic processing for that exact message without changing the account preference.

### Queue in agent (current)

Default behavior when everything is online:

- your message is written to the transcript immediately
- the agent processes it when ready

Safety fallback:

- if the session is **offline**, **resuming**, or the agent is **not ready yet**, Happier may store the message in the **pending queue first** to avoid losing it.
- if the session is currently under **local control** during an attach/local-control flow, Happier queues the message until the session is ready to resume remote processing.

### Interrupt & send

Aborts the current turn (if any), then sends your message immediately.

If the session needs to resume (or is offline), Happier may store the message in the **pending queue first** and then deliver it once the agent is ready.

### Pending until ready

Stores your message in the session’s pending queue and lets the agent pull it when ready.

This is the best option when you want to:

- queue up multiple messages and control their order,
- keep messages editable until the agent starts processing them,
- avoid losing a message when the agent is offline or not ready yet.

## Local-control sessions

Local control means the provider TUI is active in your terminal. Remote control means Happier is driving the same provider session in the background for the app.

For **Claude**, local control is exclusive. While the provider TUI owns the session, Happier does not inject app messages directly into that terminal process. Instead:

- the app stores the message in the session pending queue,
- the local Happier process watches for pending messages,
- if no local turn is running, Happier can switch the session back to remote processing and deliver the queued message,
- if a local turn is still running, Happier waits for that turn to finish, abort, or exit before switching back to remote.

This avoids interrupting an in-progress local Claude turn. Without this wait, sending an app message into a busy terminal TUI could cancel or corrupt the current provider turn.

For **OpenCode**, and for App Server sessions using Codex CLI 0.131.0 or newer on macOS or Linux, local control is shared. The provider TUI and Happier app stay connected to the same provider session, so app messages do not need the exclusive-control handoff path merely because a TUI is attached. Earlier Codex versions and Windows do not expose terminal attachment in 0.3.

You can always review queued messages from the **Pending messages** sheet before they run.

## Mixed-version behavior (server / agent compatibility)

The pending queue feature requires support from both:

- the **server** (pending queue endpoints + updates), and
- the **agent/CLI** that processes sessions (must know how to materialize pending into the transcript).

If your setup doesn’t support pending queues, the app will fall back to the normal message sending behavior and you won’t be able to rely on pending queue actions.

Modern unattended activation additionally requires server Pending Input V2 support and activation capability from the session's exact target machine. Older or mixed components retain the existing direct-wake fallback. Happier does not use this path to take over Direct or otherwise external sessions.

### Messages for an execution run (0.3 development)

An interactive Execution Run inside a Session uses the same Pending queue as
the main conversation, but with one exact Run recipient. Its rows, count, and
actions are shown in that Run's conversation; they do not inflate the main
Session's pending count or block another Run's queue.

Targeted delivery requires the server and the Session's exact daemon to
positively support the current target-aware admission contract. If either side
is older or incomplete, Happier refuses that targeted send with an update-
required result before creating a row. It never retries the message without its
recipient and never delivers it to the main conversation.

After a disconnect or restart, Happier may restore a Run that the daemon can
prove is resumable. A target proven terminal or permanently unavailable becomes
blocked on that Run, while a target that cannot yet be classified stays queued.
Use the visible retry or recovery action after checking the Run state; do not
submit the same uncertain message under a new identity.

When a caller sends and waits, the wait belongs to that exact accepted turn.
A timeout stops only the observation, not the Run. If Happier cannot prove the
turn's outcome, it reports **Outcome unknown** rather than treating parent
Session idle or the Run's eventual terminal state as success.

This is a Developer Preview contract in the current 0.3 source, not a released
availability claim.

## Tips

- If you’re queuing multiple thoughts, use **Move up / Move down** to ensure the agent processes them in the intended order.
- If you decide something is no longer relevant, **Remove** it before it runs.
- If you need something handled immediately, **Send now** is the fastest path.
- During local to remote switching, a short queued or waiting state is normal and helps avoid losing messages or interrupting an active local turn.
