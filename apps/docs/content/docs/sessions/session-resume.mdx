---
title: Resume inactive sessions
description: Resume an inactive Happier session from the app, web UI, or CLI without starting over.
---

Session resume lets you continue an **inactive Happier session** by asking the provider backend to reopen the same provider session, then reconnecting that provider session to the same Happier session.

<Callout type="info">
  Sending to a resumable inactive session while its machine is offline is currently available in development builds and is not yet a released contract.
</Callout>

This is different from:

- **Attach**: reconnecting to a session that is still running locally through its live terminal/provider host
- **Browse Direct sessions**: opening a provider-native session that Happier does not own yet
- **Resume ID**: starting a new session by resuming an existing provider session id (see [Resume an Agent session (Resume ID)](/sessions/resume-provider-sessions))
- **Starting a new session**: creating a fresh provider session with no vendor resume

## What “resume” means in Happier

For a stopped session, Agent resume is a strict workflow:

1. Happier finds the existing Happier session
2. Happier checks whether that session is actually **vendor-resumable**
3. Happier asks the backend/provider to resume the same vendor session
4. If that vendor resume fails, Happier shows an error instead of silently starting a new session

That strict behavior matters because it keeps one session identity and one transcript source of truth.

When a Happier-managed session resumes, Happier continues the existing session. It does **not** create a second imported-history pass just because you resumed it.

## When a session is resumable

A session is resumable only when all of these are true:

- the session is a normal Happier-managed session
- it is currently **inactive**
- it is **not archived**
- Happier has a valid provider resume id stored in session metadata
- the selected backend/provider supports resume for that session
- your current settings do not disable that backend

If any of those checks fail, Happier treats the session as **not resumable** and shows that clearly in the UI or CLI.

## App and web behavior

In the app or web UI, an inactive session can still accept input **only if it is resumable**.

Typical behavior:

- **Inactive + resumable + machine reachable**: you can send a message and Happier resumes the session first
- **Inactive + resumable + machine offline**: you can still send; Happier persists the message in Pending while the session continues to show offline
- **Inactive + not resumable**: input is disabled

The composer banner says whether the exact message is waiting for an offline machine, waiting for a reachable daemon, kept queued without activation, or blocked by a terminal start failure. It offers **Retry**, **Resume**, or **Process when online**, plus **Keep queued** and **Auto-resume options** as appropriate. A terminal failure waits for your explicit retry; reconnecting does not start an unlimited retry cycle.

Under **Settings → Session → Message sending**, **Automatic resume after sending** controls future inactive/offline sends. The default, **Only if machine is online**, makes one immediate attempt when the exact machine is reachable but never parks authorization for a later restart. You can instead choose **Now or when machine returns** or **Never automatically**. Changing it does not rewrite an existing request.

Modern unattended activation requires Pending Input V2 on the server and activation capability from the exact target machine. Older or mixed components keep the existing direct-wake fallback. Only the owning daemon performs unattended starts, and external or Direct sessions keep their existing takeover safeguards.

In unreleased 0.3 development source, **Stop session** from session Info and CLI
Stop hold the session until you explicitly resume it. Sending another message
does not clear that hold. Stops from machine resource controls—Processes,
widgets, Guard, Storage holder cleanup and the machine's Runs section—leave the
session eligible to wake under your automatic-resume setting, unless it was
already held. This distinction still awaits integrated live verification.

## CLI behavior

Happier CLI exposes two main workflows for resume.

### List sessions

```bash
happier session list
```

By default this prints a table with:

- shortened session id
- agent
- last updated time
- active state
- resume status
- title
- working directory path

Useful variants:

```bash
happier session list --resumable
happier session list --plain
happier session list --json
```

Use:

- `--resumable` to show only sessions that can currently be resumed
- `--plain` for the older one-line output format
- `--json` for scripting

### Resume interactively

<Callout type="info">
  The combined attach/resume selector and attaching to running sessions through `happier resume` are available in current development builds.
</Callout>

```bash
happier resume
```

In a real TTY, Happier opens one selector for running sessions you can attach to and inactive sessions you can resume. Unavailable actions are shown with a reason.

If your terminal does not support the interactive selector, list sessions with `happier session list` and continue by id.

### Resume by id

```bash
happier resume <session-id>
```

You can pass a full session id or an unambiguous prefix.

If the session is running and attachable, Happier uses the same attachment as `happier attach <session-id>`. Otherwise, for a stopped session, Happier:

1. resolves the session
2. validates that it is inactive, not archived, and vendor-resumable
3. restores the session’s working directory
4. resumes the provider session
5. reconnects that provider session to the same Happier session

An active session that cannot be attached fails with a clear error; Happier does not start another Agent as a fallback. Archived sessions and stopped sessions without the required resume information also fail.

## Resume a folderless session

<Callout type="info">
  Folderless resume is implemented in the 0.3 development line and awaits
  integrated verification. It is not a released contract.
</Callout>

The development resume flow keeps the same session and private working folder after a daemon
restart. Unarchive an archived session before resuming; archiving retains its files.

If that folder is missing, or the daemon cannot prove that it belongs to this session,
resume will stop rather than silently create an empty folder. The app will offer
**Continue in a fresh folder** and explain that the previous files are unavailable.
Choosing it explicitly resumes with an empty private folder while preserving the transcript.
Until you choose, no folder is created and any queued prompt stays queued. **Not now**
leaves the session stopped.

This recovery applies to folderless sessions. It does not promise restoration of lost files
or change the existing behavior of sessions started in a user-selected folder. See
[starting without a folder](/sessions/start-a-session#start-without-choosing-a-folder).

## Resume status in the CLI table

The `RESUME` column is a quick summary:

- `yes`: resumable
- `no(unsupported)`: that agent/backend does not support vendor resume
- `no(missing-id)`: the session does not have the provider resume id Happier needs
- `no(disabled)`: resume exists for that backend, but your current settings disable it
- `no(off)`: account settings disabled that backend entirely

## Codex-specific behavior

Codex resume in Happier normally uses the default App Server path. ACP resume is still available when you explicitly choose ACP.

Important points:

- Codex now defaults to **App Server** in Happier
- legacy `mcp_resume` behavior is gone
- if you opt Codex back to plain **MCP**, fresh sessions can still start there, but vendor resume is not available on that path
- for new Codex sessions, Happier does not silently fall back from the default App Server path; choose ACP or MCP explicitly if you want a different backend
- App Server is the default resumable path; ACP still works when you explicitly select it
- for an explicit **resume**, Happier stays strict and errors instead of falling back

So for Codex, “can I resume this session?” depends on the session metadata and on whether the current backend path supports resume for that session.

## Resume vs attach

Use **resume** when the session is inactive and the provider supports reopening that provider session.

Use **attach** when the session is still running locally and you want to reconnect to the live process:

```bash
happier attach <session-id>
```

If you are unsure:

- use `attach` for a still-running local session
- use `resume` for an inactive session you want to continue

Attach can mean different things depending on how the session was started:

- tmux reattach,
- focusing an existing Windows Terminal or Console host,
- or using a provider-native attach flow when the provider supports it.

## Resume vs Direct sessions

Direct sessions are provider-native sessions that Happier can inspect or follow, but that Happier does not fully own yet.

For those sessions:

- browsing/opening happens through the **Direct** sessions flow
- syncing/importing happens through **Take over + Sync**
- normal Happier resume applies after the session is a Happier-managed session and has valid vendor-resume metadata

## Things to check if resume is unavailable

Development builds preserve the Claude account directory saved by the session's CLI when the daemon resumes it. An explicit account-directory override on the new launch takes precedence. This saves the directory selection only, not API keys or other shell environment variables. Older sessions may lack the saved selection; start those from a terminal with the original account environment when needed.

If a session does not resume, check:

- is the session inactive rather than already running?
- is it archived?
- does it belong to the provider/backend you think it does?
- are you on the correct Happier server/account profile?
- for Codex, is the selected resume path available (App Server by default, or ACP when explicitly selected)?
- is the owning machine online and reachable from Happier?
